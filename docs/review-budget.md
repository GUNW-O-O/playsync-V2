# 리뷰 예산 — 서브에이전트로 티켓을 돌릴 때

**티켓을 서브에이전트에 분배할 때만 읽는다.** 혼자 고칠 때는 필요 없다.

숫자가 근거다. T29가 2시간 / 1.53M 토큰을 썼고, 그중 **태스크 리뷰 둘이 16분을
쓰고 아무것도 잡지 못했다.** 반면 **최종 전체 리뷰 하나가 Important 3건을 혼자
다 잡았다.** 아래 규칙은 전부 그 사실을 따라간다.

## 티켓을 한 세션 크기로 자른다

T29는 스키마 마이그레이션 + 새 API + 동작 삭제 + 시나리오였다. 티켓 하나가
아니다. 총량은 같아도 **세션 한도에 걸리지 않게** 자른다.

## 태스크를 덜 쪼갠다

**리뷰어가 이웃 태스크는 통과시키면서 이것만 반려할 수 있어야 태스크 경계다.**

T29의 Task 3은 3줄 삭제였는데 brief · dispatch · review-package · 리뷰 한
사이클을 통째로 먹었다. 설정 · 문서 · 스캐폴딩은 **그것을 필요로 하는 태스크에
접는다.**

## 태스크 리뷰는 동시성에 닿는 제품 코드를 추가하는 태스크만 받는다

삭제만 하는 태스크, 테스트 · 문서만 만지는 태스크는 **최종 전체 리뷰가 본다.**

## 최종 전체 리뷰는 자르지 않는다

**opus로 돌린다.** 여기서 아끼면 이 리포의 결과물(락 경계를 설명할 수 있는 것)
자체가 없어진다.

다만 **fix는 sonnet**이다 — 찾는 일이 끝난 뒤 목록대로 고치는 일에는 판단이 들지
않는다. T29에서 최종 fix 한 번이 20분으로 세션 최장이었다.

## 리뷰어에게 전체 스위트를 다시 돌리게 하지 않는다

통합 전체는 컨테이너 기동 포함 50초가 넘고, 숫자는 구현자 보고서에 이미 있다.
**돌려도 되는 명령을 dispatch에 명시한다.**

```
cd backend && KEEP_TEST_CONTAINERS=1 npx jest --config ./test/jest-int.json \
  --testPathPatterns <해당 스펙>
```

## RED 재현은 구현자가 하고, 리뷰어는 제일 위험한 단언 하나만 다시 본다

구현자에게 **실패한 단언의 expected/received를 그대로 옮기게** 하면 가짜 RED는
거기서 걸린다. 둘 다 제품 코드를 깨고 전체를 다시 돌릴 이유가 없다.

## dispatch 프롬프트는 짧게

프롬프트는 **내 컨텍스트에 남아 매 턴 다시 읽힌다.** 요구사항은 brief 파일이
갖고, dispatch에는 **brief가 모르는 것만** 적는다 — 앞 태스크가 만든 인터페이스,
내가 푼 모호함, 보고 파일 경로.
