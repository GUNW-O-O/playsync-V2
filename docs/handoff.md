- 이 문서가 대체하는 것: 「무엇을 녹화할 것인가」를 정하던 판. **그 결정은 끝났다.**

## 1. 결정은 끝났고 두 문서로 갔다

앞 세션이 「무엇을 한 화면에 담을 것인가」에서 멈춰 있었다. 열려 있던 질문
셋이 전부 닫혔다.

| 무엇 | 어디 |
|---|---|
| 설계 — 프레임 넷의 화면 · 마크 창 · 타일 배치 · 파일 이름 서른 개 | [`superpowers/specs/2026-08-24-settlement-demo-design.md`](./superpowers/specs/2026-08-24-settlement-demo-design.md) |
| 계획 — 태스크 일곱과 단계별 코드 | [`superpowers/plans/2026-08-24-settlement-demo-frames.md`](./superpowers/plans/2026-08-24-settlement-demo-frames.md) |
| 왜 이 촬영이 티켓인가 · 35명인 이유 · 촬영이 잡은 결함 넷 | [`tickets-audit.md`](./tickets-audit.md)의 T84 절 |
| 하네스 사용법 · 이름 규칙 | [`../frontend/e2e/README.md`](../frontend/e2e/README.md) |

**여기 다시 적지 않는다. 읽고 시작하라.**

정해진 것만 간추리면 이렇다.

- **순서를 바꿨다.** 등록 마감 대기 8분을 맨 뒤로 몰았다. 병합은 등록이
  열려 있어도 되기 때문이다(`releaseSeats`는 `WAITING`만 요구하고,
  마감을 요구하는 것은 `isFinalTable` 하나다). 그래야 리바인과 좌석 이동이
  한 프레임에 붙는다.
- **파이널 테이블에 셋을 남긴다.** 마무리 프레임의 폰 셋이 「남은 전원」이
  되어 고르는 임의성이 없어지고, 이미 나간 상금이 셋(6·5·4위)이라 확인
  대화의 「남은 상금」이 걷은 돈과 갈린다.
- **프레임 ③만 촬영 실행을 가로지른다.** 좌열이 `chop`, 우열이 `complete`다.
  같은 시드라 파이널 테이블에 남는 셋이 두 실행에서 같고, 그래서 좌우가
  **같은 사람의 다른 결말**이 된다.
- **이 브랜치는 자산까지다.** README를 세 층(동작한다 · 디테일 · 개발 문서)으로
  나누는 재구성은 **다음 브랜치**다 — 어느 그림을 어느 층에 놓느냐는 그림을
  다 보고 나야 서는 판단이다.

## 3. 리뷰가 잡은 것 — 둘 다 촬영 14분을 태워야 드러났을 것

타입 체커가 못 잡는 자리였다. 코드 태스크를 촬영 게이트 **앞에** 몰아 둔
이유가 이것이다.

| 무엇 | 왜 생겼나 |
|---|---|
| **둘째 판에 리바인 거절이 없다** | 순서를 바꾸면서 그 판이 마감 **앞**으로 왔다. 등록이 열려 있으면 `DealerService.resolveWinners`가 파산자 전원에게 리바인을 묻고 `waitForRebuyResponse`로 최대 15초를 락 밖에서 기다린다. 첫 판에는 있던 `declineRebuys`가 둘째 판에는 없었다 — 그 전에는 필요가 없었으니까 |
| **리바인 대기가 도달 불가능했다** | 리바인하는 배역을 1번 테이블에서 3번으로 옮겼는데, 그 앞의 「촬영 테이블만 한 판 돌고 리바인을 기다린다」를 같이 안 고쳤다. 3번 테이블은 아직 한 판도 안 돌아 스택이 0이 될 방법이 없다 — 30초 타임아웃으로 죽고 뒤의 병합·폰 코드가 **한 번도 실행되지 못한다** |

둘째 것은 **계획의 결함**이었다. 지금은 네 테이블이 다 첫 판을 돈 뒤에
리바인을 기다리되 **rebuyer의 테이블을 마지막에** 돌린다 — 리바인 물음이
15초만 열려 있어서, 먼저 돌리면 다른 테이블을 도는 동안 그 창이 닫힌다.

## 4. 다음 단계

### 4-1. 촬영 게이트 (Task 5)

**하나만 먼저 돌린다.**

```bash
node scripts/demo-settlement.mjs --only=complete
```

~14분. 이것이 태스크 2·3·4를 **한꺼번에** 검증하는 자리다. 셋을 한 번에
돌리면 실패를 44분 뒤에 안다.

돌기 전에 확인:

```powershell
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match 'playwright' }
```

출력이 있으면 죽이고 다시 본다. **`TaskStop`이 playwright 자식 프로세스를 안
죽인다** — 세 실행이 같은 DB에서 동시에 돌아 진단이 통째로 어긋난 적이 있다.

인프라는 `cd backend && docker compose up -d`. 지금 띄워 두었다.

통과하면 **자르기 전에** 마크와 면을 본다.

```bash
ls frontend/e2e/recordings/
node -e "console.log(require('./frontend/e2e/recordings/<폴더>/timeline.json').marks.map(m=>m.name).join('\n'))"
ls frontend/e2e/recordings/<폴더>/*.webm
```

- 마크가 계획의 열넷과 같은 순서인가. **`셋만 남는다`가 `마감` 뒤에 있어야 한다**
- 영상이 **열셋**인가 — `console` · `scoreboard` · `dealer-t1`~`t4` ·
  `seat-rebuyer` · `seat-mover` · `phone-rebuyer` · `phone-mover` ·
  `phone-final-1`~`3`

그 다음 나머지 둘.

```bash
node scripts/demo-settlement.mjs --only=chop --no-build
node scripts/demo-settlement.mjs --only=abort --no-build
```

**세 실행의 남은 셋이 같은 사람이어야 한다.** 다르면 프레임 ③의 주장이
거짓이 된다 — 원인은 시드가 아니라 시계다(촬영이 레벨 2를 넘겼다는 뜻).

## 5. 촬영을 돌릴 때 걸리는 것들

앞 세션이 여덟 번 돌려서 얻은 것이다. 안 지키면 12분씩 날린다.

- **촬영 중에 제품 소스를 고치지 마라.** Next dev가 hot reload하면서 워커가
  죽는다(`code=3221226505`). 백엔드도 nest watch라 같은 일이 난다
  (`ECONNREFUSED ::1:3001`).
- **시드는 개발 DB를 지운다.** 촬영마다 다시 깐다.
- 개발 서버 둘을 직접 띄웠다면 촬영 뒤 정리하라. `npm run demo:settlement`는
  프로덕션 빌드로 돌며 Playwright가 서버를 소유한다.
- `ffmpeg-static`의 바이너리는 postinstall로 받는다. 없으면
  `node node_modules/ffmpeg-static/install.js`.
