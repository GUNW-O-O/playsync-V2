## 2. 열려 있는 결정 — **무엇을 한 화면에 담을 것인가**

여기가 이번 세션이 멈춘 자리다.

`img/`에 들어가 있는 `s6`~`s9` 움짤 넷은 **장면 설계 없이 만든 것**이다.
흐름대로 `mark()`를 찍은 뒤 나중에 타일을 짐작했고, 그래서 74초짜리 움짤에
5초짜리 주장이 들어 있다. 사람이 그걸 지적했고, **순서를 바로잡는 중이다** —
무엇을 보여줄지 → 어떻게 붙일지 → 그 다음에 찍는다.

장면 1~5에는 그 설계가 문서로 있다
([`superpowers/specs/2026-08-08-readme-demo-design.md`](./superpowers/specs/2026-08-08-readme-demo-design.md)
§5). 장면마다 `화면(면 조합) · 산출 · 보이는 정합 · 짝`을 표로 못 박아 두고,
그것이 마크 위치와 타일 배치를 정한다. **정산도 같은 문서가 필요하다.**

### 2-1. 합의된 것

**주장 셋만 화면으로 남긴다.** 나머지는 시나리오 테스트에 맡긴다.

| 주장 | 근거 티켓 |
|---|---|
| 끝나는 길이 여럿인데 **등식은 하나** (`걷은 == 상금 + 환불 + 상점 몫`) | T79 · T80 · T82 |
| **엔트리는 사람 수가 아니다** — 리바인 하나가 상금권을 5→6으로 | T81 |
| **필드가 넷에서 하나로 줄어든다** | 규모 |

「못 누르는 이유를 화면이 적는다」(T83 · `FINISH_BLOCKERS`)는 **뺐다.** 스틸
`console-finish-blocked.png`로는 남아 있다.

### 2-2. 사람이 낸 프레임 안 둘

**프레임 ① 딜러 셋 + 전광판 (2×2)**

```
[딜러 T2] [딜러 T3]
[딜러 T4] [전광판 ]
```

세 테이블에서 동시에 여섯씩 올인 → 딜러가 승자 지명 → 다섯씩 사라진다 →
전광판 남은 인원 35→15. 이어서 **T3의 한 자리가 0에서 5,000으로 되살아나고**
전광판 엔트리가 36, 상금 목록이 다섯 줄에서 여섯 줄로.

리바인하는 사람을 **T3에 둔다** — 원인(딜러 타일)과 결과(전광판)가 한
프레임에 있어야 한다.

세 테이블은 **카메라로만** 연다. 게이트웨이가 그 테이블 소켓 전원에게
`renderGame`을 뿌리므로, 누르는 것은 계속 `fixtures/wire.ts`가 하고 태블릿은
보기만 한다. 비용이 거의 안 든다.

**프레임 ② 다섯 면을 2×2에 (한 칸에 폰 둘)**

```
[좌석 · 리바인한 사람(T3)] [좌석 · 다른 사람(T4)]
[상점 콘솔            ] [폰A | 폰B         ]
```

리바인 모달 수락 → 콘솔에서 T3·T4 좌석 해제 → 두 사람이 폰에서 **참가 OTP를
다시 보고** → 태블릿에 넣어 T1·T2에 앉는다 → 콘솔이 T3·T4를 닫는다.

병합①이 `T3→T1`, `T4→T2`라 **두 사람이 서로 다른 테이블로 흩어진다.** 폰이
둘인 것이 거기서 값을 한다.

### 2-3. 아직 답을 못 받은 것

**순서를 바꿔야 프레임 ②가 한 컷으로 붙는다.** 지금은 `첫 판 → 리바인 →
마감 대기(8분) → 병합`이라 리바인과 이동 사이에 대기가 통째로 낀다.

파이널 테이블 판정은 `!isRegistrationOpen && tableCount === 1`이고
(`store/session/final-table.ts`), **병합 자체는 등록이 열려 있어도 된다.**
마감이 필요한 것은 ICM 버튼이 열리는 순간뿐이다. 그러니 대기를 맨 뒤로 민다.

```
첫 판(4테이블) → 리바인 → 병합①(4→2) → 둘째 판 → 병합②(2→1)
  → [마감 대기 8분 · 통째로 버림] → 여섯째 탈락 → 마무리
```

실측으로 앞부분이 ~4분이라 레벨 1(10분) 안에 들어간다. **여섯째를 대기 뒤로
두는 이유**는 상금이 「마감 전 · 예상」 상태에서 나가면 안 되기 때문이다.

이 순서 변경에 사람의 승인을 못 받은 채 세션이 끝났다. **먼저 물어라.**

## 3. 그 아이디어를 얹으면 코드가 어떻게 바뀌나

**버릴 코드는 없다.** `wire.ts` · `playHand` · `mergeInto` · 시드 · 마크
체계가 전부 남는다. 얹는 것이지 갈아엎는 게 아니다.

| 무엇 | 지금 | 바꿀 것 |
|---|---|---|
| 딜러 면 | T1 하나만 화면 | T2·T3·T4도 화면 (카메라 전용) |
| 리바인하는 사람 | T1 (`ON_SCREEN.rebuyer = 'A5'`) | **T3** |
| 좌석 태블릿 배역 | 둘 다 T1 (살아남는 쪽 · 리바인 쪽) | T3 리바인한 사람 · T4 다른 사람 |
| 폰 | 안 연다 | 둘 (참가 OTP 재조회) |
| 좌석 해제 · 재착석 · 테이블 닫기 | 전부 REST (`mergeInto`) | 콘솔 클릭 · 태블릿 키패드 |
| 순서 | 리바인 → 대기 → 병합 | 리바인 → 병합 → … → 대기 |
| 마크 | 흐름 이정표 | **프레임 경계** (설계가 정한다) |

면이 열이 된다(딜러 4 · 전광판 · 콘솔 · 좌석 2 · 폰 2). 기존 촬영은 일곱이었다.
32GB 기계라 메모리는 문제 없고 원본이 take마다 ~200MB 나온다.

재착석은 `screen.ts`의 `sitDown`이 이미 있고, 폰의 OTP 재조회 흐름은 장면 1
(`demo/tournament.spec.ts`)에 그대로 있다. **새로 쓸 것이 적다.**

시드는 **손 안 댄다** — 배역은 스펙 상수(`ON_SCREEN`)에서 옮기면 된다.

## 4. 촬영을 돌릴 때 걸리는 것들

이번 세션에 여덟 번 돌려서 얻은 것이다. 안 지키면 12분씩 날린다.

- **`TaskStop`이 playwright 자식 프로세스를 안 죽인다.** 실제로 세 실행이 같은
  DB에서 동시에 돌아 진단이 통째로 어긋났다. 죽였으면
  `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match 'playwright' }`로
  **확인하고** 다음 촬영을 시작하라.
- **촬영 중에 제품 소스를 고치지 마라.** Next dev가 hot reload하면서 워커가
  죽는다(`code=3221226505`). 백엔드도 nest watch라 같은 일이 난다
  (`ECONNREFUSED ::1:3001`).
- **시드는 개발 DB를 지운다.** 촬영마다 다시 깐다.
- 개발 서버 둘을 직접 띄웠다면 촬영 뒤 정리하라. `npm run demo:settlement`는
  프로덕션 빌드로 돌며 Playwright가 서버를 소유한다.
- `ffmpeg-static`의 바이너리는 postinstall로 받는다. 없으면
  `node node_modules/ffmpeg-static/install.js`. 지금 리포에는 받아져 있다.

## 5. 산출물이 어디 있나

| 자리 | 무엇 | git |
|---|---|---|
| `frontend/e2e/recordings/` | 원본 webm + `timeline.json` | 무시됨 |
| `frontend/e2e/.shots/` | 촬영 중 찍은 스틸 | 무시됨 |
| `img/` | 자른 결과 (README에 붙는 것) | **추적됨** |

지금 남아 있는 정산 take는 **`마무리-ICM으로-닫는다` 하나**다. `complete`와
`abort`는 옛 이름으로 찍힌 것을 지웠다 — 둘 다 통과는 확인했지만 원본이 없다.

`img/`의 `s6-six-all-in` · `s7-entry-not-player` · `s8-four-tables-to-one` ·
`s9-close-icm`은 **설계 없이 만든 것이라 갈아 끼울 예정**이다. 정산 스틸 여덟은
그대로 쓸 만하다.
