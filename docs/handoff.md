## 지금 열려 있는 것 — T92

### 무엇을 고쳤나

로그인 상한(`POST /auth/login`, IP당 분당 120)에 걸린 참가자가 폰에서
`ThrottlerException: Too Many Requests`를 읽는다. 서버 액션이 429 본문의
`message`를 그대로 띄우기 때문이다. 그리고 한 번 넘기면 **그 문이 60초간
통째로 닫힌다** — 블록 동안 히트를 세지도 않고, 풀릴 때 카운터가 0이 된다.
행사장 전원이 Next 프로세스 하나로 접혀 같은 버킷을 쓰므로, 대회 직전 몰림에서
한 번 넘기면 줄 서 있는 사람 전부가 1분간 막힌다.

셋을 했다.

1. 블록 길이를 **30초**로 정했다(`throttle.ts`의 `blockDurationMs`). 모듈에만
   두면 인증 라우트에도 적용된다 — 라이브러리 해석 순서가 `라우트 → 모듈 → ttl`이고
   `authThrottle()`이 덮는 것은 창과 상한뿐이다.
2. 429 본문 문구를 **한국어**로 바꿨다. 옵션이 배열이면 라이브러리가 커스텀
   문구를 안 보므로 `{ throttlers, errorMessage }` 객체 형태로 넘긴다.
3. `handleLogin`·`handleRegister`가 **429일 때만** `Retry-After`를 읽어 몇 초 뒤에
   다시 시도하면 되는지 안내한다. 헤더가 없으면 초 없이 안내만 남긴다.

**값은 사용자가 정했다 — 블록 30초, 상한 120 유지. 최소 인스턴스 기준이다.**
다시 논의하지 말고 그대로 간다.

## 이 세션에서 배운 것 (반복하지 말 것)

- **계획이 화면과 라우트의 대응을 확인 없이 단정하면 물린다.** T90에서 목록
  화면이 다른 라우트를 읽는 것을 모르고 계획을 썼고, 브랜치를 중간에 늘렸다.
  T91부터는 프론트의 `fetch` 호출을 먼저 뒤지고 계획을 썼다.
- **「세 라우트가 한 버킷을 나눠 쓴다」는 거짓이다.** Nest의 기본 `generateKey`가
  컨트롤러·핸들러 이름을 키에 넣는다. 로그인·가입·딜러 인증이 각자 분당 120을
  따로 갖는다. 참인 것은 행사장 전원이 **로그인의** 120을 나눠 쓴다는 쪽이다.
- **측정 도구가 자기가 무엇을 재는지 확인해야 한다.** 문 앞 도구가 상한이 열린
  무대에서 「전부 통과」를 찍고 그걸 파일에 남기는 상태였다. 응답 헤더로
  무대를 확인하고 아니면 멈추게 고쳤다.
- **실패할 수 없는 검사는 지운다.** 「반복해서 읽어도 컬럼이 다시 열리지 않는다」가
  구조상 초록일 수밖에 없어 지웠다. 경고는 주석으로 남겼다.
