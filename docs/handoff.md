## T41이 무엇으로 바뀌었나

착수 직전에 질문이 한 겹 구체화되면서 원 설계(`2026-08-09-load-test-design.md`)의
램프 모양을 바꿨다.

> 동시접속을 어디까지 커버하나, 그리고 동시접속자가 많을 때 피크 부하를
> 어디까지 견디나.

**두 질문은 같은 실행의 서로 다른 구간이 답한다.** 그래서 램프를 성장형으로
바꾸고 구간에 태그를 갈랐다.

| | 원 설계 | 지금 |
|---|---|---|
| 램프 모양 | 단계마다 세우고 잰다 | **붙은 테이블은 끝까지 돈다.** 계속 붙인다 |
| 인원 | 자연 감소 | **무한 리바인.** 탈락자가 즉시 다시 앉는다 |
| 봇 액션 | 콜만 | 체크·콜 65 / 레이즈 20 / 폴드 15 |
| 딜러 승자 | 폴드 안 한 전원(보드 하이) | **무작위 한 명** |
| 중단 | 서버 lag 붕괴선 | + **사용자 불편선(내 액션 p95 1초)** |
| 램프 A·B | 시나리오 둘 | 파일 하나 + `LOAD_TABLES_PER_STORE` |
| 대회 | 램프가 실행 중에 만든다 | **시드가 미리 세운다**(`LOAD_STORES`, 기본 12) |

마지막 줄이 착수 직전에 뒤집은 자리다. **k6에 VU 간 공유가 없어 7번째 VU가
앞선 VU가 만든 대회의 id를 알 방법이 없다.** 그리고 시점으로 가르면 애초에
측정 밖이 맞다 — 대회 생성은 대회 몇 시간~며칠 전에 한 번 하는 일이고, 직전에
몰리는 것은 로그인과 착석이다. T40이 bcrypt의 `hash`와 `compare`를 가른 것과
같은 판단이다.

## 왜 무한 리바인인가 — 지금 봇은 아무도 안 터진다

딜러 봇이 폴드 안 한 **전원**을 한 그룹으로 넣어(보드 하이) 팟이 낸 만큼
되돌아오고, 좌석 봇이 콜만 하니 스택이 갈리지도 않는다. 결과로
`resolveWinners`의 리바인 분기(`dealer.service.ts:309`)가 **한 번도 실행되지
않는다.** 부하의 한 갈래(리바인 · 탈락 · 사이드팟)가 통째로 비어 있다.

딜러가 승자를 하나로 고르면 칩이 쏠려 탈락자가 나오고, 좌석 봇이
`REBUY_PROMPT`에 즉시 수락하면 좌석이 비지 않는다. 대가는 `processRebuy`가 락
**밖에서** 최대 15초 기다리는 동안 `HAND_END`가 다음 핸드를 막는 것이다 —
핸드 주기가 늘어나지만 실제 대회도 그렇다.

## 중단선 — 사람이 "이거 왜 이래"라고 말하는 지점

| 선 | 내 액션 p95 | 사람이 느끼는 것 |
|---|---|---|
| 합격 | 200ms | 즉각 |
| **불편** | **1초** | **"이거 왜 이래"** |
| 실패 | 3초 | 안 먹은 줄 알고 **다시 누른다.** 중복 액션이 또 얹힌다 |

일반 웹보다 낮게 잡는 이유가 도메인에 있다. 턴 타이머가 30초라 지연이 커지면
증상이 "느리다"가 아니라 **폴드당한다**로 바뀐다.

중단은 먼저 닿는 것으로 한다 — 테이블 VU가 자기 롤링 창 30건의 p95로, 모니터가
서버 lag으로, 각각 **연속 2회**에 `test.abort()`. k6 `thresholds`로는 못 한다:
실행 전체 누적이라 성장 램프에서 앞 단계가 뒤 단계를 희석한다.

## 다음 세션이 할 일

계획의 태스크 1부터 순서대로. 각 태스크에 실제 코드와 검증 명령이 들어 있다.

| | | 검증 |
|---|---|---|
| 1 | `createSession`이 빈 스냅샷을 세운다 | 통합 RED→GREEN |
| 2 | 시드가 상점·대회를 12개 | 매니페스트 + 스모크 |
| 3 | 봇: 액션 믹스 · 승자 한 명 · 리바인 수락 | `raises`·`folds`·`rebuysAccepted` > 0 |
| 4 | 성장 램프 (`load/scenarios/ramp.js`) | 짧은 램프로 배선 확인 |
| 5 | 재접속 폭발 | 고원 한가운데 |
| 6 | 실행 · 결과 문서 · 기록 갱신 | 램프 B → 램프 A |

**세션이 모자라면 자르는 순서**: 태스크 5 → 램프 A → 그 앞은 자르지 않는다.
램프 B(O(T²) 곡선)가 설계 문서가 말한 "부하테스트의 첫 산출물"이다.

실행 방식은 아직 안 정했다. 서브에이전트(태스크마다 새 에이전트, 사이에 리뷰)와
인라인 둘 중 하나다. CLAUDE.md의 리뷰 예산대로면 **태스크 리뷰는 태스크 1**
(동시성에 닿는 제품 코드)만 받고 나머지는 최종 전체 리뷰가 본다.

## 착수 전에 알아야 할 제품 결함 하나

**`createSession`이 첫 테이블에 빈 스냅샷을 세우지 않는다**
(`session.service.ts:181` — `setSeatBitmap`만). `createTable`은 T38 이후 둘 다
부른다(`:220`, `:235`). 즉 T38의 불변식("테이블이 있으면 스냅샷이 있다")이
지금 **경로 하나에서만 참**이다.

드러나는 순서는 딜러가 손님보다 먼저 붙을 때다 — `GET /playsync/:tableId`가
500이고(`playsync.service.ts:41`), WS는 `data: null`을 조용히 보내 화면이 빈
펠트로 선다. 착석이 `createEmptyTableState`로 덮어 주므로
(`entry.service.ts:267`) 손님이 먼저 앉으면 안 보인다.

램프는 이 자리를 밟지 않는다(시드가 대회를 세우고, 시드는 `setEmptySnapshot`을
이미 쓴다). 그래도 태스크 1로 고치는 이유는 이것이 제품 경로의 결함이기
때문이다.

## 돌려 보는 법

**순서가 중요하다.** `npm run test:int`가 끝나며 컨테이너를 내리는데 tmpfs라
데이터가 사라진다 — 시드를 먼저 돌리고 통합 테스트를 돌리면 무대가 날아간다.

```bash
npm run load:up        # 백엔드를 1코어 컨테이너로 (첫 빌드 몇 분)
npm run seed:load      # 무대 (전부 지우고 다시)
npm run load:smoke     # 스모크
npm run load:down      # 정리
```

태스크 4가 붙이는 것:

```bash
npm run load:ramp-b    # 대회 하나 안에서 테이블을 늘린다 (O(T²))
npm run load:ramp-a    # 6테이블마다 다음 대회로
```

통합 테스트를 반복해서 돌릴 때:

```bash
cd backend && KEEP_TEST_CONTAINERS=1 npx jest --config ./test/jest-int.json \
  --testPathPatterns <해당 스펙>
```

시드를 호스트에서 돌릴 때는 테스트 인프라를 가리켜야 한다.

```bash
DATABASE_URL="postgresql://test:test@127.0.0.1:5433/playsync_test" \
REDIS_HOST=127.0.0.1 REDIS_PORT=6380 REDIS_PASSWORD=test \
npm run seed:load
```

마지막 스모크 실측(T40 시점, 생각 시간 0):

```

      · lag 중앙 0.57ms · CPU 22.3% · rss 201MB · 경고 0 붕괴 0
```

## 램프 중에 터진 것을 어떻게 다루나

| | 어떻게 |
|---|---|
| 장부 · 락 · 트랜잭션 경계 | **우선 고치고 진행한다.** 하네스 완주보다 장부가 먼저다 |
| 나머지 | 티켓으로 적고 램프를 계속 돌린다 |

이미 알고 있는 후보 둘.

- **T42 — 레이스 컨디션 전수조사.** 스냅샷을 고치는 경로 열한 곳이 "락 안에서
  다시 읽는다"를 각자 손으로 지킨다. `enterSeat`의 재읽기
  (`entry.service.ts:263`)를 지워도 아무 테스트도 빨개지지 않는다(T37이 세
  라운드로 확인). 램프가 그 창을 실제로 열면 앞으로 당긴다.
- **테이블 생성 동시 409.** `insertTable`이 트랜잭션 안에서 `tableOrder`
  최댓값을 뽑고 최종 방어가 유니크 제약이라, 여러 VU가 같이 열면 진 쪽이 409를
  받는다. 봇이 재시도하고 **그 횟수 자체를 지표로 남긴다.**

- **등록 마감 권위 이원화**(T31 이월). 자동 마감이 Redis에만 반영되고 결제

  지금 시드는 600분이라 안 넘는다.

## 함정 모음

봇을 짜며 실제로 밟은 것들이다. 전부 **조용히 잘못된 수치를 냈다.**

- **지연 측정 창은 큐여야 한다.** 창 하나를 두고 새 액션을 막으면 테이블이
  멈춘다 — 브로드캐스트 하나를 소켓 열 개가 각자 처리하는데, 세 번째가 "내
  차례다"를 볼 때는 아직 일곱이 안 받아 창이 열려 있다.
- **같은 소켓의 중복 예약을 막아야 한다.** 안 막으면 생각 시간이 그대로 지연
  으로 잡힌다(실측에서 정확히 `THINK_MS`만큼 나왔다).
- **WS 경로는 `/playsync`다.** 루트로 붙으면 핸드셰이크 이전에 거절돼 서버
  로그에도 남지 않는다.
- **WS 티켓은 1회용이다.** 소켓마다 새로 받는다 — 재접속 폭발이 REST 부하이기도
  한 이유다.
- **`prisma generate`가 `nest build`보다 앞이다.** 아니면 TS2305로 죽는다.
- **닉네임은 3~10자다.** 램프에서 순번이 커지면 접두사 길이가 상한을 넘는다.
- **메트릭 응답의 `resolutionMs`가 지연의 바닥값이다.** 유휴 서버도 p50이 약
  10ms다. 빼고 읽어야 한다.
- **`teardown`과 `handleSummary` 사이에 모듈 상태가 이어지지 않는다.** 서버
  지표는 모니터가 기록한 k6 지표에서 읽는다.
- **계정 풀보다 램프가 커지면 조용히 전부 신규 가입으로 넘어간다.** bcrypt가
  두 배가 되어 정원이 낮게 나온다. `signups`/`logins` 비율로 확인한다 — 풀은
  600이고 66테이블(594명)이 상한이다.
- **Git Bash에서 k6를 직접 부를 때는 `MSYS_NO_PATHCONV=1`이 필요하다.**
  `/load/...`를 윈도우 경로로 바꿔 버린다. npm 스크립트는 cmd를 타므로 무관하다.
