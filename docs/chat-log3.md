## 3. 병목 위치 — 사용자가 AI 진단을 두 번 정정

- **사용자 요청(요지):** "playwright를 쓰라는말이 아니라 뼈대를 사용하라는거였고, ws가 tableState를 직렬화해서 전송하는게 제일 병목인걸 알고있었음." 이어서 "아니 직렬화는 v1때도 한번할껄? 이 직렬화된걸 ws의 접속자마다 보내주는게 병목이라는거아님?"
- **AI 제안:** 처음엔 `JSON.stringify`가 이미 루프 밖(`ws.gateway.ts:178`)이라 "v1 때 들었던 소켓마다 직렬화는 지금 코드에 없다"고 답 — 사용자가 짚은 병목의 모양이 다르다고 반박했음.
- **추가 질문·문제제기:** 사용자가 "직렬화는 1회가 맞고, 그 문자열을 접속자 수만큼 밀어내는 것이 병목"이라고 재지적
- **사람 판단:** 병목은 직렬화가 아니라 fan-out 자체 — 같은 문자열을 소켓 수만큼 write하는 비용
- **근거:** v1에서 이 부분을 준비할 때 "여기가 제일 병목"이라는 지적을 들었음
- **결과:** AI가 오류 인정("내가 틀리게 말했다"). 그 방향으로 다시 뒤져 곱셈이 두 겹인 자리를 찾음 — `entry.service.ts:327-328`의 `getTournamentTables`(`hgetall`, 테이블 수에 비례한 페이로드)를 대회 전체 소켓에 `SEAT_LIST_UPDATED`로 브로드캐스트, 즉 한 명 착석마다 O(테이블²). 최악 지점이 게임 중이 아니라 **등록 구간**이라는 것이 드러남. 부하테스트의 1차 산출물로 두고 수정은 별건으로 미룸.

## 4. 대회 규모 조사와 pub/sub 도입 순서

- **사용자 요청(요지):** 동네펍 / 한국 대회 / WSOP급 실제 규모를 파악해달라. "한 행사장 한 프로세스를 깨는 것"이 곧 대규모는 pub/sub부터 깔고 시작해야 한다는 뜻인가? 여러 인스턴스로 나눠 시작해야 하나? 한 인스턴스에서 동네펍 몇 상점까지 커버되는가부터 시작하면?
- **AI 제안:** 규모 조사 결과(WSOP 2025 총 9,735 엔트리이지만 Day 1 플라이트 넷으로 갈라 최대 동시 착석은 Day 1d 4,997명·약 560테이블 / 국내 수치는 공개 자료가 얕아 역산 추정) 제시. pub/sub은 마지막이라고 답 — ① 소켓당 UTF-8 인코딩 제거 → ② 메시지 크기 축소 → ③ 프로세스 여럿 + 대회별 고정 배정 → ④ Redis pub/sub. 브로드캐스트가 대회 경계를 안 넘으므로 대회를 프로세스에 고정 배정하면 pub/sub 없이 코어를 다 쓸 수 있고, pub/sub은 한 대회가 프로세스 하나에 안 들어갈 때(WSOP급 하나)만 필요.
- **사람 판단:** "한 인스턴스에 동네펍 몇 상점"을 1차 산출물로 앞세우라
- **근거:** 사용자가 물은 질문 자체가 그것이었음 (SaaS로 상점 여럿을 한 인스턴스에 얹을 수 있나)
- **결과:** 램프 A(동네펍 대회 복제 수)가 주력, 램프 B(대회 하나의 테이블 수)가 정원, 램프 C(대규모 1회)로 재편.

## 5. 램프 둘로 확정 + 도착 프로필

- **사용자 요청(요지):** "한대회에서 테이블을 계속 늘려가면서 부하를 늘리는(wsop급)"과 "동네펍 몇개까지 커버가능한가" 이 두 가지가 있어야 할 것 같다. 홀덤은 모든 참여자가 한 번에 와서 일괄 시작하지 않는데 부하테스트는 그냥 최악 상황에서 돌리면 되는 건가?
- **AI 제안:** 램프 C를 접고 B의 끝점으로 흡수(B를 계속 늘리면 그게 WSOP급). 최악 하나만 재면 답이 "정원"이 아니라 "스파이크 내성"이 되어 질문이 안 닫힌다며 도착 프로필 셋 제시 — 현실 등록 / 재접속 폭발 / 정상 운영.
- **추가 질문·문제제기:** "전원동시는 jitter로 방어해놓긴했는데 저 구성 맞음. 리바인마감전에서부터 대회인원 피크이고 마감후는 사람이 줄기만하니 맞을듯"
- **사람 판단:** 램프 2개 × 프로필 3개 구성 수용. 다만 현실 등록의 정점은 대회 시작이 아니라 **리바인 마감 직전**이고 마감 후는 인원이 줄기만 한다.
- **근거:** 대회 인원 피크가 리바인 마감 직전이라는 도메인 지식
- **결과:** 프로필 1의 정점을 `rebuyUntil` 직전으로 고침 — 등록 부하와 게임 부하가 겹치는 유일한 구간이라 여기가 진짜 최악이고, 램프 실행 시간도 마감까지만 돌리면 되어 짧아짐. 한편 사용자의 jitter 전제는 AI 조사로 반증됨: `retryAsync`는 프로덕션 호출자가 `playsync.service.ts:238` 한 곳(체크포인트 DB 쓰기 재시도)뿐이고 좌석 클라이언트(`SeatGameClient.tsx:118`)는 자동 재접속 자체가 없어 지터가 안 걸림. 프로필 2는 그대로 유효.

## 6. 메트릭 엔드포인트를 제품 코드에 넣을지

- **추가 질문·문제제기:** "딜레이는 node.js의 자체기능 on/off 한다는거?"
- **사람 판단:** 환경변수 게이트로 넣는다
- **근거:** (근거 미명시 — "변수로하는게 맞는것같음")
- **결과:** `LOAD_METRICS=1`일 때만 `h.enable()`과 `GET /internal/metrics` 라우트 등록. 기본값이면 둘 다 안 일어나고 제품 경로에는 조건문 하나만 남음. 설계 문서에 확정 사항으로 반영. T39에서 실제로 구현되고 게이트가 닫히는 것(라우트 매핑 0건, 404)까지 실측 확인됨.

## 9. Task 3 — 락을 블랙박스로 증명 못 한 세 라운드의 처분

- **사용자 요청(요지):** (없음 — AI가 판단을 요청한 자리)
- **AI 제안:** Task 3(동시 액션 테스트)이 세 라운드를 돌았는데 RED가 0/3 — ① 팟 고정값 단언은 도착 순서 의존이라 플레이키, ② 기여합==팟 불변식은 스냅샷이 Redis 키 하나 통째 read-modify-SET이라 락을 없애도 절대 빨개지지 않음, ③ `enterSeat`은 Redis에 닿기 전 Prisma 왕복이 있어 `handleAction`과 시간상 겹치지 않아 레이스 창이 안 열림. 락 자체는 `redis.service.int-spec.ts:37`, 늦은 참가는 `entry.service.int-spec.ts:388`이 이미 커버하므로 **커밋 셋(`09e1404`, `bc89cb1`, `26ab9b0`)을 되돌리고 삭제**하자고 권함.
- **추가 질문·문제제기:** 사용자가 중간에 "이 테스트가 보는 건 착석과 액션이 같은 TableState에 둘 다 남는가 아니냐"고 짚어 AI가 테스트의 값을 재해석하게 만들었음
- **사람 판단:** 삭제하지 않는다. "커밋을 증거로 남기고 핸드액션과 착석 레이스컨디션은 추후 티켓 작업으로 남기고, 정합성 관련이니 제일 앞의 티켓으로."

- **결과:** 커밋 셋 유지 + 무엇을 증명하고 무엇을 증명하지 않는지를 JSDoc으로 파일에 박는 커밋(`83edadb`) 추가. 레이스는 백로그 맨 앞 새 티켓으로. T37은 통합 340/28, 타입 0으로 닫힘(main 대비 13커밋). 최종 리뷰가 문서의 RED 재현 절차 오류(`@@unique` 주석 처리는 마이그레이션을 안 돌리면 DB 제약이 그대로 남아 통하지 않음)를 포함해 9건을 잡아 전부 수정.

## 10. T38 성격 전환 — 테스트가 아니라 제품 코드를 고친다

- **사용자 요청(요지):** "실제코드자체가 이 레이스컨디션을 해결하는방안으로 수정함. 이 테스트가 통과하기위함이 아닌 실제 코드를 고치는. 단순히 핸드가 진행중일때는 폴드상태로 앉는다였는데 앉는동시에 액션이 나온다는점을 놓쳤음."
- **AI 제안:** 원래는 테스트가 `withTableLock`을 먼저 쥐어 타이밍 창을 여는 방식(제품 코드 0줄, 스텁 0개)을 제안했음
- **사람 판단:** 테스트 훅이 아니라 제품 코드를 고치는 티켓으로 바꾼다. 놓친 것은 "핸드 진행 중에는 폴드 상태로 앉는다"만 봤고 **앉는 동시에 액션이 나온다**는 점.
- **근거:** 테스트를 통과시키려는 것이 아니라 실제 결함을 고쳐야 함
- **결과:** AI가 코드를 다시 조사 — 폴드 상태 착석 설계 자체는 성립하고(`shouldGoToNextPhase`, `findNextActiveSeat`, `nextPhase` 리셋이 전부 `hasFolded`를 건너뜀), 깨지는 것은 판정이 아니라 쓰기. 스냅샷을 고치는 경로가 11곳이고 전부 `withTableLock → getSnapShot → 고침 → saveSnapShot`을 손으로 반복하며, `enterSeat`의 락 안 재읽기(`entry.service.ts:263`)가 유일한 방어인데 관행이지 구조가 아님. ## 35. `checkAndSyncBlindLevel`에 락을 걸지 않는다

- **사용자 요청(요지):** "checkAndSyncBlindLevel은 여러 테이블이 실제로 동시에 값을 가져와야 하고, 락을 만들면 한 테이블이 시작 완료 전까지는 다른 테이블이 시작할 수가 없음." 이어서 다음 티켓 후보를 어려운 용어 없이 전체적으로 설명해 달라고 요청.
- **AI 제안:** 직전 턴까지 AI는 이 자리를 "조사가 안 짚은 락 없는 read-modify-write"로 남은 위험처럼 제시했고, 다음 티켓 후보로 "근거를 주석으로 박기"를 올려 뒀다.
- **사람 판단:** **락을 걸면 안 되는 자리**라고 사람이 직접 판정. AI의 문제 제기를 방향째로 뒤집었다.
- **근거:** 사람의 도메인 근거 — 블라인드 시계는 대회 전체가 같이 보는 값이고, 락을 걸면 A 테이블이 핸드를 시작하는 동안 B 테이블이 못 시작한다. 테이블별 독립 실행을 위해 테이블 단위로 잡아 둔 락을 대회 단위로 되돌리는 셈이다.
- **결과:** 이 자리는 코드 변경 대상에서 빠지고 "그 판단을 주석으로 남기는 일"로만 축소. 이후 핸드오프의 「하지 말 것」에 기록됨.
