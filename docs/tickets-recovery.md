## 완료

### T93 — 소켓이 끊기면 단말이 스스로 돌아오지 않는다

`onclose`가 에러 문구만 세우고 다시 붙지 않았다. **#114**가 좌석·딜러의 배선을
`useTableSocket` 하나로 모으고, 재접속 규칙을 `reconnect-policy.ts`로 뺐다 —
`Retry-After` 바닥 + 지터, 딜러는 좌석보다 늦게 붙는다.

**왜 못 잡았나**: 끊었다 다시 붙이는 시나리오가 e2e에도 부하 무대에도 없었다.

### T94 — 재시작이 차례였던 사람을 자동 폴드시킨다

블라인드 시계는 정지만큼 밀었는데 턴 시계는 아무도 안 밀었다. 폴드 경로가
둘이었다 — 큐에 남은 타임아웃 잡, 절대 시각인 `actionDeadline`. **#113**이
부팅에서 세대를 올려 잡을 무효로 만들고 마감을 다시 찍었다. 유예 60초는 T95가
걷어냈다.

**왜 못 잡았나**: 복구 스펙이 스냅샷과 블라인드만 봤다. 큐의 잡을 부팅 뒤에
돌려 보는 자리가 없었다.

### T95 — 정지와 재개가 화면에 없다

**#115**가 복구를 「멈춰 세우기」로 바꿨다 — `actionDeadline` 삭제, 세대 올림,
`TableState.resumePending`. 다시 여는 것은 딜러가 누르는 `DealerService.resumeTable`이고,
`resumePending`인 테이블은 좌석 액션을 거절한다.

### T96 — 소켓이 없는 화면은 정지를 모른다

REST로 읽는 폰·전광판이 `resumePending`을 못 봤고, 블라인드는 부팅 순간부터
흘렀다. **#116**이 좀비 소켓을 치우고(ping/pong · `keepalive` 침묵), **#117**이
`SYNCING`을 되살려 딜러 n/n까지 블라인드를 `pausedAt`에서 멈췄다. 설계는
[스펙](./superpowers/specs/2026-09-11-t96-syncing-design.md).

**왜 못 잡았나**: 부팅 보정을 단언하던 복구 검사 일곱이 **보정이 부팅에 있다는
것 자체**를 사실로 삼고 있었다.

## 대기 — Redis만 죽는 경로

**T93~T96은 전부 부팅이 시작점이다**(`RecoveryService.onApplicationBootstrap`).
백엔드가 살아 있고 Redis만 죽었다 돌아오면 부팅이 없으므로, 그 넷이 닫은 것이
이 경로에서는 하나도 돌지 않는다.

### 재현 (2026-09-13 실측, 한 번)

개발 compose와 같은 Redis(`redis:7`, AOF 켬)에 빌드한 백엔드를 붙이고, 데모 시드
테이블 하나에 넷을 앉혀 `ws` 클라이언트로 판을 몬다.

| 시각 | 일 |
|---|---|
| 2.5s | 한 명이 콜 → 딥스택 차례, 마감 32.5s |
| 4.0s | `docker kill` Redis |
| 7.7s | 딥스택이 콜을 누른다 |
| 14.9s | 딥스택만 `error` 수신 (아래 T99) |
| 35.5s | Redis 기동 |
| 52.6s | **딥스택 자동 폴드** |
| 이후 | 칩 총량 20,000 유지, 핸드 완주, 다음 핸드 시작, 티켓 발급 정상 |

**멀쩡했던 것**: 프로세스는 안 죽었고, 스냅샷·칩 총량이 보존됐다(`docker kill`에서
AOF). 소켓도 끊기지 않았다.

### T97 — Redis만 죽으면 차례였던 사람이 자동 폴드된다

**등급**: 치명 · **범위**: `backend/src/playsync` · `backend/src/recovery`

T94와 같은 결과가 다른 길로 난다. 장애 중에 누른 콜은 Redis 쓰기에 실패해
거절되고, 복구 뒤 BullMQ 타임아웃 잡이 돌아 **이미 지난 마감**으로 폴드한다.
T94의 무효화(세대 올림 · 마감 삭제)는 부팅에서만 돈다.

복구 17초 뒤에 발화한 이유는 확인하지 않았다(BullMQ 워커의 재시도 지연으로
추정).

**왜 못 잡나**: 복구 테스트가 전부 `recoverAll()`을 직접 부른다
(`src/scenario/syncing.int-spec.ts`). Redis만 죽이는 무대가 없다.

### T98 — Redis만 죽은 시간이 블라인드 시간으로 샌다

**등급**: 중간 · **범위**: `backend/src/recovery`

`HeartbeatService`는 Redis ping이 실패하면 하트비트를 안 찍는다. 주석이 이유를
적어 뒀다 — 「서버는 살아 있고 Redis만 죽은 구간을 잡으려고, 조건 하나가 케이스
하나를 닫는다」. 실제로 두 번 건너뛰었다.

**그런데 그 공백을 읽는 자리가 다음 부팅뿐이다.** Redis가 먼저 돌아오면 다음
하트비트가 공백을 덮는다. 실측 뒤 대회는 `ONGOING` · `pausedMs=0`이었다 — 30초가
그대로 게임 시간이다. 주석이 닫았다고 한 케이스는 **백엔드가 장애 중에 같이
죽을 때만** 닫힌다.

### T99 — Redis가 죽어도 아무 화면도 모른다

**등급**: 중간 · **범위**: `backend/src/ws` · `frontend/src/app/(terminal)`

- 누른 사람만 7.2초 뒤에 ioredis 원문을 받는다 —
  `Reached the max retries per request limit (which is 20)…`. 인프라 언어가 좌석
  태블릿으로 나간다.
- 딜러와 나머지 좌석에는 아무것도 안 뜬다. `keepalive`는 메모리 타이머라 계속
  온다.
- 장애 중 REST(`POST /ws/ticket`, `GET /tournaments/:id`)는 약 5초 뒤 500이다.

## 잔여 목록

| 자리 | 무엇 | 상태 |
|---|---|---|
| 실제 kill 무대 | 백엔드 프로세스·Redis를 **진짜로** 죽이는 자동 검사가 없다. 부팅 배선(`onApplicationBootstrap` → `recoverAll`)과 진짜 마지막 하트비트는 어느 테스트도 안 지난다 | 대기 |
| Redis 장애의 다른 모양 | 한 번, `docker kill` 30초만 봤다. 볼륨 유실과 **7초보다 짧은 장애**(ioredis가 명령을 들고 있다 뒤늦게 실행할 수 있는 구간)는 안 봤다 | 대기 (측정) |
| `WsGateway.sweepSockets`의 틱 비용 | 10초마다 모든 소켓에 `ping()`과 `keepalive`를 동기로 보낸다. 12,000명이면 틱마다 쓰기 약 2.4만 번이라 `my_action_server_ms`에 10초 주기 스파이크로 보일 수 있다. 다음 램프에서 본다 | 대기 (측정) |
| `WsGateway.recount`의 k 표시 | `broadcast`가 OPEN이 아닌 소켓을 방에서 먼저 지우면 뒤이은 `handleDisconnect`의 재집계가 안 돈다. n/n 판정은 OPEN 딜러만 세어 안전하고, 「k/n 복귀」 표시만 다음 이벤트까지 높게 남는다 | 감수 (T96) |
