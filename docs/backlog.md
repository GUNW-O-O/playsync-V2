# Playsync V2 백로그 — 방향과 안 하기로 한 것

> MVP(1단계, T1~T21 — [`archive/tickets.md`](./archive/tickets.md))를 닫은 뒤 정한
> **방향**(B1~B11)이다. 방향은 전부 닫혔다 — 했거나, 안 하기로 했다. 이 문서의
> 값은 **안 하기로 한 것의 근거**다.
>
> 이미 깨져 있는 것은 결함 대장([`tickets-audit.md`](./tickets-audit.md) ·
> [`tickets-recovery.md`](./tickets-recovery.md))에, 지금 코드의 규칙은
> [`domain.md`](./domain.md)에, 무엇을 왜 했는지는 PR 본문과 커밋에 있다.

## 방향

순서를 정한 기준은 **커플링 → 의존성 → 심각도**, 그리고 **프론트를 막는 것 먼저**였다.

| # | 항목 | 결과 |
|---|---|---|
| B1 | 인증 정책 | 딜러 OTP 강화(T23) · WS 1회용 티켓(T24) · 테이블 생성을 상점 수동으로(T25). **딜러 단말 신원(T26)은 안 한다** |
| B2 | 서버 장애 복구 | 재구성 · 정지 시간 보정(T31), 그 뒤 복구 결함 대장(T93~T109) |
| B3 | 레이크와 상점 정산 | 걷은 총액에서 한 번 뗀다(T80) |
| B4 | ICM 찹 정산 | 파이널 테이블에서 칩 비율로 나누고 닫는다(T82) |
| B5 | 프론트 기능 명세 | 면 다섯 · 화면 열하나(와이어프레임). **`(admin)` 면은 안 그린다** |
| B6 | 백엔드 API 재구성 | **독립 티켓으로 세우지 않았다** — B7에서 걸리는 것을 그때 고쳤다(T32 · T56) |
| B7 | 프론트 재구성 | T34 |
| B8 | 테이블 간 인원 이동 | 상점이 해제하고 사람이 옮긴다(T27~T29). 자동 밸런싱을 안 하는 근거는 `domain.md`의 「없는 것은 누락이 아니다」 |
| B9 | WS 수평 확장 | **안 한다** |
| B10 | 감사 로그 | **안 한다** |

금지(T77), 시작한 대회의 중단(T79).

## 안 하기로 한 것

공통점은 하나다 — **규칙이 아니라 사람의 결정인 것은 코드가 정할 수 없다.**
운영에 올리기로 하면 이 절을 다시 연다.

### 딜러 단말 신원 (T26)

딜러 토큰의 `sub`가 대회 단위 `DealerSession.id`라 한 대회의 딜러 셋이 구분되지
않는다(위협 모델 관찰 6·7). 사실이지만 **닫아서 얻는 것 둘이 비어 있다.**

- **단말 단위 내보내기를 쓸 자리가 없다.** 대회가 끝나면 `completeSession`이
  `Table`·`DealerSession`·스냅샷을 지워 살아 있는 토큰으로 할 수 있는 조작이 없다.
  딜러 태블릿은 직원이 관리하는 기기라 악의적 조작은 신뢰 경계 밖이다. 남는 경우는
  OTP 유출 의심뿐인데, 그때 원하는 조작은 **전원 끊고 재발급**이고 지금의 대회
  단위 동작이 정확히 그것이다.
- **감사 로그는 적을 곳이 없다**(아래 「감사 로그와 어드민」). T26은 감사 로그에
  선행하는 것이 아니라 그것에 의존한다.

### WS 수평 확장 (B9)

게이트웨이가 세션을 인메모리 Map으로 든다. 서버를 늘리면 브로드캐스트가 갈라지지만
**한 행사장 한 프로세스가 단위**이고, 1코어가 12,420명을 들었다. 대회를 여럿 여는
것은 지금도 된다(Map이 `tournamentId` 키).

**착수하면 Redis 장애 가드(T97)도 다시 짠다.** 장애 상태가 프로세스 메모리
(`RedisService.outage`)에 있어, 인스턴스가 여럿이면 A가 복구하는 동안 B가 폴드시킬
수 있다. 옮길 모양은 [T97 스펙](./superpowers/specs/2026-09-13-t97-redis-outage-design.md)의
「인스턴스가 여럿이 되면」.

### 감사 로그와 어드민 (B10 · B5)

MVP의 기준선은 **장부가 맞고 대회가 닫히는 것**이지 누가 무엇을 눌렀나가 아니다.
이 시스템에서는 그 경계가 도메인에서 나온다 — **분쟁의 1차 근거는 시스템이 아니라
테이블 위다.** 카드는 실물이고 현장에 직원이 있다. 「누가 눌렀나」를 시스템이
붙들어야 하는 상황이면 이미 현장 통제가 무너진 뒤다.

어드민(`(admin)` 면 · 가맹점 온보딩)은 도메인 서사(카드는 물리, 칩은 디지털)에
보태는 것이 없는데 화면 하나가 프론트 비용의 4분의 1이다. **SaaS 멀티테넌트
구조까지만 갖는다** — 상점 계정은 시드가 만든다. 그래서 초기 비밀번호 · 초대
링크 같은 온보딩 정책도 없고, 어드민이 전체 상점을 보는 경로(`GET /store`)도
소유자 기준 그대로다.

코드에 남은 `PLATFORM_ADMIN`(`@Roles` · 프록시의 `/stores`)은 소유자가 아니라 **모든
요청이 403**이다. 떼어 내면 가드와 검사 수십 줄이 함께 움직여 얻는 것이 없다.

### SIT_AND_GO · 실제 PG 결제 · 애드온 · 가맹점 문의

넷 중 어느 것도 지금 코드의 어떤 결정을 막고 있지 않다. 실 PG는 T72가 목업으로
경계를 만들어 뒀으므로 입구만 바꾸면 된다.

## 남은 것

결함이 아니라 **다듬을 자리**다. 결함은 대장의 잔여 목록에 있다.

| 무엇 | 왜 남겼나 |
|---|---|
| `payAnte`의 저수준 프리미티브 분리 | 앤티 뒤 `p.bet = 0` 보정이 **`initTable`이 `bet`을 0으로 맞춘다는 암묵 전제**에 기댄다. 칩 이동의 리팩터라 T58의 결함 수정과 한 브랜치에 섞지 않았다. 전제가 깨지면 `ante` 시나리오의 칩 총량 검사가 잡는다 |
| 트랜잭션 경계 관행이 둘이다 | `enterSeat`은 DB를 락 **밖**에서, `releaseSeats`는 락 **안**에서 커밋한다. 둘 다 주석에 근거가 있는데 서로 반대다(T42) |
| 스냅샷을 고치는 경로가 전부 락 안에서 읽는가 | 관행으로만 지켜진다. 하나라도 락 밖에서 읽은 값을 쓰면 조용한 유실 지점이다(T42) |
| 재기동 없는 좌석 해시 유실 | 부팅 복구가 안 도는 구간이라 스스로 낫지 않는다. 착석의 자가치유는 T48이 일부러 닫았다(지워진 테이블이 되살아난다). 재현 경로가 생기면 고친다 |
| `SEAT_LIST_UPDATED` 단위 검사 | `tournamentId`만 `objectContaining`으로 보고 페이로드 내용은 안 본다 |
| `createTable`의 두 왕복 | 소유권 확인과 생성이 `tournament.findUnique`를 각각 부른다. 다른 조작도 같은 모양이다 |
| e2e가 상태를 남긴다 | 사람을 앉히므로 반복 실행에는 시드가 앞에 붙는다. 파일 이름 순서가 실행 순서다 |
