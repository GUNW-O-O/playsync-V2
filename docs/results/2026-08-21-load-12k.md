# 12,000명 실측 — 정원을 깎고 있던 것은 인스턴스가 아니라 기본 힙 상한

2026-08-21. 질문은 하나였다. **가용 램에서 12,000명 가량을 명시 스펙(t4g.micro급
1 vCPU / 512MB)이 처리하는가.**

답은 **처리한다**. 다만 배포 설정 한 줄이 있어야 하고, 그 한 줄이 없으면 정원의
절반 가까이를 버린다.

## 기계

| | 값 |
|---|---|
| 호스트 | 32GB · 가용 18.7GB · 16코어 |
| Docker VM | 15.57GiB · 16 CPU |
| 백엔드 | `cpus: 1` · `mem_limit: 512m` (측정 구간). 착석에만 코어를 빌렸다 |
| k6 | `cpus: 10` |

[`2026-08-17-load-ceiling.md`](./2026-08-17-load-ceiling.md)를 잰 기계는 Docker VM이
3.785GB였다. **그 실측의 "600 VU 상한"은 이 기계에 적용되지 않는다** — 측정기 쪽
한계였고 여기서는 1,380 VU가 3.6GB로 들어갔다.

무대는 대회 230개 · 계정 풀 12,600개로 다시 세웠다(`LOAD_STORES` ·
`LOAD_ACCOUNT_POOL`). 램프 A(`LOAD_TABLES_PER_STORE=6`), 생각 시간은 라이브
기본값이고 **태우기는 쓰지 않았다** — VU를 다 띄울 수 있는 기계에서 태우기는
연산량을 억지로 만드는 대체 수단이라 여기서는 부하 모양을 왜곡한다.

## 실행 셋

| | 무대 | 도달 | 끝난 이유 |
|---|---|---|---|
| 1 | 계단 램프(200씩) · 중단 연속 2회 | 1,281테이블 · 11,529명 | 착석 몰림 스파이크로 **k6가 중단** |
| 2 | 단일 단계 · 증설 900초 · 중단 연속 6회 | 1,310테이블 · 11,790명 | **백엔드가 V8 힙 고갈로 abort** |
| 3 | 2와 같고 `--max-old-space-size=340` | **1,380테이블 · 12,420명 전원 착석** | 1코어 강등 뒤 내 액션 p95 1,061ms |

### 실행 1이 잰 것은 한계가 아니었다

```
ramp-a · 핸드 2087 · 내 액션 p95 48ms · lag 중앙 0.97ms 최대 144ms
       · CPU 362.6% · rss 381MB · 경고 0 붕괴 2
aborted: 서버 lag p95가 100ms를 2번 연속 넘었다 (grow-1294)
```

중단 태그가 `grow-1294`다 — **고원이 아니라 새 테이블을 밀어 넣는 순간**이다. lag
중앙이 0.97ms인데 최대 144ms 스파이크 두 표본이 연속 2회 조건을 채웠다. 내 액션
p95는 48ms로 합격선(200ms)의 1/4이었다.

**중단 조건을 지속 조건으로 바꿨다**(`LOAD_BREACH_STREAK=6`, 30초). 선(100ms)은
그대로다. 무르게 만든 것이 아니라, 몰림 스파이크에서 멈춘 가짜 한계를 답으로
적지 않기 위해서다.

### 실행 2 — 죽인 것은 컨테이너가 아니라 V8

```
State=exited  OOMKilled=false  ExitCode=134
FATAL ERROR: Ineffective mark-compacts near heap limit
             JavaScript heap out of memory
```

마지막 정상 표본은 1,310테이블 · **rss 398MB**였다. **컨테이너 512MB에 114MB가
남아 있는데 죽었다.** `OOMKilled=false`가 그 증거다 — 커널이 죽인 것이 아니라 V8이
자기 힙 상한에 부딪혀 스스로 abort했다.

컨테이너 안에서 잰 값:

```
heap_size_limit   259MB      ← 노드가 cgroup 512MB를 보고 자동 설정
NODE_OPTIONS      (없음)
```

## 고친 것 — 한 줄

```yaml
NODE_OPTIONS: --max-old-space-size=340   # 259 → 343MB
```

인스턴스 크기(512MB)도 CPU 스펙도 바꾸지 않았다. `rss = 힙 + 소켓·버퍼`이고 실측
외부 사용량이 약 140MB라, 상한을 컨테이너 한도까지 올리면 이번에는 커널이 죽인다.
그래서 340이다.

**결과: 11,790 → 12,420명.** 같은 돈에서 정원이 늘었다.

## 1코어 강등 — 12,420명을 물린 채

고원에서 코어만 떨궜다. 소켓은 끊기지 않는다(`docker update`는 재시작이 없다).

| CPU | lag p95 (바닥 10ms 제외) | rss | 힙 |
|---|---|---|---|
| 12코어 | 0.92ms | 433MB | 259MB |
| 4코어 | 1.30ms | 448MB | 283MB |
| 2코어 | 0.72ms | 447MB | 258MB |
| **1코어** | **0.72ms** | 451MB | 287MB |

**코어를 12분의 1로 줄여도 서버 지연이 변하지 않았다.** CPU 사용률은 27~56%.
라이브 속도(시간당 27핸드)에서 12,420명의 액션은 1코어의 절반으로 처리된다.

## 제일 무거운 것은 bcrypt다

이 구조에서 CPU를 먹는 것은 게임 진행이 아니라 **문 앞**이다.

| | 어디 | 이번 실행 |
|---|---|---|
| `hash` | `AuthService.createUser` (가입) | 12,600회 |
| `compare` | `AuthService.login` (로그인) | 14,092회 |

합쳐 **26,692회 × 58ms**(T41 실측 p50, `auth/throttle.ts`의 주석) = **1,548 CPU초**다.
착석 창이 900초였으므로, 완전 병렬이어도 그 창의 상당 부분이 bcrypt다.

**그리고 병렬도는 코어 수가 아니라 libuv 스레드풀이 정한다.** bcrypt는 JS 스레드가
아니라 스레드풀에서 돌고, `UV_THREADPOOL_SIZE`가 미설정이라 **기본 4**다.

이것이 관찰 둘을 한꺼번에 설명한다.

- **착석 구간 CPU가 250~370%에서 멈췄다.** 12코어를 줬는데도 3.7코어를 못 넘긴
  것은 서버가 한가해서가 아니라 **스레드풀이 4**라서다
- **고원에서는 1코어로 충분했다.** 게임 진행은 JS 스레드 하나가 하는 일이고,
  액션이 시간당 27핸드 속도로 흩어져 오면 그 스레드가 놀고 있다

즉 **정원의 축이 둘로 갈린다** — 문 앞(bcrypt, 스레드풀 병렬)과 게임 안(단일 JS
스레드, 브로드캐스트). 이번 실측에서 막은 것은 메모리였고, CPU 쪽으로 막힌다면
먼저 걸리는 것은 문 앞이다.

## 이 수치를 믿을 때의 단서 넷

- **리바인 0.** 22분에 핸드 4,177개(테이블당 3개)라 **아무도 파산하지 않았다.**
  탈락 · 사이드팟 · 리바인 갈래가 통째로 안 돌았다. 이 수치는 **소켓과 액션
  브로드캐스트의 정원**이지 대회 전 구간의 정원이 아니다
- **가입이 12,600건이다.** `NEW_USER_RATIO`가 10%라 약 1,240건이어야 하는데 좌석
  수(12,420)에 육박했다. 원인을 못 짚었다. **의도보다 무거운 조건에서 버틴 것**이라
  정원 수치 자체는 보수적이지만, bcrypt 비중을 위에서 계산한 근거가 이 값이므로
  그 비율은 다시 재야 한다
- **무응답창 75.** 죽은 소켓 하나가 지연 지표를 부풀리는 경로가 있다
  (`load/README.md`의 실측 기록). 내 액션 p95에 얼마나 섞였는지 갈라 보지 않았다
- **1코어에서 내 액션 p95가 1,061ms로 중단됐다.** 그런데 같은 시각 서버 lag은
  중앙 2.34ms · 최대 103ms이고 CPU는 51.6%였다. **서버가 포화된 것이 아니다.**
  자리비움 5,610 · 지각 3,657이 만드는 타임아웃 잡 몰림이거나 측정 경로 쪽이고,
  아직 갈라 보지 않았다

## 다음에 잴 것

1. **가입 12,600 이상 현상.** 봇이 의도보다 무겁게 돌고 있다는 뜻이고, 위의 bcrypt
   비중 계산이 그 값 위에 서 있다
2. **1코어의 체감 지연 1초.** 서버 lag이 멀쩡한데 왕복이 1초면 잡 큐나 측정 경로다
3. **`UV_THREADPOOL_SIZE`를 올리면 착석이 빨라지는가.** 위 설명이 맞다면 4 → 8이
   착석 창을 줄여야 한다. **아직 안 재봤다**
4. **탈락이 도는 실행.** 리바인 0인 채로 잰 정원은 갈래 하나가 비어 있다
