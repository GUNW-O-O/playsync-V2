# 부하 램프 실측 (2026-08-15)

T41이 돌린 성장 램프의 결과다. 설계는
[`../superpowers/specs/2026-08-15-load-ramp-design.md`](../superpowers/specs/2026-08-15-load-ramp-design.md),
판단의 기록은 [`../chat-log3.md`](../chat-log3.md)의 T41 절들에 있다.

**답하려 한 것 둘.** 동시접속을 어디까지 받나(고원 구간), 몰림을 어디까지
견디나(증설 구간).

## 결론부터

**서버가 한계에 닿지 않았다.** 램프 둘 다 66테이블 · 594명 · 소켓 660까지
중단 없이 갔고, 그 지점에서 내 액션 p95가 10~11ms · CPU 10% · rss 228MB였다.
여기서 멈춘 이유는 부하가 아니라 **계정 풀이 600이기 때문**이다.

즉 이 수치는 **정원이 아니라 하한**이다. 계정 풀을 9,000으로 늘려 이어서 재고
아래 "정원 추적"에 적었다 — **정상 운영 240테이블에 CPU 19.2%, 외삽 상한 약
1,200테이블. 그리고 벽은 동시접속이 아니라 도착이었다.**

**대회를 하나로 몰든 열하나로 나누든 같았다.** `SEAT_LIST_UPDATED`의 O(T²)를
예상했는데 이 규모에서는 측정 오차 안이다.

**대신 부하와 무관한 결함 둘이 나왔다.** 토큰 수명이 대회 길이를 못 버티고
(T43), 2천 번에 한 번 초 단위 지연이 난다(최대 9.8초, 원인 미확인). 정원보다
이쪽이 이 실행의 값진 산출물이다.

## 측정 환경

| | |
|---|---|
| 백엔드 | 컨테이너 `cpus: 1`, `mem_limit: 512m` (`backend/docker-compose.test.yml`) |
| DB · Redis | 제한 없음. 서버와 관리형 스토어를 나누는 구성이 맞아서다 |
| k6 | 제한 없음. 측정기가 피측정자를 굶기면 재는 것이 측정기가 된다 |
| 램프 | 6테이블에서 시작해 **6씩** 66까지. 증설 30초 + 고원 180초 × 11단계 = 38분 |
| `LOAD_TABLES_PER_STORE` | **미설정(램프 B)** / **6(램프 A)** |
| 생각 시간 | 기본 분포 (즉시 2초 85% · 오래 18초 15% · 자리비움 3% · 지각 2%) |
| 핸드 사이 딜링 | 25초 |
| 계정 풀 | 600. 66테이블(594명)이 상한이다 |
| 재접속 폭발 | 30테이블 고원 한가운데 |

**`LOAD_TABLES_PER_STORE`를 반드시 함께 읽는다.** 이 값이 "몇 상점"의 전제라
빼면 숫자가 혼자 돌아다닌다.

## 램프 B — 대회 하나 안에서 테이블을 늘린다

`SEAT_LIST_UPDATED`가 착석마다 그 대회의 모든 테이블 좌석 비트맵을 대회의 모든
소켓에 보내므로(`entry.service.ts:327`) 이론상 O(T²)다. 그 곡선이 실제로
꺾이는지를 보는 실행이다.

증설 목표와 같은 6의 배수 행**이다(그 사이 숫자는 증설 중에 스쳐 간 값이라
표본이 한 자릿수다).

| 18 | 162 | 180 | 12ms | 13ms | 538 |
| 24 | 216 | 240 | 10ms | 10ms | 643 |

| | 값 |

### 램프 A와 B가 사실상 같다

| | 램프 B (대회 1개) | 램프 A (대회 11개) |
|---|---|---|
| 66테이블 고원 p95 | 9ms | 10ms |
| 실행 전체 p95 | 11ms | 10ms |
| CPU | 9.6% | 10.7% |
| rss | 225MB | 228MB |
| 재접속 복구 p95 | 1206ms | 1167ms |

`SEAT_LIST_UPDATED`의 O(T²)를 예상해 램프 B가 더 나쁠 것으로 봤는데,
**이 규모에서는 차이가 측정 오차 안이다.** 대회 하나에 테이블 66개를 몰아도
브로드캐스트 비용이 사람이 느끼는 지연에 나타나지 않는다.

O(T²)가 틀렸다는 뜻은 아니다. 계산상 테이블 66개의 좌석 목록이 수백 KB고,
그것이 대회의 모든 소켓에 착석마다 나간다. **CPU가 10%라 그 비용을 낼 여유가
아직 많다는 뜻**이고, 곡선이 꺾이는 지점은 계정 풀을 늘려야 보인다.

## 어느 선이 먼저 왔나

**둘 다 안 왔다.** 사용자 불편선(내 액션 p95 1초)도 서버 붕괴선(lag p95 100ms)도
66테이블까지 한 번도 닿지 않았다. 경고선(20ms)조차 0회다.

첫 실행은 23테이블에서 불편선에 걸려 멈췄는데, **그것은 제품이 아니라 측정이
깨진 것이었다** — 같은 시각 서버는 lag 0.4ms · CPU 1.8%였다. 원인과 수정은
`chat-log3.md`의 T41 절들에 있다.

## 꼬리 — 드물게 초 단위가 난다

p95만 보면 안 보이는 것이 있다. 원시 시계열에서 **내 액션 표본을 전부 세어**
합격선과 불편선을 넘은 횟수를 직접 셌다.

| | 표본 | > 200ms | > 1초 | > 3초 | 최대 |
|---|---|---|---|---|---|
| 램프 B | 12,386 | 6 (0.05%) | 5 (0.04%) | 0 | 2.2초 |
| 램프 A | 12,460 | 7 (0.06%) | 6 (0.05%) | **1** | **9.8초** |

**2천 번에 한 번꼴로 사람이 "이거 왜 이래"라고 말할 지연이 난다.** 램프 A에서는
한 번이 9.8초였다 — 그건 "안 먹었나" 하고 다시 누르는 크기다.

**부하 때문이 아니다.** 난 시각을 보면 테이블 수와 무관하게 흩어져 있다.

```
램프 B  steady-12  steady-18  steady-48  steady-48  steady-54  steady-66
램프 A  grow-26    steady-30  steady-40  steady-48  steady-54(9.8초)  steady-54  steady-66
```

12테이블에서 나는 일이 66테이블에서 더 자주 나지 않는다. 즉 정원의 문제가
아니라 **경로 어딘가가 가끔 초 단위로 막힌다**는 뜻이고, 그건 부하를 키워서
찾을 것이 아니다.

가장 그럴듯한 후보는 **타임아웃 잡과의 락 경합**이다. 이 실행에서 자리비움이
400건, 지각이 253건인데, `TIME_OUT` 잡은 BullMQ에서 독립적으로 깨어나 테이블
락을 잡는다. 액션이 그 뒤에 줄을 서면 `withTableLock`의 재시도(5초)만큼
기다린다. 다만 9.8초는 그 한도를 넘으므로 이것만으로는 설명되지 않는다.
**추정이고, 확인하지 않았다.**

`grow-N` 라벨의 수치는 표본이 0~3개라 백분위로 읽지 않는다 — 증설 구간이
짧아서 그 사이에 액션이 몇 건 안 잡힌다. 위 표가 그 자리를 대신한다.

## 램프가 드러낸 것

| | |
|---|---|
| **토큰 수명이 대회 길이를 못 버틴다** | JWT가 전역 1시간이라 좌석 태블릿이 한 시간 뒤 스스로 재접속하지 못한다. **T43으로 뺐다** — 부하가 기능 테스트로는 안 보이는 것을 잡은 자리다 |
| 죽은 소켓 하나가 지연 지표를 부풀린다 | 하네스 결함. 창 큐가 죽은 소켓을 기다리다 지연이 무한히 커졌다 |
| WS 티켓 30초 만료 | 열 개를 미리 받아 두면 마지막이 만료된다. 소켓 여는 자리에서 받도록 고쳤다 |
| `BlindStructure.name`이 전역 유니크 | 상점 범위가 아니다. 시드가 상점을 여럿 세우며 드러났다 |
| 테이블 생성 409 | 이 두 램프에서는 **0회**. 예상했던 경합이 66테이블에서는 나지 않았다 — 아래 정원 추적에서 포화 상태(328테이블)에 이르자 **131회** 났다 |
| **2천 번에 한 번의 초 단위 지연** | 부하와 무관하게 흩어져 난다. 최대 9.8초. 원인 미확인 |
| 레이스 컨디션(T42) | 램프가 그 창을 열지 못했다. T42를 앞으로 당길 근거가 생기지 않았다 |

# 정원 추적 (같은 날 이어서)

위 두 램프가 계정 풀 600에서 끊겨 "정원이 아니라 하한"만 남겼다. 풀을 9,000으로
늘리고 세 번 더 돌려 상한을 잡았다.

## 결론 — 벽은 동시접속이 아니라 도착이다

**정상 운영은 240테이블(2,160명 · 소켓 2,400)에서 코어의 5분의 1만 쓴다.**
그런데 그 240테이블을 **세우는 동안**에는 코어가 꽉 찬다. 두 숫자가 열 배 넘게
차이 나고, 무너지는 것은 언제나 뒤쪽이다.

| | CPU | lag p95 | 내 액션 p95 |
|---|---|---|---|
| 240테이블 정상 운영 | **19.2%** | 0.9ms | **31ms** |
| 240테이블 도착 중(초당 5명) | 72.7% | 2.4ms | 65ms |

## 세 실행

`LOAD_STORES=170` · `LOAD_ACCOUNT_POOL=9000` · `LOAD_TABLES_PER_STORE=6`
(대회당 6테이블이라 `SEAT_LIST_UPDATED` 팬아웃이 묶인다 — 순수 정원을 재려고
램프 A 쪽을 골랐다).

### 1. 터뜨리기 — 66→990테이블, 132씩 30초

**328테이블에서 중단.** 사용자 불편선(내 액션 p95 1초, 연속 2회).

| | 값 |
|---|---|
| 서버 lag | 중앙 79ms · 최대 102ms (**붕괴선 1회**) · 경고 38회 |
| CPU · rss | 100% · 211MB |
| 테이블 세우기 | 중앙 **41초** (여유 시 1초) |
| 테이블 생성 409 | **131회** (앞선 램프에서는 0) |
| 소켓 오류 | 3 |

**결제와 테이블 추가가 500을 냈다.** 정체는 Prisma 대화형 트랜잭션 만료다.

```
Unable to start a transaction in the given time.
A query cannot be executed on an expired transaction.
  timeout was 5000 ms, however 6701 ms passed since the start
```

결제 트랜잭션 안에는 DB 쓰기 셋뿐이고 bcrypt가 없다. **트랜잭션이 느린 것이
아니라 이벤트 루프가 굶어서** 5초 안에 재개되지 못했다. 장부가 깨지지는
않는다(Prisma가 롤백한다) — 손님이 결제 도중 500을 본다.

### 2. 도착률 낮추기 — 66씩 60초 (초당 약 10명)

330테이블 증설 중 같은 선에서 중단. **회복 창이 있으면 264까지 간다.**

| 테이블 | 사람 | 고원 CPU | 고원 lag | 고원 내 액션 p95 |
|---|---|---|---|---|
| 66 | 594 | 10.5% | 4.8ms | 13ms |
| 132 | 1,188 | 12.6% | 4.7ms | 18ms |
| **198** | 1,782 | 21.0% | 5.8ms | **98ms** — 합격선 안 |
| 264 | 2,376 | 49.8% | 35.4ms | **606ms** — 경고선 초과 |
| 330 | 2,970 | — | 137ms | **1541ms** — 중단 |

**고원 CPU에 도착 잔업이 섞여 있다.** 한 단계가 594명 × 약 150ms ≈ 90 CPU초를
요구하는데 고원이 90초뿐이라, 264테이블에서는 고원의 대부분이 밀린 착석을
배수하는 데 쓰인다. 49.8%는 게임 비용이 아니다.

같은 도착률을 **끊지 않고** 4분 이어 붙이면(240테이블을 432초가 아니라 240초에)
264를 못 넘기고 죽는다. 즉 도착은 **순간 속도가 아니라 지속률**이 문제다.

### 3. 정상 운영만 재기 — 240테이블, 도착 초당 5명, 고원 5분

**완주했다.** 중단도 붕괴도 없다.

| | 도착 중 (432초) | **정상 운영 (300초)** |
|---|---|---|
| CPU 평균 | 72.7% | **19.2%** |
| lag 평균 | 2.4ms | **0.9ms** |
| 내 액션 p95 | 65ms | **31ms** |
| 표본 | 728 | **17,803** |

실행 전체: 핸드 373 · 소켓 오류 **0** · 테이블 409 **0** · 붕괴 **0** ·
경고 1 · rss 258MB · 로그인 2,160 / 가입 217.

**테이블 세우기가 중앙 1,133ms다.** 실행 1의 41초와 같은 일이고, 도착률만
다르다.

## 착석 한 명이 얼마짜리인가

여유 상태와 포화 상태의 REST 지연을 나란히 놓으면 비용이 보인다.

| 단계 | ≤66테이블 | 328테이블(포화) |
|---|---|---|
| `POST /auth/login` | **58ms** | 1,785ms |
| `POST /dealer/auth` | 63ms | 908ms |
| `POST /tournaments/payment` | 11ms | 1,601ms |
| `POST /tournaments/:id/enter` | 13ms | 2,209ms |
| `POST /store/sessions/:id/tables` | 9ms | **8,412ms** |
| `POST /ws/ticket` | 3ms | 82ms |

**58ms가 bcrypt 한 번이다**(cost 10). 딜러 인증도 같은 bcrypt다(T23).

착석 한 명의 직접 비용이 로그인 58 + 결제 11 + 착석 13 ≈ **82ms**인데, 실측
도착 능력은 초당 5~6명(CPU 73%)이다. 즉 실제 비용은 **150ms 쯤**이고 차액은
테이블마다 붙는 것들이다 — 딜러 인증 한 번, WS 티켓 열 번, 좌석 목록
브로드캐스트, 스냅샷 쓰기.

**병목은 로그인 bcrypt고, 착석 비용의 3분의 2다.**

## 그래서 맥스는

| 한계 | 외삽 | 근거 |
|---|---|---|
| CPU | 약 1,200테이블 | 240테이블에 19.2% → 테이블당 0.08% |
| 메모리 | 약 1,200테이블 | 258MB, 기저 195MB → 테이블당 0.26MB |

**둘이 같은 지점에서 만난다 — 약 1,200테이블 = 10,800명 = 소켓 12,000**
(1코어 512MB).

**단 조건이 붙는다. 도착을 초당 5~6명으로 흘려보낼 때만이다.**

| 도착 지속률 | 결과 |
|---|---|
| 초당 5명 | 편안 (CPU 73%, 내 액션 65ms) |
| 초당 9~10명 | **4분 만에 불편선 초과** |
| 초당 40명(버스트) | 300테이블 부근 붕괴, 결제 500 |

2,160명을 채우는 데 7분이 걸렸다. 10,800명이면 **30분**이다. "1만 명을 받을 수
있나"의 답은 **받을 수 있다, 다만 문 앞에 줄을 세워야 한다**.

**외삽의 한계를 적어 둔다.** 19.2%에서 100%를 미는 것이라 지렛대가 길다.
240테이블까지는 실측이고 그 위는 계산이다. 그리고 이 계산은 **정상 운영만**의
것이라, 실제로 1,200테이블을 세우려면 도착에 세 시간이 걸린다.

## 늘리려면

| | 무엇 |
|---|---|
| 코어를 늘린다 | 도착 능력이 그대로 비례한다. 가장 단순하다 |
| bcrypt를 주 프로세스 밖으로 | 착석 비용의 3분의 2가 사라진다. 인증 서버를 가르거나 워커로 뺀다 |
| 도착을 분산시킨다 | 사전 체크인. **코드를 안 바꾸고 되는 유일한 방법**이고, 실제 대회 운영과도 맞다 |
| 트랜잭션 타임아웃 | 5초는 이벤트 루프가 굶으면 짧다. 늘리면 500이 줄지만 **원인이 아니라 증상을 가린다** |

## 남은 것

- **정원의 진짜 상한은 계산이다.** 240테이블까지가 실측이다. `LOAD_ACCOUNT_POOL`을
  더 늘리면 재량껏 올릴 수 있지만, k6 VU 하나가 소켓 열 개를 드므로 그 위는
  **측정기가 먼저 병목이 된다.**
- **결제 500(트랜잭션 만료)을 티켓으로 뺄지 정해야 한다.** 장부는 롤백으로
  지켜지지만 손님이 오류를 본다. 원인은 CPU 포화라 인증 비용을 줄이는 쪽과
  같은 티켓일 수 있다.
- **리바인이 세 실행 모두 0이다.** 실행이 짧아 스택 10만이 마르지 않는다.
- **리바인 경로가 램프 규모에서는 안 돌았다**(`rebuys_accepted` 0). 38분에
  테이블당 핸드가 네댓이라 스택 10만이 마르지 않는다. 경로 자체는 스모크에서
  확인했다(3분에 5회). 램프에서 보려면 시작 스택을 줄이거나 실행을 늘려야 한다.
- **초 단위 꼬리의 원인.** 2천 번에 한 번이고 부하와 무관하다. 타임아웃 잡의
  락 경합을 의심하지만 확인하지 않았다. **부하를 키워서 찾을 것이 아니므로**
  램프의 후속이 아니라 별도 조사다.
- **B9(WS 수평 확장)의 근거.** 1코어가 660소켓에서 CPU 10%면, 확장은 지금
  판단할 문제가 아니다.
