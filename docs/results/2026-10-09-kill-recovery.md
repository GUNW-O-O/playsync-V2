# 재기동 뒤 5분 — 무엇이 시간을 쓰나 (T119)

2026-10-09. [`2026-10-08-t117-sync-all-devices.md`](./2026-10-08-t117-sync-all-devices.md)에서
대회 하나 · 1,000테이블 kill의 `SYNCING` 해제가 약 6분 16초였다. 합격선은 5분이다.
어디가 시간을 쓰는지 가려서 고쳤다.

**667테이블(6,003명 · 기기 6,670대) `SYNCING` 해제: 407초 → 104초.** 1,000테이블은
이 기기에서 못 돌렸고, 실측에서 나온 값으로 계산만 했다(아래 「1,000테이블」).

## 무대

T116 · T117과 같다(1코어 · 512MB · bcrypt 4, 착석에만 6코어). 다른 것은 호스트다 —
Docker VM이 4GB라 667테이블까지만 돌렸다. 램프 B(대회 하나), 전원이 앉은 뒤 1코어로
내려 150초 판을 돌리고 `docker kill` → 8초 뒤 `docker start`. 실행은
`load/kill-run.sh`가 한다.

## 결과

같은 무대에서 하나씩 얹었다.

| 단계 | `SYNCING` 해제 | 그때 본 것 |
|---|---|---|
| 처음 | 407초 | 서버는 2분째부터 한가한데 마지막 100대가 3분에 걸쳐 온다 |
| 재접속 걸음 정책 | 198 · 201초 | 꼬리가 줄었다. 90% 복귀는 125초로 그대로 |
| 리스너 16개 | 95 · 104초 | 대기열 넘침 67,174 → 0. 버려지는 티켓이 없어졌다 |
| 세대 조회 묶기 | 111초 | pg 풀 대기 1,246 → 102. 접속 대기 11.2초 → 3.4초 |
| pg 풀 20 | 104초 | 접속 대기 3.4초 → 0.9초. 6,600대 복귀 50초 → 40초 |

끝난 뒤 참가자는 모든 실행에서 PLAYING 6,003명이다(탈락 0).

마지막 세 줄의 해제 시각이 비슷한 이유: 기기 6,668대는 kill 78초쯤에 다 돌아오고,
**마지막 한두 대가 다음 걸음(최대 60초)을 다 기다려** 해제를 정한다. 해제 시각은
이제 「서버가 뜨는 시각 + 최대 한 걸음」이다.

## 원인 셋

### 1. 실패할 때마다 폭을 두 배로 벌렸다

좌석의 첫 시도는 0~40초에 흩어지고, 실패하면 폭이 80 · 160 · 320초로 늘었다. 값의
근거는 660소켓이 요청 상한에 걸린 실측이었다 — 서버가 살아 있고 상한이 막는 경우다.

서버가 죽었다 뜨는 경우에는 맞지 않는다. 서버가 34초쯤 못 받으면 첫 시도의 약 85%가
실패하고, 그 기기들은 서버가 이미 떠 있는데 최대 80초를 더 기다린다. T117부터는 가장
늦은 한 대가 `SYNCING`을 풀므로 그 꼬리가 대회 전체의 대기가 됐다.

고친 것: 첫 시도의 지터가 기기마다 다른 출발 시각을 이미 줬으므로, 그 뒤는 5 → 10 →
20 → 40초 걸음(±50%)으로 간다. 폭을 다시 벌리지 않아도 무리는 흩어진 채다.

### 2. Node는 이벤트 루프 한 바퀴에 접속을 하나만 받는다

정책을 고친 뒤에도 90% 복귀가 125초로 같았다. 서버가 뜬 직후 25초 동안 티켓은 약
4,100장 나갔는데 접속은 약 200건뿐이었다.

| 증거 | 값 |
|---|---|
| 커널 `ListenOverflows` (부팅 45초 뒤 → 해제 때) | 33,095 → 67,174 |
| 봇의 소켓 오류: 연결 시간초과 | 2,839 |
| 봇의 소켓 오류: 연결 끊김 | 681 |

같은 이미지(Node 22 · libuv 1.51)에서 루프를 한 바퀴에 100ms씩 바쁘게 하고 접속
3,000개를 걸었더니 10초에 97개, **한 바퀴에 정확히 하나씩** 받았다. 받는 속도가
「1초 ÷ 한 바퀴 시간」이라, 루프가 바쁠수록 떨어진다(실측: 한 바퀴 13ms에 초당
약 75대, 36ms에 초당 7대).

티켓은 이미 열린 연결을 타고 초당 200장씩 나가는데 소켓은 기기마다 새 연결이라
초당 57대만 받는다. 나머지는 대기열에서 버려지고, 그 사이 티켓(수명 30초)이 낡는다.

**대기열을 넓히는 것은 답이 아니다.** 받는 속도는 그대로라 줄만 길어진다 — 초당
57대로 빠지는 줄에 4,096개가 서면 맨 뒤가 72초를 기다려, 태블릿의 침묵 감시(25초)와
티켓 수명(30초)을 넘긴다. 넣었다가 되돌렸다.

고친 것: 같은 포트에 `SO_REUSEPORT` 리스너를 여럿 둔다. 실험에서 리스너 8개는 한
바퀴에 8개, 32개는 32개를 받았다. 리눅스 기본 16.

### 3. 기기마다 같은 DB 조회를 세 번 한다

접속이 다 들어오자 CPU(91~101%)와 pg 풀(대기 1,246)이 한계가 됐다. 좌석 한 대는
좌석 토큰 세대를 티켓 발급 · 접속 · 등록 뒤 재확인에서 세 번 조회한다(T110).

부팅 뒤 110초의 CPU 프로파일:

| 몫 | 주체 |
|---|---|
| 19.4% | 가비지 컬렉션 |
| 17.7% | DB (Prisma + pg) |
| 6.5% | HTTP |
| 6.4% | Redis |
| 5.1% | 소켓 생존 확인(ping) |
| 4.8% | 소켓 프레임 쓰기 |
| 4.5% | 게이트웨이 방송 |
| 20.2% | 한가 (부팅 전후와 해제 뒤) |

고친 것: 앞의 조회가 도는 동안 들어온 조회를 다음 쿼리 하나(대회별 `IN`)로 묶는다
(`common/batched.ts`). 확인을 세 번 하는 구조는 그대로다. DB 19.5초 → 13.2초,
GC 21.4초 → 14.8초.

pg 풀은 10 → 20. 40은 재지 않았다 — 재접속은 CPU가 한계라 더 늘려도 얻을 것이 없다.

## 1,000테이블 — 계산

돌리지 못했다. 667테이블 실측에서 기기 한 대에 CPU 약 7.5ms(6,670대를 50초에, CPU
약 100%)가 나왔고 그 값으로 옮겼다.

| | 667테이블 (실측) | 1,000테이블 (계산) |
|---|---|---|
| 기기 수 | 6,670 | 10,000 |
| 전원을 받는 시간 | 40~50초 | 약 60~75초 |
| `SYNCING` 해제 | 104초 | 약 130~170초 |
| 접속 한 번의 대기 | 0.9초 | 약 2~3초 |

전제는 받는 속도가 유지된다는 것이다. 계산이지 측정이 아니다.

## 남은 것

- **해제 순간의 몰림.** `SYNCING`이 풀리면 전 테이블이 한꺼번에 움직여 pg 풀 대기가
  500대까지 차고 리바인 트랜잭션 300건쯤이 일시 실패한다. T118 덕에 탈락은 0이지만
  그 테이블은 딜러가 다시 재개해야 한다. 풀을 20으로 올려도 안 줄었다(243 → 306) —
  그 구간도 CPU가 꽉 찬다. 아래 「해제 순간의 몰림」에서 닫았다(T120).
- **회선만 끊겼다 붙는 경우의 지터 폭.** 서버가 살아 있으면 전원이 40초 안에 한 번에
  성공한다. 10,000대면 초당 250대인데 받는 속도는 초당 약 133대라, 계산상 맨 뒤가
  25초 감시를 넘는다. 667테이블은 괜찮다. 재지 않았다. T121.
- **GC 15초.** 스냅샷을 기기마다 두 번 읽어 파싱하는 것이 후보다. 접속 순서를 건드려야
  해서 안 했다.

## 해제 순간의 몰림 (T120)

`SYNCING` 동안에는 재개만이 아니라 승자 입력도 판 시작도 거절된다. 띠가 걷히면 그것들이
전 테이블에서 한꺼번에 풀린다. 실패의 문구는 전부 「Unable to start a transaction in the
given time」(P2028)이었다 — Prisma가 트랜잭션용 연결을 2초만 기다리고 던진다. 재시도
넷이 합쳐 약 9초인데 몰림은 10~15초다.

| | 고치기 전 | 봇의 재개만 흩음 | 연결 대기 5초 + 봇의 첫 동작을 흩음 | 연결 대기 5초, 봇은 동시에 |
|---|---|---|---|---|
| 리바인 끝내 실패(미룸) | 243 · 306 | 189 | 0 | **0** |
| 리바인 재시도 | 1,063 · 1,263 | 953 | 1 | 156 (전부 두 번째에 성공) |
| 체크포인트 시도 실패 | 41 · 50 | 82 | 0 | 56 (전부 두 번째에 성공) |
| 해제 뒤 풀 대기의 봉우리 | 526 · 556 | 513 | 252 | 433 |

- 재개만 5~15초에 흩어서는 안 줄었다. 쇼다운이던 테이블은 재개 없이 곧바로 승자를 넣고
  리바인을 묻기 때문이다.
- 마지막 열이 제품 수정만의 효과다. 봇이 전혀 흩어지지 않는 가장 나쁜 경우에도 끝내
  실패한 것이 없다.
- 끝난 뒤 참가자는 네 실행 모두 PLAYING 6,003명이다.

## 측정의 한계

- 봇에는 태블릿의 25초 침묵 감시가 없다. 줄에서 오래 기다린 소켓을 버리는 행동은
  부하로 안 보인다.
- 무대는 요청 상한을 100,000으로 올려 놓고 돈다. 짧아진 걸음이 제품의 상한(기기당
  분당 600)에 걸리는지는 재지 않았다. 걸렸을 때 `Retry-After`를 바닥으로 까는 경로는
  코드로 확인했다.
- 풀 20의 첫 실행은 착석 중 500 두 건으로 봇이 계정 7개를 새로 만들어 앉혀 무효였다
  (소켓 없는 자리가 생겨 6,670/6,677에서 멈췄다). 재실행에서는 안 났다.
