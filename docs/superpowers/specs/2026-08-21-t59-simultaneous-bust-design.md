# T59 — 동시 파산의 등수와 상금

> 2026-08-21. 결함 대장의 [T59 절](../../tickets-audit.md)이 무엇이 깨졌는지를
> 들고 있다. 여기는 **어떻게 고칠 것인가**만 적는다.

## 문제 둘

하나는 **한 배열 안**이다. `PlaysyncService.eliminatePlayer`가 여러 명을 받는데
등수와 금액을 루프 밖에서 한 번 계산해 전원에게 같은 값을 매긴다.

```ts
playerIds.map(userId => ({ userId, place: eliminatedRank, amount: prize }))
```

사이드팟이 갈리는 표준 핸드(숏스택 둘이 올인)면 흔한 배치다. 3위 상금이 두 번
나가고 2위는 아무도 못 받아 `걷은 참가비 == 나간 상금`이 영영 안 맞는다 —
**대회를 닫을 수 없다.**

다른 하나는 **테이블 사이**다. `eliminatePlayer`가 등수로 쓰는 `activePlayers`를
트랜잭션 안에서 읽지만 그 읽기에 행 잠금이 없다. 두 테이블이 동시에 정산하면
둘 다 감소 전 값을 읽어 같은 등수를 매긴다.

T60이 등수의 출처를 Redis 대시보드에서 DB로 옮겼지만 **성질은 같다.** 좌표만
`resolveWinners` 맨 앞에서 `eliminatePlayer` 트랜잭션의 `findUniqueOrThrow`로
옮겼다.

## 결정 — 핸드 시작 스택으로 가른다 (2026-08-21)

실제 홀덤이 같은 핸드에 파산한 둘을 가르는 기준이다. 많이 들고 시작한 쪽이
높은 등수다.

### 값은 이미 그 자리에 있다

대장의 「결정해야 하는 것」은 "핸드 시작 스택이라면 `resolveWinners`가 1단계에서
그 값을 들고 나와야 한다"고 적었다. **그 배선은 필요 없다.**

`eliminatePlayer`가 받는 `TablePlayer`에서 **`stack + totalContributed`가 곧 핸드
시작 스택**이다. 셋이 받쳐 준다.

1. **`totalContributed`가 살아 있다.** `resolveWinners` 3단계에서 스냅샷은 아직
   `HAND_END`이고, `TableEngine.resolveWinner`가 끝에 부르는 `resetStatus`는
   `hasFolded` · `hasChecked` · `isAllIn` 셋만 되돌린다.
2. **환불이 둘을 함께 움직인다.** `refundUncalledBets`가 `stack += refund`와
   `totalContributed -= refund`를 같이 하므로 합이 보존된다.
3. **파산자는 `stack <= 0`이다.** 그래서 실질적으로 `totalContributed`가 답이지만,
   식은 합으로 쓴다 — 리바인으로 살아난 사람이 섞여 들어오는 경우까지 같은 식이
   덮는다.

### 동점은 공동 등수이고, 억지로 재현하지 않는다

같은 스택으로 동시에 파산하는 경우가 남는다(둘 다 `startStack` 전액 올인).
**공동 등수로 두고 두 등수의 상금을 합쳐 나눈다** — 포커 표준이다.

실제로 도달하기는 거의 불가능하다는 판단이 섰다(2026-08-21). 등록이 열려 있는
동안의 탈락은 상금권 밖이라 `prizeFor`가 0을 주고, 상금이 걸린 등수까지 내려온
뒤에 스택이 정확히 같기는 어렵다. **그래서 이 경로를 위해 시나리오를 비틀지
않는다.** 규칙은 `eliminatePlayer`의 순수 계산 부분을 단위 테스트로 덮는 것으로
충분하다.

**나머지 한 단위는 좌석 인덱스가 작은 쪽이 흡수한다.** 합계가 풀과 정확히 같아야
`SessionService.completeSession`이 열리기 때문이고, 이는 `calculatePrizes`가 1위에
나머지를 몰아 주는 것과 같은 이유다(각자 내림하면 나머지가 사라진다 — T15의
사이드팟 증발과 같은 모양).

### 등록 마감 전 탈락자의 등수

**지금 동작을 바꾸지 않는다.** `eliminatePlayer`는 등록 개방 여부와 무관하게
`finalPlace`를 매기고, 그 등수는 상금권 밖이라 `prizeFor`가 0을 준다 — 기록만
남고 돈은 안 나간다. 이 티켓의 범위는 **등수가 겹치는 것**이지 등수를 매기는
조건이 아니다.

## 결정 — 등수 구간을 원자적으로 받는다 (2026-08-21)

교차 테이블은 스택 비교로 안 풀린다. 다른 테이블의 파산자는 이 배열에 없다.

**읽고 → 주고 → 깎는 순서를 뒤집는다.** `activePlayers`를 **먼저** 깎고 그
반환값으로 이번 배치가 가져갈 등수 구간을 잡는다.

```
before = after + n          (n = 이번 배치가 실제로 탈락시킨 인원)
이번 배치의 등수: after+1 … after+n
```

`UPDATE`가 행 잠금을 잡으므로 두 번째 트랜잭션은 첫 번째의 커밋을 기다렸다가
겹치지 않는 구간을 받는다. 한 대회 안의 짧은 트랜잭션이라 대기가 길지 않다.

이것이 루프 밖 계산과 **같은 자리에서 닫힌다** — 등수를 하나의 스칼라가 아니라
구간으로 다루는 순간, 배열 안에서 나눠 갖는 문제와 배열 사이에서 겹치는 문제가
한 식으로 표현된다.

## 바뀌는 모양

`eliminatePlayer`의 트랜잭션이 이렇게 된다.

1. `awardPrize`가 멱등이므로 **먼저 몇 명이 실제로 탈락하는지** 확정해야 한다.
   지금은 `awardPrize`가 그 판정과 지급을 함께 하는데, 지급 금액이 등수에
   달렸으므로 **판정을 앞으로 뺀다** — 대상 참가 행을 `status`로 걸러 세는
   문장이 하나 앞에 온다.
2. 그 수 `n`만큼 `activePlayers`를 깎고 `after`를 받는다.
3. 파산자를 **핸드 시작 스택 내림차순**으로 정렬한다. 큰 쪽이 `after+1`.
4. 같은 스택끼리 묶어 공동 등수로 만들고, 그 그룹이 차지한 등수들의 상금을
   합쳐 나눈다. 나머지는 좌석 인덱스가 작은 쪽.
5. `awardPrize`에 **각자 다른 `place`와 `amount`**를 넘긴다.

`awardPrize`의 시그니처(`{ userId, place, amount }[]`)는 이미 각자 다른 값을
받게 돼 있다. 호출부가 같은 값을 채워 넣고 있었을 뿐이다.

### 순수 함수로 뺀다

3~4단계는 트랜잭션도 Redis도 필요 없는 순수 계산이다. `prize.ts` 옆에 두고
단위 테스트로 덮는다.

```ts
/**
 * 동시 파산자에게 등수와 상금을 나눈다.
 *
 * @param busted 파산자. `handStartStack`은 `stack + totalContributed`다
 * @param lastPlace 이번 배치가 가져가는 **가장 낮은** 등수(`after + n`)
 */
export function splitBustedRanks(
  busted: { userId: string; seatIndex: number; handStartStack: number }[],
  lastPlace: number,
  pool: number,
  payouts: unknown,
): { userId: string; place: number; amount: number }[]
```

## 테스트

| 무엇 | 어디 | 왜 |
|---|---|---|
| 스택이 다르면 등수가 갈린다 | 단위 (`prize.spec.ts` 계열) | 핵심 규칙 |
| 스택이 같으면 공동 등수이고 두 등수의 합을 나눈다 | 단위 | 억지 시나리오 없이 규칙만 |
| 나머지 한 단위가 사라지지 않는다 | 단위 | 합계 == 풀이 `completeSession`의 전제다 |
| 상금권 밖이면 0이다 | 단위 | `prizeFor`가 이미 하는 일이지만 그룹 분배가 그것을 깨지 않는지 |
| 한 테이블의 동시 파산 둘이 서로 다른 등수와 금액을 받는다 | 통합 (`prize.int-spec.ts`) | 지금 결함의 재현 |
| 두 테이블이 동시에 정산해도 등수가 겹치지 않는다 | 통합 (시나리오) | 교차 테이블. **일부러 동시에 띄운다** |
| 중복 도착이 상금을 두 번 주지 않는다 | 통합 | 기존 멱등성이 새 경로에서도 성립하는지 |

### 실패를 먼저 본다

지금 코드는 동시 파산 둘에게 **같은 등수와 같은 금액**을 준다. 그 값이 단언에
그대로 박혀야 빨간불이 진짜다.

교차 테이블 테스트는 **두 트랜잭션이 실제로 겹치게** 만들어야 한다. 순차로
부르면 지금 코드도 통과한다 — T29에서 물린 "둘이 어긋나는 입력"과 같은 함정이다.

## 하지 않는 것

- **등록 마감 전 탈락자의 등수를 없애는 것.** 위 절
- **`resolveWinners`가 핸드 시작 스택을 들고 나오게 하는 것.** 값이 이미 있다
- **동점 상황의 e2e·시나리오 재현.** 도달 가능성이 낮고, 억지로 만든 무대는
  규칙이 아니라 무대를 검사한다
