# T97 — Redis만 죽으면 차례였던 사람이 자동 폴드된다

**티켓**: `tickets-recovery.md`의 T97. 같은 설계로 **T98**(블라인드 시간이 샌다)과
**T99**(아무 화면도 모른다)를 함께 닫는다. **의존**: T94 · T95 · T96.

## 무엇이 깨졌나

T93~T96의 복구는 전부 **부팅**에서 시작한다(`RecoveryService.onApplicationBootstrap`).
백엔드는 살아 있고 Redis만 죽었다 돌아오면 부팅이 없어서, 그 넷이 닫은 것이 이
경로에서는 하나도 돌지 않는다. 2026-09-13 실측(`docker kill` → 30초 → `start`)은
이렇게 끝났다.

- 장애 중 차례였던 사람이 누른 콜은 7초 뒤 ioredis 원문 에러로 거절됐다
- 복구 17초 뒤 타임아웃 잡이 **이미 지난 마감**으로 그 사람을 폴드시켰다
- 대회는 `ONGOING` · `pausedMs=0` — 30초가 블라인드 시간으로 샜다
- 좌석·딜러·REST 화면 누구도 장애를 몰랐다

## 결정

**Redis 장애를 "짧은 부팅"으로 다룬다.** 서버가 자동으로 멈춰 세우고, 장애는 전원
화면에 뜨고, 판을 다시 여는 것은 딜러다(T95 그대로).

```
Redis 끊김 감지 ─ 메모리: 상태 down · 장애 세대 +1 · 감지 시각
               ├ 게이트웨이: 좌석·딜러 액션 즉시 거절, serverOutage{down:true} 방송
               └ DB: 진행 중 대회 → SYNCING, pausedAt = 감지 시각
Redis 복귀     ─ 상태 recovering
               ├ 대회마다: 블라인드 기준점 대입 + pausedAt (부팅 2단계)
               ├ 차례 있던 테이블: 락 안에서 멈춰 세우기 (세대+1 · 마감 삭제 · resumePending)
               ├ 상태 up → renderGame · serverOutage{down:false} 방송
               └ n/n 재집계 → completeSync가 블라인드를 한 번 민다
딜러           ─ 테이블마다 「이어서 진행」 → 30초 새 턴
```

### 기각한 것

| 안 | 왜 버렸나 |
|---|---|
| 장애와 겹친 시간만큼 턴을 연장한다 | 장애 동안 화면이 아무 말도 안 하다가 시간이 **갑자기 생긴다.** 20초 넘는 장애면 사람은 "왜 안 눌리지"만 겪다가 영문 모를 연장을 받는다 |
| 복구되면 서버가 자동 재개한다 | 장애는 전원이 알아야 하고, 판을 다시 여는 순간은 테이블을 보는 딜러가 정한다(T95와 같은 판단) |
| 턴 시계만 멈추고 블라인드는 따로 한다 | 테이블은 딜러 재개를 기다리며 멈췄는데 그 위로 블라인드가 오른다. 딜러가 늦게 누를수록 벌어진다 |
| Redis가 죽으면 프로세스를 내린다 | 소켓이 전부 끊겨 재접속(실측 30초대)을 겪고, Redis가 안 올라온 동안 부팅이 실패해 재시작 루프가 된다 |
| 감지 순간 BullMQ 워커를 로컬로 멈춘다 | 아래 가드가 이미 잡을 막고, 복구가 세대를 올린 뒤의 낡은 잡은 `isStaleEpoch`가 버린다. 같은 일을 하는 장치가 둘이 된다 |

### 인스턴스가 여럿이 되면 (B9)

**이 설계의 장애 상태와 가드는 프로세스 메모리에 있다.** 지금은 프로세스가 하나라
맞다(`backlog.md` B9). 여러 인스턴스가 되면 셋이 깨진다 — 감지가 인스턴스마다 다르고,
**A가 복구 중인 동안 B의 액션·타임아웃 워커가 폴드시킬 수 있고**, 복구가 여러 곳에서
돈다.

그때 옮길 모양은 정해 뒀다. **판정에 쓰는 사실을 공유 저장소로, 메모리에는 화면
알림만.**

1. 장애 기록 `{세대, 시작}`을 Redis에 Lua로 원자적으로 남긴다(다시 붙은 첫 인스턴스가)
2. 스냅샷에 「반영한 장애 세대」를 두고, `mutateSnapshot`을 지나는 모든 쓰기가 락 안에서
   비교해 뒤처졌으면 **먼저 멈춰 세우고 거절**한다 — 누가 먼저 만지든 결과가 같다
3. 복구 스윕은 화면을 빨리 띄우는 가속일 뿐, 정확성은 2가 진다

지금 하지 않는 이유: B9를 하지 않기로 했고, 반나절이 더 든다. **B9를 착수할 때 이
가드를 다시 짠다.**

## 1. 감지와 장애 세대

**`RedisService`가 자기 클라이언트(`REDIS_CLIENT`)의 이벤트로 상태를 든다.** 전이는
순수 함수로 뺀다(`redis/outage.ts`).

| 지금 | 입력 | 다음 | 부수효과 |
|---|---|---|---|
| up | `close` | down | 세대 +1, 감지 시각 기록, `redis.down` 발행 |
| down | `ready` | recovering | `redis.up` 발행 |
| recovering | 복구 끝 | up | `redis.recovered` 발행 |
| recovering | `close` | down | 세대 +1, **감지 시각은 첫 장애의 것을 유지** |
| (부팅 전) | 첫 `ready` | up | 없음 — 부팅 복구가 따로 돈다 |
| 아무 상태 | 종료 중의 `close`(`quit` · 모듈 종료) | 그대로 | 없음 — 안 거르면 종료할 때마다 대회가 `SYNCING`이 된다 |

**막는 자리는 둘이다.**

1. **게이트웨이** — up이 아니면 `PLAYER_ACTION` · `DEALER_ACTION`을 「서버 장애를
   복구하는 중입니다」로 즉시 거절한다. ioredis가 7초 재시도한 뒤 원문을 내보내던 자리다.
2. **`PlaysyncService.handleAction`의 락 안** — 들어올 때 잡은 세대가 락 안에서
   달라졌거나 up이 아니면 거절한다. 끊기기 전에 이미 나가 ioredis가 들고 있던 명령과,
   복구 직후 먼저 발화한 낡은 타임아웃 잡이 여기서 막힌다.

**감지의 한계.** Redis 프로세스가 죽는 경우(RST)는 `close`가 곧바로 뜬다. 망이 조용히
끊기는 경우는 TCP가 알아챌 때까지 늦다 — 잔여 목록에 남긴다.

## 2. 감지 순간 — DB만 쓴다

**Redis가 죽어도 DB는 산다.** 그래서 대회를 켜는 일은 복귀를 기다리지 않는다.

- 진행 중 대회를 `SYNCING`으로, `pausedAt`은 감지 시각. 이미 `SYNCING`이면 덮지 않는다
  (부팅 1단계와 같은 조건부 update). **DB만 읽는 화면(`/me`)이 장애 중에 곧바로
  「복구 중」을 띄운다.**
- 좌석·딜러 소켓 전원에게 `serverOutage { down: true }`.

DB 쓰기가 실패하면 로그만 남긴다 — 복귀 순간에 같은 조건부 update를 한 번 더 한다.

## 3. 복귀 순간 — 부팅과 같은 함수

`RecoveryService`가 `redis.up`을 받아 대회마다(대회 단위 격리, 부팅과 같다):

1. 대회 켜기 — 2에서 실패했을 수 있으므로 같은 조건부 update를 한 번 더
2. 블라인드 — DB에서 기준점을 **대입**하고 `pausedAt`을 싣는다(부팅 2단계 그대로)
3. 테이블 — 스냅샷이 있고 차례가 있으면(`planPause`) 멈춰 세운다.
   `resumePending.downMs` = 지금 − 감지 시각. **이미 `resumePending`이면 건너뛴다.**
4. 끝나면 상태 up, `redis.recovered` 발행
5. **게이트웨이가 그 이벤트를 받아** 멈춘 테이블 `renderGame`과 `serverOutage { down: false }`를
   방송하고, 대회마다 n/n을 다시 센다(`reportSync`). 소켓이 안 끊겼으면 곧바로 n/n이
   차고 `completeSync`가 블라인드를 `pausedAt`부터 지금까지 한 번 민다 — **T98이 닫힌다**

`RecoveryService`가 게이트웨이를 직접 부르지 않는 이유: 게이트웨이가 이미
`RecoveryService`에 의존한다(`completeSync`). 방향을 뒤집으면 순환이다. 이벤트는
`game.state.updated`와 같은 `EventEmitter2`다.

### 락

**멈춰 세우기는 부팅과 런타임 모두 `mutateSnapshot`을 탄다.** 한 벌로 만든다. 부팅에는
경합 상대가 없어 락이 비용일 뿐이고, `saveSnapshotUnlocked('boot-recovery')`의
사용처가 하나 준다.

**스냅샷을 잃은 테이블의 재구성(`rebuildTable`)과 빈 테이블 스냅샷 세우기는 부팅
전용으로 남긴다.** 런타임에서 락 없이 돌면 착석과 경합한다. 런타임은 로그만 남긴다
(Redis 데이터 유실은 잔여 목록).

### 감수하는 창

`checkAndSyncBlindLevel`은 락 없이 읽고 통째로 쓴다(`domain.md` 동시성 규약 — 의도된
선택). 2단계와 전광판 폴링이 겹치면 Redis의 `pausedAt`이 지워질 수 있고, 그러면 n/n
전 몇 초 동안 레벨 계산이 풀린다. **보정량은 DB `pausedAt`으로 계산하므로
`completeSync`의 Δ는 틀리지 않는다.** 그 몇 초 안에 레벨 경계를 넘는 경우의 등록
마감만 틀어질 수 있다.

## 4. 계약과 화면

**계약** (`packages/contract`)

- `serverOutage` 이벤트 — `{ down: boolean }`. 소켓 화면용
- `SERVER_RECOVERING_STATUS = 503`. REST 화면용

**백엔드**

- 예외 필터 `RedisOutageFilter` — 상태가 up이 아닐 때 난 오류를 503 「서버 장애를
  복구하는 중입니다」로. `PrismaExceptionFilter`와 같은 `APP_FILTER`. **up일 때의
  오류는 건드리지 않는다** — 진짜 결함을 장애로 가리지 않는다
- 게이트웨이 — 복구 중(up이 아닐 때) 새로 붙은 소켓에는 붙는 즉시 `down: true`를 한 번.
  T96 「붙는 쪽이 매번 확인한다」와 같은 이유다(장애 중에는 티켓이 Redis라 못 붙는다)

**프론트** — 판정 `isServerRecovering(res)`과 문구를 `lib`에 한 벌. 화면마다 따로
적으면 그것이 드리프트다.

| 화면 | 장애 중 | 복구 뒤 (`SYNCING`) |
|---|---|---|
| 좌석 · 딜러 테이블 | `useTableSocket`이 `outage`를 돌려준다. 배너, 버튼 비활성, 턴 게이지 숨김 | T95 정지 배너 · T96 「k/n 복귀」 |
| 좌석 · 딜러 대기 (`WaitingClient` · `DealerWaitingClient`) | 503 → 장애 문구 | 기존 |
| 테이블 진입 SSR (`table/[tableId]` · `dealer/table/[tableId]`) | 503 → 장애 문구 | 기존 |
| 재접속 티켓 (`api/ws-ticket` → `reconnect-policy`) | 503은 재시도 대상 | — |
| 전광판 (`DisplayClient`) | 503 → 「서버 장애 복구 중」 | 「서버 복구 중」 + 멈춘 시계 |
| 참가자 `/me` | DB만 읽어 「복구 중」 라벨 | 같다 |
| 참가자 대회 상세 · 목록 | 503 → 장애 문구 (지금은 「대회를 찾을 수 없습니다」라는 틀린 말) | 「복구 중 ·」 |
| 상점 콘솔 | 503 → 장애 문구 | 「복구 중」 |

서버 액션(버튼)은 이미 `failureMessage`로 본문 문구를 띄운다 — 503 본문이 그대로 뜬다.

## 5. 테스트

**장애를 만드는 법.** 통합·시나리오는 실제 ioredis 클라이언트를 `disconnect()`로 끊고
`connect()`로 붙인다 — 이벤트를 흉내 내는 것이 아니라 명령이 실제로 실패하는 구간이
생기고, 그 길이를 테스트가 쥔다. 컨테이너를 죽이는 검사는 따로 둔다(아래).

| 계층 | 자리 | 무엇 | 반대 입력 |
|---|---|---|---|
| 단위 | `redis/outage.spec.ts` | 위 전이표 | 부팅 전 첫 `ready`는 복구를 안 부른다 |
| 시나리오 | `src/scenario/redis-outage.int-spec.ts` | 아래 단계, 단계마다 칩 총량 | 차례 없는 테이블엔 정지 표시가 안 붙는다 |
| 통합 | `ws.gateway.int-spec.ts` | down이면 액션 즉시 거절 · `serverOutage` 방송 · 복구 중 새 소켓 즉시 수신 | up이 되면 통과한다 |
| 단위 | `RedisOutageFilter` | down 중 오류 → 503 | **up일 때 오류는 500 그대로** |
| 계약 | `server-outage.spec.ts` | 모양 | — |
| 프론트 | `useTableSocket` · 좌석 · 딜러 · 대기 둘 · 전광판 · 대회 상세 · 콘솔 · `reconnect-policy` | 장애 표시 · 비활성 · 503 문구 | 404·500은 기존 문구, `down:false`면 배너가 사라진다 |

**시나리오 단계**

1. 판이 돈다. A 차례, 마감을 과거로 돌려 둔다
2. 끊는다 → `SYNCING`, `pausedAt` ≈ 감지 시각
3. 붙인다. **복구 스윕을 스파이로 붙잡아 둔 채** A의 `TIME_OUT`을 흘린다 → 폴드 없음.
   **지금 코드에서 빨개지는 단계다.** 순서는 타이밍이 아니라 조회를 조종해 강제한다
4. 스윕을 놓는다 → `resumePending`, 세대+1, 마감 없음. 낡은 세대 `TIME_OUT`은 no-op
5. n/n → `ONGOING`, `pausedMs` Δ ≈ 장애 시간
6. 복구 중 한 번 더 끊는다 → `pausedAt` 유지, 보정 한 번
7. 딜러 재개 → A의 액션이 들어간다

**실패를 먼저 본다.** 스윕 호출을 빼면 3이, 게이트웨이 가드를 빼면 통합이 빨개지는지
확인한다.

### 실제 kill 검사 (`npm run test:outage`)

**사람이 돌린다** — e2e · 촬영과 같은 계층, CI 밖. 잔여 목록의 「실제 kill 무대 없음」을
닫는다.

- **별도 컨테이너**를 띄운다. 개발 DB를 지우지 않으려는 것이고(통합 테스트가 5433/6380을
  따로 쓰는 것과 같은 이유), Redis 영속 설정은 **개발 compose와 같게**(AOF) 둔다 —
  테스트용 Redis는 영속을 꺼 둬서 재시작이 곧 유실이 되어 다른 장애를 재게 된다
- 빌드한 백엔드를 자식 프로세스로 띄우고, 데모 시드 테이블 하나에 좌석 넷 + 딜러를
  `ws`로 붙여 판을 돈다
- 차례가 있는 순간 `docker kill` → 30초 → `docker start`
- 단언: **차례였던 사람이 폴드되지 않는다** · 좌석·딜러가 `serverOutage` down/up을 받는다 ·
  장애 중 액션이 즉시(1초 안) 한국어 문구로 거절된다 · 대회가 장애 중 `SYNCING` ·
  복구 뒤 `resumePending` · 딜러 재개 뒤 핸드 완주 · 칩 총량 불변 · `pausedMs` ≈ 30초

## 범위 밖

- **망이 조용히 끊기는 장애**(RST 없음). 감지가 TCP 타임아웃만큼 늦다. Redis 하트비트
  공백 판정이 필요하다
- **Redis 데이터 유실**(볼륨 없음 · AOF 손상) 뒤의 런타임 재구성. 부팅 전용으로 남긴다
- **7초보다 짧은 장애**에서 ioredis 오프라인 큐가 명령을 뒤늦게 실행하는 경로 — 2의
  세대 가드가 턴 쓰기는 막는다. 턴 밖의 쓰기(착석 · 결제)는 보지 않았다
