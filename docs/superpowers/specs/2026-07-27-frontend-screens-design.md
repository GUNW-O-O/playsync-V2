# 프론트엔드 화면 목록

**항목**: backlog B5(프론트 기능 명세)의 선행 산출물
**상태**: 확정. 개별 화면의 상세 명세는 여기서 파생한다

이 문서는 "무엇을 그릴 것인가"의 전체 목록이다. 어떻게 생겼는지(레이아웃,
컴포넌트)는 여기 없다. 그건 화면별 명세와 `DESIGN.md`가 맡는다.

---

## 목록의 단위

**라우트 하나 = 항목 하나.** 라우트가 없는 화면(모달, 팝업, 오버레이)은
소속 라우트의 **덮이는 것**으로 적는다.

"화면"과 "컴포넌트"를 가르는 기준은 하나다 — **사용자의 주의를 독점하면 화면.**
리바인 팝업은 다른 조작을 막으니 화면이다. 액션 슬라이더는 컴포넌트다.

항목마다 다섯 칸을 반드시 채운다. 빈칸을 남기지 않는다.

| 칸 | 빈칸이면 생기는 일 |
|---|---|
| 경로·면·역할 | 가드 설계가 누락된다 |
| 하는 일 | 화면이 존재할 이유가 없다 |
| 덮이는 것 | **라우트 없는 화면이 목록에서 사라진다** |
| 데이터 출처 | 그릴 때 응답 shape을 지어낸다 |
| 나가는 곳 | 흐름이 끊긴 화면이 남는다 |

데이터 출처가 없는 항목은 빈칸 대신 **미정**이라고 쓴다. 미정은 곧
"아직 그리면 안 되는 화면"이고, 그대로 B6(백엔드 API 재구성)의 입력이 된다.

## 면 구조

면을 가른 기준은 **기기와 가드가 같이 움직인다**는 것이다.

| 면 | 라우트 | 가드 | 기기 |
|---|---|---|---|
| 인증 | `/login`, `/register` | 공개 | 아무거나 |
| `(player)` | `/tournaments/*`, `/me` | 로그인만 | 참가자 폰 |
| `(console)` | `/stores/*` | `STORE_ADMIN`, `PLATFORM_ADMIN` | 상점 PC |
| `(terminal)` | `/table/*`, `/dealer/*` | 공개 — OTP·좌석 토큰 | 좌석 태블릿, 딜러 태블릿 |
| `(admin)` | `/admin/*` | `PLATFORM_ADMIN` | 플랫폼 PC |

`(terminal)`이 공개인 이유는 좌석 태블릿과 딜러가 **사용자 로그인을 하지
않기** 때문이다. OTP로 들어온다. 그래서 `(player)`와 합칠 수 없다.

## 참가 흐름

폰과 태블릿의 역할이 갈리는 지점을 먼저 고정한다.

```
[폰] 대회 검색 → 대회 상세 → 좌석 선택 → 참가비 결제 → 참가 OTP 수령
                                                            │
                                          (참가자가 실제로 그 자리에 앉는다)
                                                            │
[태블릿] 대기 화면 → 테이블 선택 → OTP 입력 → 게임 화면
                                                            │
                                    (물리 좌석과 어긋나면 딜러가 보정)
```

**폰의 역할은 OTP 수령에서 끝난다.** 그 뒤 조작은 전부 태블릿이다.

### 좌석을 언제 정하는가

참가 시점(폰)에 정한다. `POST /tournaments/payment`가 이미
`{tournamentId, tableId, seatIndex}`를 받고, `GET /tournaments/:id`가
`{ tournament, seatStatus }`로 Redis 좌석 비트맵을 함께 준다. **빈 자리만
보여주는 데 필요한 것이 전부 있다.**

대안이었던 "테이블만 고르고 좌석은 딜러가 지정"을 버린 이유는 딜러 부담이다.
어느 방식을 골라도 **물리 좌석과 시스템 좌석은 어긋날 수 있고 고치는 사람은
딜러다.** 딜러 보정 도구는 어차피 필요하다. 그러면 차이는 기본값의 정확도뿐인데,
딜러 지정 방식은 참가자 전원(테이블당 최대 9명)을 손으로 찍어야 한다.

`acquireSeatLock`이 좌석을 선점하므로 두 명이 같은 좌석을 고르면 409
`이미 다른 유저가 선택 중인 좌석입니다.`가 온다. **좌석 선택 화면에 경합 실패
처리가 필수다.**

### 태블릿 결합도

목표는 하나다 — **태블릿은 설정된 상태를 갖지 않고, 항상 같은 화면으로
되돌아온다.** 이게 서면 운영자가 대회마다 태블릿에 하는 작업이 0이 된다.

1. **영구 설정 0.** 기기가 아는 것은 URL 하나뿐이다. 그래서 진입점이
   `/table/[tableId]`가 아니라 **`/table?store=xxx`**다. URL에 대회나 테이블이
   박히면 그게 곧 기기별 설정이고, 대회마다 20대를 손으로 고쳐야 한다.
   상점은 바뀌지 않으므로 `store`만 박는다 — 관리 대상이 태블릿 N대가 아니라
   런처 설정 1개가 된다.
2. **세션이 기기가 아니라 사람에 붙는다.** 로컬 저장은 "지금 이 기기에 들어온
   참가 세션" 하나이고 대회가 끝나면 만료된다.
3. **이탈 복구가 사용자 조작으로 끝난다.** 태블릿이 죽거나 초기화돼도 참가자가
   OTP를 다시 넣어 복귀한다. 여분 기기를 갖다 놓는 것으로 고장 대응이 끝나고,
   딜러 개입은 좌석 어긋남에만 남는다.

**원칙 3이 OTP 설계를 강제한다.** 1회용이면 재입력이 안 돼 원칙이 깨진다.
재사용 가능해야 하고, 그러면 유출 시 남이 그 자리로 들어올 수 있다.

해결: OTP 통과 시 태블릿이 **좌석 토큰**을 받고, 같은 좌석에 새 입장이 오면
**이전 연결을 끊는다(마지막 연결 우선).** 유출 피해가 "몰래 훔쳐본다"에서
"내가 튕긴다"로 바뀐다. 튕기면 즉시 알아채고 딜러에게 말할 수 있다 —
오프라인이라 이 방어가 실제로 작동한다.

**단, 인증 방식 자체는 B1이 정한다.** 지금 백엔드의 OTP는 딜러 OTP 하나뿐이고
(4자리, 시도 제한 없음), 참가 OTP를 추가하면 같은 구멍이 하나 더 생긴다.
이 문서는 흐름과 화면만 확정하고 인증 방식은 B1에 넘긴다.

### 프론트가 책임지지 않는 것

태블릿 관리 중 아래는 기기 설정이다. 프론트에서 풀 수 없고, 풀려고 하면 안 된다.

| 문제 | 어디서 푸나 |
|---|---|
| 참가자가 딴 앱으로 나감 | Android 화면 고정 / 키오스크 런처, iOS 안내식 접근 |
| 부팅 시 URL 자동 열기 | 런처 설정 |
| 배터리 | 좌석마다 충전 케이블 상시 연결 |
| 고장 | 여분 재고 |

프론트가 맡는 것은 Wake Lock(화면 꺼짐 방지), Fullscreen, WS 자동 재연결,
그리고 **세션 만료 시 대기 화면 자동 복귀**다.

### 인증 — 공개

| 경로 | 하는 일 | 덮이는 것 | 데이터 | 나가는 곳 |
|---|---|---|---|---|
| `/login` | 닉네임·비밀번호 로그인 | — | `POST /auth/login` | `next` 쿼리 또는 `/tournaments` |
| `/register` | 참가자 회원가입 | — | `POST /auth/join` | `/login` |

`/register`는 **참가자 전용**이다. 상점 운영자는 가입하지 않고 플랫폼에서
계정을 받는다(SaaS 온보딩, 아래 `(admin)` 참고).

### `(player)` — 참가자 폰, 로그인만 요구

| 경로 | 하는 일 | 덮이는 것 | 데이터 | 나가는 곳 |
|---|---|---|---|---|
| `/tournaments` | 가맹점 이름 검색 | — | `GET /tournaments/stores?id=` | 상점 대회 목록 |
| `/tournaments/stores/[storeId]` | 그 상점의 `PENDING`·`ONGOING` 대회 | — | `GET /tournaments/stores/:storeId` | 대회 상세 |
| `/tournaments/[id]` | 참가비·시작스택·상금분배·블라인드 확인 | — | `GET /tournaments/:id` | 좌석 선택 |
| `/tournaments/[id]/seat` | 빈 좌석 선택 후 참가비 결제 | **좌석 경합 실패**(409) | `seatStatus` 비트맵 / `POST /tournaments/payment` | 참가 완료 |

### `(terminal)` — 좌석 태블릿·딜러 태블릿, 공개

| 경로 | 하는 일 | 덮이는 것 | 데이터 | 나가는 곳 |
|---|---|---|---|---|
| `/table?store=xxx` | **대기 화면.** 진행 중 대회 → 테이블 번호. Wake Lock·Fullscreen 요청 | **참가 OTP 입력** | **미정 — 상점별 진행중 대회+테이블 목록 없음** | `/table/[tableId]` |
| `/table/[tableId]` | 액션 제출, 내 스택·팟·차례 확인 | **리바인 팝업**(`REBUY_PROMPT`), **연결 끊김**, **`dbSyncStatus` 표시** | `renderGame` WS | 탈락·종료 → **대기 화면 자동 복귀** |
| `/dealer?store=xxx` | 대회·테이블 선택 후 딜러 OTP | **딜러 OTP 입력** | `POST /dealer/auth` / **대회 목록 미정** | 딜러 콘솔 |
| `/dealer/table/[tableId]` | 핸드 시작, 폴드·킥, 승자 결정 | **승자 결정**(보드 하이), **좌석 보정**, **체크포인트 복구** | `renderGame` WS, 딜러 명령 5종 | — |

**승자 결정 화면의 "보드 하이" 버튼.** 누르면 폴드하지 않은 전원을 한 그룹으로
채워 보낸다. `winnerGroups: [["a","b","c"]]` 형태다. 서버에 별도 엔드포인트를
만들지 않는 이유는 **돈이 나가는 경로를 하나로 유지**하기 위해서다.

**체크포인트 복구.** `TableState.dbSyncStatus`가 `'FAILED'`가 되면 딜러 콘솔에
`RETRY_CHECKPOINT` 버튼이 뜬다. 이게 별도 이벤트가 아니라 스냅샷 필드인 것은
설계다 — 재접속한 단말도 같은 것을 봐야 하므로 기존 브로드캐스트 경로를 탄다.

**`/dealer/[id]` → `/dealer?store=xxx`.** 지금은 대회 id가 URL에 박혀 딜러
태블릿도 대회마다 URL을 바꿔야 한다. 좌석 태블릿과 같은 원칙을 적용한다.

**`/table/[tableId]`는 더 이상 진입점이 아니다.** 대기 화면에서 OTP를 통과한
뒤에만 도달한다.

### `(console)` — 상점 PC, `STORE_ADMIN`·`PLATFORM_ADMIN`

| 경로 | 하는 일 | 덮이는 것 | 데이터 | 나가는 곳 |
|---|---|---|---|---|

| `.../tournaments/[tournamentId]` | 시작·마무리, 딜러 OTP, 마감 상태 | **딜러 OTP 표시**, **마무리 확인**, **ICM 찹 지급(B4)** | `PATCH :id`, `:id/start`, `:id/complete` | 전광판 새 창 |

**`/stores`에 상점 생성이 없다.** SaaS이므로 상점은 플랫폼이 만든다.

**두 편집기를 화면급으로 올린 이유.** `prizePayouts[]`는 합이 100이어야 하고
`blindStructure`는 레벨 배열이다. 둘 다 행 추가·삭제·검증이 붙어 폼 필드
하나로 끝나지 않는다. 다만 별도 라우트로 빼지 않는다 — 생성 도중에만 쓰이고
단독으로 진입할 일이 없다.

**등록 마감 버튼은 없다.** 마감은 자동이다 — 블라인드 레벨이 `rebuyUntil`에
닿으면 `redis.service.ts`가 `isRegistrationOpen`을 `0`으로 내린다.
`UpdateTournamentDto`에 이 필드가 없어 수동 마감 경로 자체가 없다. 운영 화면은
**상태 표시만** 한다.

**전광판은 콘솔 라우트에 그대로 둔다.** 대회 상세에서 새 창으로 열고, 전체화면이
필요하면 F11을 쓴다. `backlog.md` B7 이월 항목의 "명세는 크롬 없는 전체화면을
요구한다"는 근거 없는 서술이었다 — **그 항목은 삭제한다.**

### `(admin)` — 플랫폼 PC, `PLATFORM_ADMIN`. 현재 화면 0개

MVP 범위다. 대시보드 통계, 가맹점 문의, 계정 정지는 넣지 않는다.

| 경로 | 하는 일 | 덮이는 것 | 데이터 | 나가는 곳 |
|---|---|---|---|---|
| `/admin` | 전체 가맹점 목록·검색 | **가맹점 생성**(상점 + 소유 계정 동시) | **미정 — `GET /store`는 소유자 기준** | 가맹점 상세 |
| `/admin/stores/[storeId]` | 상세, 정보 수정, 삭제 | 삭제 확인 | `GET /store/:id`, `PUT /store/:id`, `DELETE /store/:ownerId/:id` | — |

**"가맹점 생성"이 한 화면인 이유.** 상점과 소유 계정을 따로 만들면 계정 없는
상점과 상점 없는 상점 계정이 생긴다. 게다가 지금 `POST /store`는
`req.user.userId`를 소유자로 박으므로 **어드민이 만들면 어드민이 소유자가
된다** — SaaS에서는 틀린 동작이다. 화면을 하나로 묶어 "상점 + 소유 계정"을
한 트랜잭션으로 요구하고, 백엔드 변경은 B6에 넘긴다.

| `/admin` 목록 | 전체 상점 조회(소유자 무관) | B6 |
| 가맹점 생성 | 상점 + `STORE_ADMIN` 계정 동시 생성 | B6 |

## 이 문서가 만든 백엔드 과제

화면을 세는 과정에서 나왔다. 전부 B6 이후에 처리한다.

**보안 — `POST /auth/join`이 가입자 전원에게 `STORE_ADMIN`을 준다.**

```ts
// backend/src/auth/auth.service.ts:35
data: { nickname: dto.nickname, password: hashedPassword, role: Role.STORE_ADMIN },
```

누구나 회원가입만 하면 `/stores/*` 가드를 통과하고, `POST /store`로 상점을,
`POST /store/sessions`로 대회를 만들 수 있다. 프론트 미들웨어도 이 역할을 그대로
신뢰한다. SaaS 온보딩으로 가면 자연히 고쳐진다 — 가입은 `USER`만 만들고
`STORE_ADMIN`은 플랫폼이 발급한다. **B6 필수 항목.**

**`POST /store` 가드가 `STORE_ADMIN`을 허용한다.** SaaS라면 `PLATFORM_ADMIN`
전용이어야 한다.

**`GET /store`가 소유자 기준이다.** `getUserStores(req.user.userId)`라
어드민이 전체 상점을 보는 경로가 없다.

## 미결

코드가 정할 수 없는 것들. 착수 전에 판단이 필요하다.

- **상점 계정의 초기 비밀번호.** 어드민이 정해 전달하면 그 값이 어딘가에 평문으로
  남고, 상점이 잊었을 때 복구 경로가 없다. 첫 로그인 시 변경 강제(`/onboarding/password`)를
  넣을지, 초대 링크 방식으로 갈지 정해야 한다. MVP 범위에서 뺐지만 **깎은 것이
  아니라 정책이 없어서 미룬 것이다.**
- **대회 취소와 환불.** 참가자만 모이고 시작하지 않은 대회를 취소하면 상금이 0이라
  `completeSession` 게이트에 걸려 영영 닫히지 않는다. `TransactionType.REFUND`는
  스키마에만 있고 경로가 없다. 화면 자리는 대회 상세 위 모달이지만 백엔드와 정책이
  둘 다 없다.
- **가맹점 문의.** 모델도 엔드포인트도 없다. MVP에서 뺐다.
