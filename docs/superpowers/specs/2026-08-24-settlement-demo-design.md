# 정산 촬영 설계 — 무엇을 한 화면에 담나 (T84)

장면 1~5에는 이 문서가 있었다
([`2026-08-08-readme-demo-design.md`](./2026-08-08-readme-demo-design.md) §5).
장면마다 `화면 · 산출 · 보이는 정합 · 짝`을 표로 못 박아 두고, 그것이 마크
위치와 타일 배치를 정했다. **정산에는 그 문서가 없었다.**

그래서 `img/`의 `s6`~`s9`는 흐름대로 마크를 찍은 뒤 나중에 타일을 짐작한
것이고, 74초짜리 움짤에 5초짜리 주장이 들어갔다. 이 문서가 그 순서를
바로잡는다 — **무엇을 보여줄지 → 어떻게 붙일지 → 그 다음에 찍는다.**

여기서 정한 것이 **코드가 지킬 계약**이다. 마크 이름과 타일 배치가 어긋나면
자르는 쪽이 죽는다.

---

## 1. 이 촬영이 주장하는 것

셋만 화면으로 남긴다. 나머지는 시나리오 테스트에 맡긴다.

| 주장 | 어디서 보이나 | 짝 |
|---|---|---|
| **엔트리는 사람 수가 아니다** — 리바인 하나가 상금권을 5→6으로 | 프레임 ① | `itm-scaling.int-spec.ts` · T81 |
| **필드가 넷에서 하나로 줄어든다** — 자동이 아니라 사람이 걸어간다 | 프레임 ② | `table-move.int-spec.ts` · T27~T29 |
| **끝나는 길이 여럿인데 등식은 하나** | 프레임 ③ · abort | `icm-chop` · `rake` · `abort-settlement` · T79·T80·T82 |

```
걷은 참가비 == 나간 상금 + 환불 + 상점 몫
```

「못 누르는 이유를 화면이 적는다」(T83 · `FINISH_BLOCKERS`)는 **움짤에서 뺐다.**
정지 화면으로 충분해서 스틸(`18-finish-blocked-reasons.png`)로만 남는다.

## 2. README의 층이 그림의 쓰임을 정한다

README를 세 층으로 읽게 만든다. **층마다 그림이 하는 일이 다르다.**

| 층 | 무엇 | 그림의 역할 |
|---|---|---|
| 1 | 동작한다 | 그림이 **문장이다.** 사진 설명 말고는 산문이 없다 |
| 2 | 디테일 | 그림이 **근거다.** 1층에서 생긴 질문에 답한다 |
| 3 | 개발 문서 | 그림이 **좌표다.** 지금 README 본문 그대로 |

이 층 구분이 프레임 ①의 구멍을 닫는다. 인계 문서의 프레임 ①(딜러 셋 +
전광판)에는 **리바인을 수락하는 손이 없다** — 모달은 좌석 태블릿에 뜨고 딜러
화면에는 안 뜬다. 1층이면 치명적이지만 **2층이면 스틸을 옆에 붙여 원인을
대면 된다.** 디테일 층은 그림 하나가 혼자 설명할 필요가 없다.

**README 재구성은 이 브랜치가 하지 않는다.** T84는 촬영 코드와 `img/`까지고,
층 재구성은 촬영이 다 끝난 뒤 별도 브랜치에서 한다.

## 3. 시나리오 — 순서를 바꾼다

### 3-1. 무엇을 바꾸나

```
지금  첫 판 → 리바인 → [대기 8분] → 마감 → 병합① → 둘째 판 → 병합② → 여섯째 → 마무리
                        ^^^^^^^^^ 리바인과 이동 사이에 대기가 낀다

바꿈  첫 판 → 리바인 → 병합① → 둘째 판 → 병합② → [대기] → 셋만 남긴다 → 마무리
               \______________/                   ^^^^^^ 통째로 버린다
                프레임 ② 한 컷
```

**병합은 등록이 열려 있어도 된다.** `SessionService.releaseSeats`가 요구하는
것은 `GamePhase.WAITING`뿐이고 등록 상태를 안 본다. 마감을 요구하는 것은
파이널 테이블 판정 하나다 — `isFinalTable`이 `!isRegistrationOpen &&
tableCount === 1`이라(T77), **마감 전에 테이블을 하나로 합쳐도 막히지 않고
ICM의 문만 안 열린다.** 그러니 대기를 맨 뒤로 민다.

**여섯째를 대기 뒤에 두는 이유**는 그대로다. 상금이 「마감 전 · 예상」 상태에서
나가면 안 된다.

총 시간은 안 변한다. 마감은 대회 시작 후 10분에 오는 벽이고
(`SETTLEMENT_BLIND_STRUCTURE`의 레벨 1), 순서 변경은 그 10분을 무엇으로
채우느냐만 바꾼다.

### 3-2. 파이널 테이블에 **셋**을 남긴다

지금은 `playHand(final, '여섯째', 2)`라 하나만 나가고 다섯이 남는다.
**넷이 올인해 셋이 나가고 셋이 남게 바꾼다.**

얻는 것이 둘이다.

- **프레임 ③의 폰 셋이 「남은 전원」이 된다.** 다섯 중 셋을 고르는 임의성이
  없어진다 — 그 선택을 설명할 근거가 없다
- **이미 나간 상금이 셋이 된다**(6·5·4위). 마무리 확인 대화의 「남은 상금」이
  걷은 돈과 확연히 갈리고, 그 차이가 그 화면이 말하려는 전부다

둘(헤즈업)로 줄이지 않는 이유: ICM은 「칩 비율대로 **나눈다**」인데 둘이면
비율이 하나뿐이라 나눈 티가 안 난다. **셋이면 스택이 다른 셋에게 다른 금액이
가는 것이 폰 셋에 그대로 찍힌다.** 용량 때문에 둘로 줄일 이유도 없다 —
폰 화면은 로드된 뒤 안 바뀌고, animated webp는 프레임 간 차분을 저장하므로
**안 움직이는 타일은 거의 공짜다.**

`planHand`는 손대지 않는다. `occupiedSeats.slice(-count)`라 **좌석 번호가 큰
쪽부터 올인하고 앞쪽이 폴드한다** — 여섯 남은 자리에서 넷 올인이면 폴드 둘이
정해지고, 승자는 올인자 중 스택 최대다. 이미 재현된다.

## 4. 프레임 넷

### 프레임 ① — 엔트리는 사람 수가 아니다

| | |
|---|---|
| 화면 | 딜러 T1 · T2 · T3 + 전광판 (**2×2**) |
| 마크 창 | `첫 판 — 한 판에 여섯이 올인한다` → `병합 — 네 테이블이 둘이 된다` |
| 산출 | `11-entry-not-player.webp` |
| 보이는 정합 | **전광판 인원 35→15.** 이어서 **엔트리만 36이 되고 사람은 15 그대로**, 상금 목록이 다섯 줄에서 여섯 줄로 |
| 짝 | `itm-scaling.int-spec.ts` · T81 |
| 자르는 실행 | `complete` |

```
[딜러 T1 880×495] [딜러 T2 880×495]
[딜러 T3 880×495] [전광판 880×495]
                    합 1760×990 · 출력 폭 1100
```

세 테이블에서 동시에 여섯씩 올인하고 딜러가 지명하면 다섯씩 사라진다.
전광판의 남은 인원이 그 자리에서 떨어진다. 이어서 **T3의 한 자리가 0에서
5,000으로 되살아나고** 전광판의 엔트리가 36이 된다.

**리바인하는 사람을 T3에 둔다.** 원인(딜러 타일의 스택 부활)과
결과(전광판)가 한 프레임에 있어야 한다. 수락을 누르는 손은 이 프레임에
없다 — 좌석 태블릿의 일이라 **스틸 `12-rebuy-accept-raises-entry.png`가 옆에
붙는다**(§2의 2층 규칙).

**T4가 아니라 T1을 넣는 이유**: T1이 촬영 테이블이자 병합의 종착지라, 여기서
본 펠트가 프레임 ②·③에 계속 나온다. T1을 빼면 이 프레임에서 본 테이블 중
어느 것도 뒤에 안 나온다.

세 배경 테이블은 **카메라로만** 연다. 게이트웨이가 테이블 접속자 전원에게
`renderGame`을 뿌리므로, 누르는 것은 계속 `fixtures/wire.ts`가 하고 태블릿은
보기만 한다.

### 프레임 ② — 필드가 넷에서 하나로

| | |
|---|---|
| 화면 | 좌석 2 · 콘솔 · 폰 2 (**한 칸에 폰 둘**) |
| 마크 창 | `병합 — 네 테이블이 둘이 된다` → `둘째 판 — 두 테이블에서 열이 나간다` |
| 산출 | `03-four-tables-to-one.webp` |
| 보이는 정합 | **칩이 좌석보다 오래 산다.** 옮겨 앉아도 스택이 그대로다. 빈 테이블은 사람이 없어야 닫힌다 |
| 짝 | `table-move.int-spec.ts` · T27~T29 |
| 자르는 실행 | `complete` |

```
[좌석 · 리바인한 사람(T3) 880×495] [좌석 · 다른 사람(T4) 880×495]
[콘솔 1180×738] [폰A 290×738] [폰B 290×738]
                    합 1760×1233 · 출력 폭 1100
```

리바인 모달 수락 → 콘솔에서 T3·T4 좌석 해제 → 두 사람이 폰에서 **참가 OTP를
다시 보고** → 태블릿에 넣어 T1·T2에 앉는다 → 콘솔이 T3·T4를 닫는다.

**두 사람이 서로 다른 테이블로 흩어진다**(T3→T1, T4→T2). 폰이 둘인 것이
거기서 값을 한다 — 하나면 「이 사람 하나가 옮겼다」이고, 둘이면 「테이블이
합쳐지는 중이다」가 된다.

**화면으로 옮기는 것은 둘뿐이다.** 나머지 열넷은 `mergeInto`가 REST로
옮긴다. 열여섯을 전부 키패드로 태우면 촬영이 그만큼 늘어나고, 보이는 것은
같은 조작의 반복이다.

### 프레임 ③ — 두 문, 같은 등식

| | |
|---|---|
| 화면 | 콘솔(chop) · 딜러(complete) · 폰 3 + 폰 3 |
| 마크 창 | `마무리 — 셋이 한 화면에 있다` → `끝` |
| 산출 | `05-two-doors-same-ledger.webp` |
| 보이는 정합 | **같은 셋이 문에 따라 다른 금액을 받는다.** 두 장부의 「걷은」이 같다 |
| 짝 | `icm-chop.int-spec.ts` · `rake.int-spec.ts` · T79·T80·T82 |
| 자르는 실행 | **`chop`(좌열) + `complete`(우열)** |

```
[콘솔 · ICM 마무리 확인 대화 880×550] [딜러 · 마지막 순위를 찍는다 880×550]
[폰][폰][폰] 293×634 ×3               [폰][폰][폰] 293×634 ×3
        chop 실행                              complete 실행
                    합 1760×1184 · 출력 폭 1100
```

**이 프레임만 실행을 가로지른다.** 같은 시드라 파이널 테이블에 남는 셋이 두
실행에서 동일하고, 그래서 좌우가 **같은 사람의 다른 결말**이 된다. 인원이나
순서를 실행마다 달리하면 스택 분포가 갈리고 ICM 금액까지 갈려 비교가 무너진다.

위아래가 다른 것을 말한다.

- **위** — 왼쪽은 콘솔에서 합의한 숫자를 적고, 오른쪽은 테이블에서 끝까지 쳐서
  정한다. **딜은 콘솔의 일이고 승부는 펠트의 일이다.** 이 비대칭이 두 문의
  차이 자체다. `complete`에는 확인 대화가 없다 — `FinishRow`의 「종료」가
  `completeTournament`를 바로 부른다
- **아래** — 왼쪽 폰 셋은 칩 비율이 정한 금액, 오른쪽 폰 셋은 분배표가 정한
  1·2·3위 금액. **같은 화면에 다른 숫자**다

**전광판은 이 프레임에 없다.** 넣으면 좌우 대칭이 깨지고, 「제도가 정한 표」는
README에서 이 움짤 **바로 위에 스틸로** 놓는다(`04-prize-table-locked.png`).
읽는 순서가 「표를 본다 → 왼쪽은 그 표를 안 따른다 → 오른쪽은 따른다」가 된다.

**폰은 최종 셋이 정해진 뒤에 연다.** 누가 남는지는 결정적이지만 촬영 전에
알 수 없다. `stage()`는 테스트 도중 언제든 부를 수 있고, 늦게 연 면의 앞부분은
`buildScene`의 `tpad`가 검게 채운다. 대회가 닫힌 **뒤에** 폰을 새로고침해야
`/me`가 확정된 등수와 상금을 그린다.

### abort 움짤 — 중단하면 상점 몫이 0이 된다

| | |
|---|---|
| 화면 | 콘솔 · 전광판 (가로 둘) |
| 마크 창 | `마무리 — 셋이 한 화면에 있다` → `끝` |
| 산출 | `20-abort-refunds-all.webp` |
| 보이는 정합 | **환불 1,800,000 · 상점 몫 0.** 등식의 세 항이 다 보이는 유일한 문 |
| 짝 | `abort-settlement.int-spec.ts` · T82 |
| 자르는 실행 | `abort` |

```
[콘솔 · 중단 확인 대화 880×550] [전광판 880×550]
                    합 1760×550 · 출력 폭 1100
```

프레임 ③에 자리가 없어 따로 남긴다 — 문이 셋인데 좌우가 둘이다. 그래도 값이
있다: **상점 몫이 0이 되는 유일한 문**이라 등식의 오른쪽 항 셋이 한 화면에
다 나오고, 환불이 사람마다가 아니라 **무리로** 접히는 것(진행 중 · 탈락 ·
이미 상금을 받은 사람)이 표에 그대로 있다.

## 5. 파일 — 이름이 곧 그 그림의 내용이다

### 5-1. 규칙

`img/`를 `ls` 한 것만으로 **무엇이 담긴 그림인지 알 수 있어야 한다.** 지금은
아니다 — `s1-join`·`s2-hand`·`console.png`는 열어 봐야 안다. README가 그림을
고를 때마다 영상을 다시 여는 것이 그 값이다.

이 규칙은 이미 README에 적혀 있었다(「파일 이름이 그 그림의 주장이다」). 다만
**정산 촬영에만 적용됐고 기존 파일은 그대로였다.** 여기서 전부에 건다.

```
NN-<무엇을 보여주는가>.<webp|png>
```

- **`NN`은 README 등장 순서다.** `ls`가 곧 문서의 목차가 된다
- **이름은 주장이지 화면 이름이 아니다.** `console.png`가 아니라
  `18-finish-blocked-reasons.png` — 그 콘솔이 **무엇을 보여주려고** 거기
  있는지를 적는다
- 확장자가 종류를 가른다. `.webp`는 움짤, `.png`는 스틸
- **안 쓰는 그림은 번호가 없다.** 순서가 없으니 `ls`에서 뒤로 밀리고, 그것이
  곧 「지금 문서가 안 쓴다」는 표시다

번호는 그림이 끼어들면 밀린다. 그때는 `git mv`와 README 경로를 **같은
커밋**에서 고친다 — 어긋난 것을 잡아 주는 장치가 없으므로 갈라 놓으면 안 된다.

### 5-6. 이름 바꾸기는 T84가 한다

**README의 경로도 이 브랜치에서 같이 고친다.** 구조는 안 건드리고 경로만

## 7. 촬영과 자르기

```bash
npm run demo:settlement        # complete → chop → abort, 셋을 연달아
```

| | 시간 |
|---|---|
| 빌드 (contract + frontend) | ~2분 (한 번만) |
| `complete` — 시드 + 촬영 | ~14분 |
| `chop` — 시드 + 촬영 | ~14분 |
| `abort` — 시드 + 촬영 | ~14분 |
| **합** | **~44분** |

촬영 폴더가 테스트 제목별로 갈려 셋이 공존한다
(`마무리-최후-1인` · `마무리-ICM으로-닫는다` · `마무리-중단하고-환불한다`).
자르기는 셋이 다 있을 때 **한 번** 부른다.

### 돌릴 때 걸리는 것

이번 세션에 여덟 번 돌려서 얻은 것이다. 안 지키면 12분씩 날린다.

- **`TaskStop`이 playwright 자식 프로세스를 안 죽인다.** 세 실행이 같은 DB에서
  동시에 돌아 진단이 통째로 어긋난 적이 있다. 죽였으면
  `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match 'playwright' }`로
  **확인하고** 다음 촬영을 시작한다
- **촬영 중에 제품 소스를 고치지 않는다.** Next dev가 hot reload하면서 워커가
  죽는다(`code=3221226505`). 백엔드도 nest watch라 같은 일이 난다
- **시드는 개발 DB를 지운다.** 촬영마다 다시 깐다
- `ffmpeg-static`의 바이너리는 postinstall로 받는다. 없으면
  `node node_modules/ffmpeg-static/install.js`
