# 참가 OTP 설계 (T27)

**항목**: `docs/backlog.md`의 B1 계획 D(신설). 프론트 화면 명세
([`2026-07-27-frontend-screens-design.md`](./2026-07-27-frontend-screens-design.md),
front-end 워크트리)가 "미정 — 참가 OTP 없음 (B1)"으로 비워 둔 자리다.
**범위**: `backend/prisma/schema.prisma`(+마이그레이션), `backend/src/prisma/prisma.service.ts`,
`backend/src/payment/`, `backend/src/user/`
**프론트 영향**: 없음. 마이페이지 화면은 B7이다.

**이 티켓은 발급과 조회까지다.** OTP로 입장하는 것은 T28, 상점의 좌석 해제와
스택 이사는 T29다.

---

## 왜 필요해졌나

좌석 태블릿이 지금 `accessToken` 쿠키를 읽는다
(`frontend/src/app/(terminal)/table/[tableId]/page.tsx`). **플레이어가 그 태블릿에서
직접 로그인한다**는 뜻이다. 태블릿이 그 사람을 아는 이유는 거기서 로그인했기
때문이고, 마법은 없다.

문제는 사람이 자리를 옮길 때다. 쉬는 시간에 테이블을 합치면 사람은 걸어가는데
**세션은 따라가지 않는다.** 옛 태블릿에는 그 사람 로그인이 남고, 새 태블릿에는
없다. 서버가 좌석을 옮겨 주는 API를 만들어도 이 어긋남은 그대로다 — 옮겨 놓은
자리에 앉을 사람을 인증할 방법이 없기 때문이다.

**OTP는 사람이 들고 다니는 값이라 따라간다.** 폰에서 확인해 앞에 있는 태블릿에
넣으면, 그 자리에서 신원이 성립한다. 공용 기기에 개인 계정 세션이 남지 않는
것은 덤이다.

---

## 도메인 전제

**딜러 OTP와 참가 OTP는 이름만 같고 성질이 다르다.**

| | 딜러 OTP (T23) | 참가 OTP (여기) |
|---|---|---|
| 단위 | 대회 하나. 딜러 여럿이 공유 | **참가자 × 대회.** 사람마다 다르다 |
| 권한 | `resolveWinners` — 돈이 나간다 | 자기 좌석 하나 |
| 저장 | bcrypt 해시만 | **평문** |
| 재조회 | 불가. 재발급만 | 마이페이지에서 언제든 |
| 시도 제한 | 대회 단위 5회 5분 | **없다** |

네 칸이 전부 반대인데 근거가 있다. 아래에서 하나씩 적는다.

---

## 결정

### 참가자마다 다른 OTP를 발급한다

`TournamentParticipation`에 붙인다. 그 모델이 이미 "이 사람이 이 대회에
참가했다"는 사실 자체이고, 참가비·리바인 횟수·최종 순위가 모두 여기 있다.

대회 하나에 공통 OTP를 두는 안은 버렸다. 검증은 싸지지만 **누가 앉았는지
구분되지 않는다.** 남의 자리에 앉는 것을 막을 수 없고, 좌석과 사람의 대응이
시스템에 없으면 장부(스택)를 누구에게 붙일지도 정할 수 없다.

### 평문으로 저장한다

T23은 딜러 OTP를 bcrypt 해시로만 저장했다. **여기서는 정반대 결론이고, 이유가
셋이다.**

1. **요구사항이 재조회다.** 마이페이지의 참여 대회 목록에서 언제든 확인할 수
   있어야 한다. 해시로 저장하면 그 화면을 만들 수 없다. 딜러 OTP는 재발급이
   탈출구였지만(상점 콘솔이 새 값을 뽑아 준다), 참가자마다 재발급 버튼을 두는
   것은 같은 화면을 훨씬 나쁘게 만드는 길이다.
2. **권한의 크기가 다르다.** 딜러 OTP가 뚫리면 `resolveWinners`이고, 승자는
   계산되지 않고 **입력되므로** 시스템이 판정할 정답이 없다. 나간 상금은 되돌릴
   경로가 없다. 참가 OTP가 뚫리면 얻는 것은 **이미 참가비를 낸 사람의 좌석
   하나**다. 그 자리에 두 사람이 앉으면 현장에서 즉시 드러난다.
3. **해시가 막는 것이 DB 덤프인데, 그 시점에는 더 큰 것이 이미 샜다.** 같은
   테이블에 참가비와 상금 내역이 있다.

**대신 노출 경로를 구조로 막는다** — 아래 "기본이 감춤이다" 참고.

### 8자리 숫자 문자열이다

딜러 OTP는 6자리다(`dealer-otp.ts`). 참가 OTP는 8자리로 간다. **시도 제한을
두지 않기로 했기 때문**이다.

계산이 근거다. 대회 참가자가 200명이면 유효한 OTP가 200개다.

```
6자리: 200 / 10^6   = 1/5,000        5천 번이면 남의 자리에 앉는다
8자리: 200 / 10^8   = 1/500,000      같은 노력으로 100배 어렵다
```

**공짜에 가까운 방어다.** 태블릿 숫자 입력이 두 자 늘어나는 것이 전부고, 유일성
충돌에 따른 재생성도 사실상 사라진다. 생성은 딜러 OTP와 같은 방식이다 —
`randomInt`로 뽑고 `padStart`로 앞자리 0을 지킨다. 숫자로 다루면 앞자리 0이
사라져 후보 공간이 명목값에 못 미친다.

생성 함수는 `backend/src/payment/player-otp.ts`에 둔다 —
`src/dealer/dealer-otp.ts`와 같은 자리다. 해시가 없으므로 `generatePlayerOtp`
하나뿐이다.

### 대회 안에서 유일해야 한다

`@@unique([tournamentId, playerOtp])`.

입장은 "이 대회에서 이 OTP를 가진 사람"으로 사람을 찾는다. 둘이 같은 값을 가지면
그 조회가 성립하지 않는다. 8자리라 충돌은 드물지만 **드문 것은 안 나는 것이
아니다.** P2002를 잡아 다시 뽑는다(최대 5회). 재시도 코드가 아니라 제약이 최종
방어인 것은 T25의 `tableOrder`와 같은 모양이다.

### 시도 제한을 두지 않는다

T23은 딜러 OTP에 대회 단위 5회 5분 잠금을 걸었다. **여기서는 걸지 않는다.**

- **잠금 단위를 참가자로 내릴 수 없다.** OTP를 넣기 전에는 신원이 없다. T23이
  IP 단위와 계정 단위를 모두 버린 것과 같은 벽이다.
- **대회 단위로 걸면 DoS 원시함수가 된다.** 이건 이미 겪은 문제다 —
  `backlog.md`의 "T23이 남긴 이월 항목" 첫 줄이 그것이고, 딜러 로그인에 대해
  분당 한 요청으로 모든 대회를 무기한 잠글 수 있다고 적혀 있다. 참가 OTP에
  같은 것을 걸면 **대회 진행 자체가 멈춘다.** 자리를 옮긴 사람들이 전부 입장을
  못 한다.
- **입력이 반복되는 값이다.** 딜러 OTP는 대회당 한 번 넣지만, 참가 OTP는
  재배치·기기 교체·재부팅마다 다시 넣는다. 잠금과 상성이 나쁘다.

**대신 잔여 위험을 정확히 적는다.** 위협 모델 2절이 "같은 망의 단말은 WS
엔드포인트를 직접 열 수 있다"고 명시한다. 즉 태블릿 앞에 서지 않고 노트북으로
조용히 때리는 경로가 있고, **현장 직원의 감지 루프가 여기에는 닿지 않는다.**
8자리는 그 경로를 겨냥한 값이다. 프론트의 입력 제한(연속 실패 시 지연)은
사람의 오타를 줄이지만 이 경로를 막지는 못한다 — 막는 것은 길이와,
언젠가 붙을 전역 Throttler(`backlog.md` B1 이월)다.

### 기본이 감춤이다 — Prisma 클라이언트 수준 `omit`

`PrismaService`의 `super()`에 기본 omit을 건다.

```ts
omit: { tournamentParticipation: { playerOtp: true } }
```

읽는 단 한 곳(마이페이지 조회)만 `omit: { playerOtp: false }`를 준다. 그러면
**빠뜨림이 조용한 누출이 아니라 컴파일 에러**가 된다 — 단, `super()`에 이
객체를 넘기는 것만으로는 안 된다. `class PrismaService extends PrismaClient`
처럼 타입 인자 없이 상속하면 `PrismaClient<ClientOptions>`의 `ClientOptions`가
기본값(`Prisma.PrismaClientOptions`, 아직 모델별로 좁혀지지 않은 범용 타입)으로
고정돼 `omit`이 런타임에만 걸리고 생성된 결과 타입은 `playerOtp: string`을
그대로 선언한다 — 빠뜨린 읽기 경로가 컴파일은 통과하고 `undefined`를 조용히
돌려준다. 실제로 이 리포에서 그렇게 나던 것을 확인했다. 컴파일 에러로 만들려면
`extends PrismaClient<{ adapter: PrismaPg; omit: { tournamentParticipation: {
playerOtp: true } } }>`처럼 `ClientOptions`를 명시해야 한다 — 이 타입 인자가
`Prisma.TournamentParticipationDelegate<ExtArgs, ClientOptions>`를 거쳐 결과
타입에서 `playerOtp`를 실제로 지운다. `prisma.service.ts`가 이 형태를 쓴다.

`backlog.md`의 "T23이 남긴 이월 항목"에 있던 그 항목을 여기서 실제로 한다.
T23은 `dealerOtpHash`를 손으로 지우는 `omit`이 일곱 곳이었고, 그중 두 곳을
빠뜨려 실제로 누출을 겪었다. 참가 OTP는 **평문**이고 참가자 전원의 값이 한
테이블에 있어서, 상점 콘솔의 참가자 목록 한 번이면 대회 전체가 샌다.

> **버린 선택지 — 호출부마다 `omit`을 쓴다.** 지금 `TournamentParticipation`을
> 읽는 곳은 둘뿐이고(`playsync.service.ts:367`, `session.service.ts:512`) 둘 다
> 응답에 싣지 않는다. 그래서 "지금은 위험이 없다"고 말할 수 있다. 그러나 이
> 필드의 독자는 **아직 없는 화면**이다 — 상점 콘솔의 참가자 목록, 전광판,
> 어드민. 규율로 막으면 그 화면을 만드는 사람이 규율을 알아야 하고, T23이
> 그것으로 두 번 실패했다.

### 발급은 참가 확정 트랜잭션 안이다

지금 `joinSessionWithSeat`가 `TournamentParticipation`을 만드는 그 자리다.
참가비 차감과 같은 트랜잭션이라 "돈은 나갔는데 OTP가 없는" 상태가 생기지 않는다.

**리바인은 재발급하지 않는다.** 같은 대회, 같은 사람이다. `buyInCount`만 오른다.

**재발급 엔드포인트를 만들지 않는다.** 마이페이지에서 언제든 보이므로 잃어버릴
수가 없다. 딜러 OTP의 재발급은 해시 저장의 짝이었지, 그 자체가 필요한 기능이
아니었다.

### 조회는 본인만, 끝난 대회만 뺀다

```
GET /user/me/participations
```

JWT의 `userId`로만 조회한다. 경로에 `userId`를 받지 않는다 — 받는 순간 남의
것을 조회할 수 있는지 검사하는 코드가 필요해지고, 그 검사가 빠질 자리가 생긴다.

**대회가 `FINISHED`가 아니면 `playerOtp`를 싣는다.** 살아있는 상태를
나열하는 대신 끝난 상태 하나만 제외하는 방향으로 쓴다 — 나열하면 상태가
하나 늘 때 조용히 빠진다. `SYNCING`(테이블 이동/밸런싱 대기)이 그 경우다:
참가자가 새 테이블에 재입장하려면 바로 이 OTP가 필요한 순간인데, 살아있는
상태만 나열했다면 빠뜨리기 쉬웠다. 끝난 대회의 OTP는 쓸 데가 없고, 목록에
남아 있으면 유출 표면만 넓힌다.

## 범위 밖

- **OTP로 입장하기** — T28. 좌석 확정을 결제 시점에서 입장 시점으로 옮기는
  일이고, 좌석 예매와 `acquireSeatLock` 폐기가 거기 붙는다.
- **상점의 좌석 해제와 스택 이사** — T29. `currentStack`을 `TablePlayer`에서
  `TournamentParticipation`으로 옮긴다.
- **마이페이지 화면** — B7.
- **전역 레이트 리밋** — `backlog.md` B1 이월 항목. 참가 OTP만의 문제가 아니다.

## 테스트

| 파일 | 계층 | 무엇 |
|---|---|---|
| `payment/player-otp.spec.ts` | 단위 | 8자리인가, 앞자리 0이 살아 있는가, 매번 다른가 |
| `payment/payment.service.int-spec.ts` | 통합 | 참가마다 OTP가 발급되는가, 리바인은 재발급하지 않는가, 대회 안에서 유일한가, 충돌 시 재생성하는가 |
| `user/user.service.int-spec.ts` | 통합 | 본인 것만 나오는가, `FINISHED` 대회는 OTP가 빠지는가, **기본 조회에 `playerOtp`가 없는가**(omit 회귀) |

**충돌 재생성의 RED 확인 방법**: 난수 생성기를 같은 값만 뱉도록 임시로 바꾸고
두 번째 참가가 재시도 끝에 실패하는지 본다. 재시도가 없으면 P2002가 그대로
올라온다.

**omit 회귀의 RED 확인 방법**: `PrismaService`의 기본 omit 한 줄을 지우고
`playerOtp`가 응답에 실리는지 본다. 이 검사가 빨개지지 않으면 조회 경로를
잘못 고른 것이다.
