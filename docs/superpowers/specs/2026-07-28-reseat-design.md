# 좌석 재배치 설계 (T27)

**항목**: `docs/backlog.md`의 B8. 자동 밸런싱은 하지 않기로 하고, 그 자리에
상점이 트리거하는 재배치를 넣는다.
**범위**: 백엔드만. `session.service.ts`, `session.controller.ts`,
`packages/contract`. 스키마 변경 없음.
**프론트 영향**: 없음. 상점 콘솔 대시보드가 아직 없어 호출자가 생기지 않는다
(T25의 테이블 생성·삭제와 같은 상태).

---

## 도메인 전제

**좌석 재배치는 쉬는 시간에 한 번에 일어난다.**

인원이 3/3/3이면 테이블 하나로 합쳐 9가 되고, 4/4/5면 두 테이블에 6/7로 다시
나눈다. 한 명씩 옮기는 것이 아니라 **판을 다시 짜는 것**이고, 그것이 현장에서
실제로 벌어지는 일이다 — 사람들이 일어나서 걸어가고, 딜러가 칩과 카드를 정리하고,
빈 테이블에는 아무도 앉지 않는다.

**언제 할지는 사람이 정한다.** 서버가 인원을 감시하다가 스스로 옮기지 않는다.
칩 스택, 남은 인원, 딜러 배치, 손님이 자리를 비웠는지까지 보고 정해지는 일이라
서버가 대신 정할 근거가 없다 — **승자를 계산하지 않고 딜러에게 입력받는 것과
같은 결정이다.**

**옮기는 대상은 좌석이지 사람이 아니다.** 시스템이 아는 것은 "누가 몇 번 테이블
몇 번 자리에 앉아 있다"까지고, 실제로 걸어가는 것은 사람이 한다. 그래서 이
연산은 **장부를 현실에 맞추는 기록**이지 현실을 움직이는 명령이 아니다.

## 결정

### 요청은 전체 배치 계획이다

```
POST /store/sessions/:id/reseat    @Roles(STORE_ADMIN)

{ assignments: [{ userId, tableId, seatIndex }, ...] }
```

지금 앉아 있는 사람 **전원**이 정확히 한 번씩 들어온다. 서버가 현재 스냅샷과
diff해서 실제로 바뀐 사람만 옮긴다.

**전원을 받는 이유는 검증이 완전해지기 때문이다.** 부분 목록을 받으면 "빠진
사람은 그대로 두라는 뜻"인지 "빠뜨린 것"인지 구분할 수 없다. 전원이 들어오면
빠짐·중복·유령이 전부 400이 된다. 그리고 이 API의 호출자는 D&D 대시보드인데,
그 화면은 어차피 전체 배치를 들고 있다 — 전원을 보내는 것이 자연스럽다.

> **버린 선택지 — "이 사람을 저 테이블로" 부분 이동 API.** 처음에 이 모양으로
> 잡았다. 테이블 합치기가 호출 다섯 번이 되고, 중간에 실패하면 절반만 옮겨진
> 상태가 남는다. 그 사이 락이 풀려 딜러가 핸드를 시작할 수도 있다. 무엇보다
> **현장의 연산 단위와 어긋난다** — 재배치는 한 번에 일어나는 일이다.
>
> **버린 선택지 — 남길 테이블 목록만 받고 서버가 배분.** `{ tableIds: [t1, t2] }`
> 한 줄로 4/4/5 → 6/7이 된다. 간단하지만 **배분 규칙을 서버가 갖게 된다** —
> 누구를 어디로 보낼지, 최소 이동으로 풀지, 스택을 고려할지. 그건 자동 밸런싱을
> 트리거만 사람에게 넘긴 것이고, 하지 않기로 한 그 규칙이다.

### 좌석 번호는 콘솔이 정한다

`seatIndex`가 요청에 들어간다. 호출자가 D&D 대시보드라 조작 자체가 "이 사람을
저 자리로"이고, 좌석 태블릿이 자리에 고정돼 있어 **사람이 실제로 그 의자에
앉아야 한다.** 서버가 임의로 배정하면 화면이 말한 자리와 손님이 앉은 자리가
어긋난다.

### 맞바꾸기를 허용한다 — 임시 좌석 2단계로

전체 계획이라 순열이 그대로 표현된다. A와 B가 자리를 바꾸는 배치가 자연스럽게
나오는데, `@@unique([tableId, seatPosition])` 때문에 **중간 상태가 제약을
위반한다.**

한 트랜잭션 안에서 두 단계로 쓴다.

1. 바뀌는 행 전부를 임시 좌석(음수)으로 민다
2. 최종 `tableId` · `seatPosition`을 쓴다

`seatPosition`은 `Int`고 체크 제약이 없어 음수가 들어간다. 트랜잭션 안이라
중간 상태가 밖에서 보이지 않는다.

> **버린 선택지 — 맞바꾸기 금지(빈자리로만 이동).** 부분 이동 API 전제에서는
> 이것이 맞았다. 자리 교환은 인원 균형과 무관하고, 금지하면 이 제약 문제가
> 통째로 사라진다. 전체 계획에서는 성립하지 않는다 — 계획을 받는 이상 순열이
> 들어올 수 있고, 그걸 400으로 거절하면 D&D 화면에서 가능한 조작을 API가
> 거부하는 셈이다.

### 가드는 `phase === GamePhase.WAITING`이다

관련 테이블이 **전부** `WAITING`이어야 한다. 하나라도 진행 중이면 409.

**이 가드 하나가 어려운 것을 전부 지운다** — 팟, 차례 순서, 폴드 상태, 사이드팟이
개입하지 않고, `buttonUser`는 좌석 번호라 사람이 옮겨도 그대로 둔다.

**휴식 시간(`isBreak`)을 따로 보지 않는다.** 휴식 중에는 `startPreFlop`이 이미
거부하므로(`dealer.service.ts:189`) 모든 테이블이 자연히 `WAITING`에 머문다.
반대로 극후반에 휴식이 아니어도 핸드 사이라면 테이블을 합칠 수 있어야 하는데,
그것도 같은 조건으로 열린다. 조건 하나가 두 시나리오를 덮는다.

### 검사는 락 안에서 다시 한다

락 밖에서 `phase`를 보고 옮기면 T25의 `deleteTable`이 걸렸던 check-then-act가
그대로 재현된다 — 검사와 이동 사이에 딜러가 `startPreFlop`을 누르면 **핸드가
시작된 테이블에서 사람이 사라진다.** `startPreFlop`도 `withTableLock(tableId)`를
타므로 같은 락 안에서 다시 읽으면 구조로 막힌다.

### 락은 대회의 **모든** 테이블을, `tableId` 정렬 순으로 중첩한다

여럿을 동시에 잠그므로 순서 규칙이 없으면 데드락이 난다(A가 t1을 잡고 t2를
기다리는데 B가 t2를 잡고 t1을 기다린다). 정렬해 순서대로 중첩 획득한다.

**계획에 등장하는 테이블만으로는 부족하다.** 계획에서 빠진 테이블에 사람이
앉아 있으면 그 사람이 조용히 사라진다 — "앉아 있는 전원이 계획에 있는가"를
검사하려면 대회의 모든 테이블을 읽어야 하고, 읽는 것은 잠근 뒤여야 한다.
그래서 `WAITING` 검사도 대회 전체에 걸린다.

`withTableLock`은 단일 테이블용이라(`redis.service.ts:28`) 다중 락 헬퍼가 하나
필요하다. `reduce`로 중첩하면 된다.

**TTL은 이 호출에만 늘린다.** 기본값이 `ttlMs = 5000`인데(`redis.service.ts:31`)
재배치는 그 안에서 DB 트랜잭션까지 돈다. 테이블 셋을 잠그고 인원 열댓 명을 두
단계로 쓰는 동안 5초를 넘기면, 락이 만료된 뒤에도 코드가 계속 도는 상태가 된다 —
그때 딜러가 `startPreFlop`을 잡으면 락이 막아야 할 바로 그 경합이 열린다.
`ttlMs = 15000`을 준다. 통합 테스트에서 실제 소요를 재서 여유가 충분한지 확인하고,
아니면 그 자리에서 올린다.

### 빈 테이블은 자동으로 지우지 않는다

3/3/3 → 9면 테이블 둘이 빈다. 그대로 둔다. 테이블을 닫는 것은 딜러를 빼고 칩과
카드를 정리하는 물리적 행위이고, T25가 자동 생성을 지운 것과 같은 논리다.
상점이 기존 `DELETE /store/sessions/:id/tables/:tableId`로 명시적으로 닫는다.

### 실패하면 아무도 움직이지 않는다

검증 하나라도 걸리면 전체가 거부된다. 부분 적용이 없다. 재배치는 판을 다시
짜는 것이라 절반만 적용된 상태에 의미가 없다.

## 처리 순서

**락 밖**

1. `assertTournamentOwnership` — 서비스 메서드의 **첫 문장** (T25 관행)
2. 대회가 `FINISHED`면 409
3. 요청 자체의 정합성 — `assignments`가 비었거나, `userId`가 중복이거나,
   `(tableId, seatIndex)`가 중복이거나, `seatIndex`가 0~8 밖이거나, 한 테이블에
   9명을 넘으면 400
4. 등장하는 `tableId`가 전부 그 대회 소속인지 (`tournamentId_id` compound) —
   아니면 404

**락 안** (대회의 모든 테이블, 정렬 순 중첩)

5. 스냅샷 전부 로드. 하나라도 `phase !== WAITING`이면 409. **스냅샷이 없는
   테이블은 빈 테이블이다** — `createTable`은 좌석 비트맵만 만들고 스냅샷은
   만들지 않는다. 없는 것을 진행 중으로 보지 않고, 그 테이블에 사람이 오면
   살아 있는 스냅샷에서 블라인드 값을 물려받아 새로 만든다
6. 스냅샷들에 실제로 앉아 있는 사람의 집합을 만든다. `assignments`의 `userId`
   집합과 정확히 일치하지 않으면 400 (빠진 사람 · 앉아 있지 않은 사람)
7. 현재 위치와 diff — 바뀐 사람만 추린다. 하나도 없으면 그대로 200
8. DB 트랜잭션: 바뀌는 `TablePlayer` 행을 임시 좌석으로 밀었다가 최종값으로.
   `currentStack`도 스냅샷의 `stack`으로 함께 쓴다
9. 스냅샷 재구성 — 관련 테이블 전부의 `players` 배열을 새 배치로 다시 쓰고 저장
10. 좌석 비트맵: 떠난 자리 `false`, 앉은 자리 `true`. **내리는 루프와 올리는
    루프를 나눈다** — 한 루프에서 처리하면 A의 자리를 B가 물려받는 맞바꾸기에서
    B의 올리기가 먼저 돌고 A의 내리기가 나중에 돌아 방금 켠 비트를 끈다
11. `setUserContext`를 옮긴 사람마다 갱신
12. `SEAT_LIST_UPDATED` 한 번 + 영향받은 테이블마다 `renderGame`

**좌석의 진실은 스냅샷이다.** 6번에서 참가자 집합을 `TournamentParticipation`이
아니라 스냅샷에서 만드는 이유다. `status`는 탈락·상금 처리의 기록이고, 지금
누가 어느 의자에 앉아 있는지는 스냅샷과 좌석 비트맵이 안다.

**스택도 스냅샷이 진실이다.** `WAITING`이면 직전 핸드의 체크포인트가 돌아 DB와
일치해야 하지만, 어긋나 있으면 스냅샷을 따른다. 라이브 값이 그쪽이다.

**DB → Redis 순서는 기존 관행을 따른다.** `buyIn`·`createTable`·`startSession`이
전부 DB를 커밋한 뒤 Redis를 만진다. Redis 호출이 실패하면 장부와 화면이
어긋나는 노출이 있지만, 이 티켓이 만드는 것이 아니라 이미 있는 모양이다.
B2에서 한꺼번에 본다.

## 테스트

**전부 실패를 먼저 본다.** 새 테스트가 처음부터 통과하면 의심한다 — T22·T23·T24·T25가
전부 한 번씩 겪었다.

| 파일 | 계층 | 무엇 |
|---|---|---|
| `session.controller.spec.ts` | 단위 | 라우팅과 `@Roles(STORE_ADMIN)` |
| `session.service.spec.ts` | 단위 | 요청 정합성 분기 — 빈 목록, `userId` 중복, 좌석 중복, `seatIndex` 범위 밖, 한 테이블 9명 초과 |
| `session.service.int-spec.ts` | 통합 | 3/3/3 → 9, 4/4/5 → 6/7, 맞바꾸기, 소유권 403, 남의 대회 테이블 404, `FINISHED` 409, `WAITING` 아님 409, 앉은 사람 집합 불일치 400, **원자성**(하나 틀리면 DB·스냅샷·비트맵 전부 그대로), 이벤트 방출 |
| `session.service.int-spec.ts` | 통합 | **경합** — 락 밖 검사 통과 후 `startPreFlop`이 끼어드는 경우. 락 안 재확인이 없으면 통과하는 테스트여야 한다 |
| `scenario/*.int-spec.ts` | 시나리오 | 두 테이블 하네스에서 재배치 후 불변식 — 칩 총량 보존, 좌석 비트맵 == 스냅샷, 폴드 자격, 차례 |

**시나리오 하네스를 넓히는 것이 이 티켓의 숨은 비용이다.** `harness.ts`가 지금
`tableId` 하나만 들고 있다(`harness.ts:49`). 두 테이블을 세우고 양쪽에 사람을
앉히는 배선이 필요하다.

**RED 확인이 특히 중요한 곳 둘.**

- **원자성** — 성공 경로만 보면 초록이 나온다. 일부러 실패하는 배치를 넣고 DB와
  Redis 양쪽이 **손대지 않은 상태**인지 봐야 한다.
- **락 안 재확인** — 이 테스트는 재확인 코드를 지웠을 때 실제로 빨개져야 한다.
  안 빨개지면 경합 창을 못 만든 것이다.
