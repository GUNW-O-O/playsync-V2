# README 시각 자산 — 산출물과 촬영

**항목**: 백로그 (T34 후속). 선행은 T33(촬영 하네스) · T34(화면 구현)다.
**상태**: 초안. 승인 전.

README는 563줄인데 **이미지가 0장**이다. 이 문서는 그 그림을 무엇으로,
어디서, 어떻게 뽑는지를 정한다. README의 글 구조는 건드리지 않는다.

---

## 1. 규칙 둘

> **README에 들어가지 않을 화면은 그리지 않는다.**
> 그 경로가 필요하면 API로만 통신되면 된다.

§2가 그 목록이다. 여기 없는 화면은 404가 나지 않을 만큼만 유지하고 디자인
투자를 하지 않는다.

> **데모가 증명하는 것은 "돌아간다"가 아니라 "정합이 무너지지 않는다"다.**

돌아간다는 것은 V1이 이미 보였다. V2가 한 일은 **흔들었을 때 장부가 맞는지**를
확인한 것이고, 데모는 그것을 보여야 한다.

그래서 장면마다 **시나리오 테스트를 짝으로 붙인다.** 시나리오 계층이 단계마다
검사하는 불변식이 그대로 화면에서 눈으로 확인되는 것들이기 때문이다 — 칩 총량
보존, 사이드팟 합 == 팟, 폴드한 사람은 자격 없음, 쇼다운에는 차례 없음,
좌석 비트맵 == 스냅샷.

README에서 둘을 나란히 놓으면 "테스트가 있다"가 아니라 **"이 테스트가 저
화면의 이것을 지킨다"**가 된다.

## 4. 무대

시드가 깔아 둔 것 위에 얹는다(`backend/prisma/seed.ts` — 상점 1 · 대회 1
`PENDING` · 테이블 2 · 결제 마친 참가자 7 + 미결제 `demo` 1).

| 테이블 | 사람 | 시작 스택 | 나중 역할 |
|---|---|---|---|
| 1번 | `short` | 5,000 | 올인. 족보 1위로 메인팟을 먹는다 |
| 1번 | `mid` | 5,000 | 사이드팟에서 져서 **탈락한다** |
| 1번 | `deep` | 5,000 | 사이드팟을 먹는다 |
| 2번 | 둘 | 5,000 | 합치기 대상. 1번으로 옮겨 온다 |

칩 총량 **15,000**(1번 테이블). 이 값이 촬영 끝까지 변하지 않는다.

### 스택은 핸드를 돌려서 벌린다 — 손으로 고치지 않는다

시드는 전원 5,000 균등이다. **스택이 같으면 사이드팟이 갈리지 않아** 장면 3의
경로가 아예 실행되지 않는다.

`allin-sidepot.int-spec.ts`는 스냅샷을 직접 고쳐 벌린다 — 그 테스트의 검증
대상이 착석이 아니라 정산이기 때문이다. **데모는 그렇게 하지 않는다.**

승자를 딜러가 입력하므로 **누가 이길지는 촬영이 통제한다.** 그래서 앞에
핸드를 한두 판 돌려 `deep`에게 몰아주면 스택이 저절로 갈린다. 그 편이 낫다:

- **"무대를 손으로 세팅했다"는 각주가 필요 없다.** 화면에 보이는 모든 숫자가
  화면에서 벌어진 일의 결과다
- **칩 총량 보존을 여러 판에 걸쳐 보여준다.** 한 판만 찍으면 그 판의 덧셈이
  맞는 것이고, 여러 판을 거쳐도 15,000이면 그건 다른 주장이다
- 장면 2(핸드가 돈다)가 억지 데모가 아니라 **장면 3의 준비**가 된다

**금액을 미리 박지 않는다.** 워밍업 핸드가 끝난 뒤 스냅샷에서 실제 스택을
읽고, 그 값을 기준으로 올인 금액을 정한다. 필요한 것은 정확한 숫자가 아니라
`short < mid < deep`과 사이드팟이 갈리는 것뿐이다.

각 핸드가 끝날 때마다 칩 총량이 15,000인지 확인하고, 어긋나면 **거기서
촬영을 멈춘다** — 시나리오 계층이 단계마다 불변식을 검사하는 것과 같은 이유다.
마지막에 한 번만 보면 "어딘가에서 칩이 사라졌다"까지만 알 수 있다.

## 5. 장면 다섯

**따로 뽑는다.** 섹션마다 캡션을 붙일 수 있고, 하나가 실패해도 나머지가 산다.
정지 화면으로 충분한 것은 스틸로 뺀다.

촬영은 이어서 한 번에 돌린다 — 장면이 서로의 상태를 이어받기 때문이다
(핸드에서 사람이 죽어야 합칠 인원이 준다). 자르는 것은 ffmpeg가 한다.

---

### 장면 1 — 사람이 대회에 들어간다

| | |
|---|---|
| 화면 | 폰 · 좌석 태블릿 · 콘솔 (3면) |
| 산출 | 움짤 + 스틸 3장 |
| 보이는 정합 | **좌석 비트맵 == 스냅샷.** 같은 자리에 두 사람이 앉지 못한다 |
| 짝 | `frontend/e2e/terminal.spec.ts` · T28 · T29 |

폰에서 참가비를 낸다 → `/me`에서 **참가 OTP를 조회한다** → 자리로 걸어가
태블릿에 그 번호를 넣는다 → 앉는다 → **콘솔의 좌석 도식에 그 사람이 뜬다.**

세 화면이 같은 사람 하나를 각자의 자리에서 가리키는 것이 이 시스템의 구조
자체다. 폰이 보여준 모양(자릿수만큼 칸)과 태블릿이 요구하는 모양(키패드)이
같다는 것도 여기서 보인다.

---

### 장면 2 — 대회가 열리고 핸드가 돈다

| | |
|---|---|
| 화면 | 좌석 태블릿 2 · 딜러 1 · 전광판 1 (**2×2**) |
| 산출 | 움짤 |
| 보이는 정합 | **차례는 하나뿐**(한쪽 태블릿에 액션 버튼이 살아 있으면 다른 쪽은 죽어 있다). **여러 판을 거쳐도 칩 총량 15,000** |
| 짝 | `full-flow.int-spec.ts` |

콘솔에서 **대회 시작** → 전광판이 `대기 중`에서 블라인드 시계로 바뀐다.
딜러가 **프리플랍 시작** → 두 펠트에 블라인드가 깔린다. 액션이 오간다.

한 클릭이 세 면을 동시에 바꾸는 것을 한 화면에서 본다.

**여기서 핸드를 한두 판 돌려 스택을 벌린다**(§4). 스택이 갈리는 것이 곧
장면 3의 무대이고, 판이 바뀌어도 총량이 그대로인 것이 이 장면의 두 번째
주장이다.

---

### 장면 3 — 올인, 사이드팟, 그리고 딜러의 실수를 시스템이 막는다

| | |
|---|---|
| 화면 | 딜러 1 · 좌석 태블릿 2 |
| 산출 | 움짤 + 스틸(승자 결정 화면) |
| 보이는 정합 | **사이드팟 합 == 팟.** **칩 총량 14,000 보존** |
| 짝 | `allin-sidepot.int-spec.ts` — *"이 시나리오가 가장 중요하다"* |

```
short 올인 (자기 전부) · mid 올인 (자기 전부) · deep 콜
  1층(메인)  short의 스택 × 3     자격 short · mid · deep
  2층        (mid − short) × 2    자격 mid · deep    ← short는 낼 돈이 없었다
```

금액은 장면 2가 끝난 시점의 실제 스택에서 나온다(§4). 아래 표는 `short 1,000
· mid 3,000 · deep 11,000`으로 갈렸다고 가정한 예시다 — 비율이 아니라 **덧셈이
맞는다는 것**이 요점이다.

**여기가 이 데모의 심장이다.** 딜러가 승자를 찍는다.

1. 딜러가 **`short`만 찍는다** → 화면이 **거부**하고 "지명되지 않은 팟"이라고
   알려준다. 예전에는 그 팟이 조용히 증발했다(T15)
2. 다시 **`short` → `deep`** 순서로 찍는다 → 층마다 알맞은 사람에게 간다

| | 전 | 후 |
|---|---|---|
| short | 1,000 | **3,000** — 족보 1위, 메인팟 |
| mid | 3,000 | **0** — 탈락 |
| deep | 11,000 | **12,000** — 사이드팟 |
| 합 | **15,000** | **15,000** |

승자는 계산되지 않고 **입력된다**. 대신 부기 — 팟이 몇 층이고 누가 어느 층의
자격자인지 — 는 시스템이 책임진다. 카드가 실물이라 잘못 나간 지급을 되돌릴
근거가 테이블 위에 남지 않기 때문이다.

**거부 장면을 반드시 넣는다.** "정합이 무너지지 않는다"의 가장 직접적인
그림이다 — 시스템이 사람의 실수를 막는 순간.

---

### 장면 4 — 탈락과 리바인

| | |
|---|---|
| 화면 | 좌석 태블릿 (mid) · 폰 |
| 산출 | 움짤 |
| 보이는 정합 | 탈락은 폰으로 간다. 태블릿은 **다음 사람의 자리**로 돌아간다 |
| 짝 | `elimination-rebuy.int-spec.ts` |

mid의 스택이 0이 된다 → **리바인 오버레이**(리바인은 lv3까지, 지금 lv1) →
거절 → 탈락 → "폰에서 확인" 뒤 대기 화면으로 → **폰에서 순위를 본다.**

순위와 상금은 사람에게 붙는 정보이고 폰이 이미 들고 있다. 좌석에 고정된
태블릿은 다음 사람이 앉을 자리라서 비워야 한다.

---

### 장면 5 — 테이블을 합친다

| | |
|---|---|
| 화면 | 콘솔 · 좌석 태블릿 |
| 산출 | 움짤 |
| 보이는 정합 | **칩이 좌석보다 오래 산다.** 옮겨 앉아도 스택이 그대로다 |
| 짝 | `table-move.int-spec.ts` |

인원이 줄어서 테이블을 합친다 — 장면 4에서 사람이 죽었기 때문에 이 장면이
생긴다. 억지로 붙이는 것이 아니라 대회가 실제로 그렇게 흘러간다.

콘솔에서 **2번 테이블 좌석을 해제한다** → 사람이 1번 테이블로 걸어가
**참가 OTP를 다시 넣는다** → 원래 칩 그대로 앉는다 → 빈 2번 테이블을 닫는다.

**휴식을 기다리지 않는다.** `releaseSeats`는 `GamePhase.WAITING`을 요구하는데
(T29), 핸드가 정산되면 테이블이 자연히 그 상태로 돌아온다
(`allin-sidepot` 8번). e2e README가 이 장면을 휴식(lv 99) 자리에 적어 둔 것은
운영 흐름 기준이고, 촬영에서는 다음 핸드를 시작하지 않으면 된다 —
블라인드 레벨당 3분을 기다릴 이유가 없다.

## 6. 촬영 — 실측과 하네스

### 자원 (실측)

8GB / Ryzen 7 2700X. Docker(Postgres+Redis) · Next dev · NestJS가 이미 물고
있는 상태에서 녹화 컨텍스트 8개를 동시에 열어 재 봤다.

```
시작        chromium 0.96GB · 여유 1.72GB
8개 열림    chromium 1.96GB · 여유 0.93GB
정리 후     chromium 1.27GB · 여유 1.63GB
컨텍스트당 ≈ 131MB
```

`browser.newContext()`는 브라우저를 새로 띄우는 것이 아니라 쿠키가 격리된
세션만 하나 더 만드는 것이라, 크롬 창을 여러 개 띄우는 것(창당 300~500MB)보다
훨씬 싸다. CPU는 여유가 있다.

**다만 여유 RAM이 0.89GB까지 떨어졌다.** 스왑이 시작되면 페인트가 밀려
영상이 끊긴다. 실무적으로:

- 촬영 전에 다른 프로그램을 닫는다
- **한 장면에 4면을 넘기지 않는다.** 장면 2가 최대(4면)이고 나머지는 2~3면이다
- 전광판을 1280×720으로 찍는 이유이기도 하다

### 하네스에 필요한 변경

**`slowMo`.** 지금 영상은 클릭이 즉시 끝나 무슨 일이 일어났는지 안 보인다.
촬영 프로젝트에만 건다.

**커서.** Playwright는 커서를 그리지 않는다(클릭이 영상에 안 보인다).
`addInitScript`로 촬영할 때만 꽂는다 — **제품 코드에 넣지 않는다.**

**`fixtures/backstage.ts`에 헬퍼 둘.** 지금은 `login` 하나뿐이다.

- 좌석 예약 — 장면 2의 좌석 태블릿 둘 말고 나머지는 API로 앉힌다
- 스냅샷 스택 조정 — §4

경계는 기존 규칙 그대로: 대회 시작 · 딜러 입장 · 액션 · 승자 결정 · 좌석
해제는 **화면으로**, 배경 착석과 스택 세팅은 **API로**.

**Playwright projects 둘.** 데모 스펙은 대회를 시작하므로 `harness.spec.ts`의
"무대는 아직 PENDING" 단언보다 뒤여야 한다. 파일 이름 알파벳순은 우연히 맞은
것이고 다섯 번째부터 이름을 억지로 짓게 된다.

```ts
projects: [
  { name: 'regression', testMatch: /e2e\/(console|dealer|harness|terminal)\.spec\.ts/ },
  { name: 'demo', testMatch: /e2e\/demo\/.*\.spec\.ts/, dependencies: ['regression'] },
]
```

### Playwright가 못 하는 것

webp·gif·mp4 인코딩, 영상 합성, 커서 렌더링, 영상 fps 제어와 구간 자르기.
전부 ffmpeg 또는 주입으로 해결한다.

`page.clock`으로 **블라인드를 올릴 수 없다.** 레벨을 미는 것은 서버
(`checkAndSyncBlindLevel`)이고 브라우저 시계를 속여도 서버 시각은 그대로다.
데모에 블라인드 상승은 넣지 않는다.

### 규격

| | 값 | 근거 |
|---|---|---|
| 움짤 형식 | **애니메이션 WebP** | GitHub README의 `<img>`에서 자동재생된다. WebM은 상대경로 raw 파일로 재생되지 않는다. GIF 대비 0.15~0.3배 |
| 프레임 | 12fps | Playwright webm은 fps가 등간격이 아니다. ffmpeg에서 고정한다 |
| 타일 | 960×540 | 면이 다 16:9라 레터박스가 없다 |
| 용량 | 장면당 ≤ 2MB | 다섯 개가 한 README에 붙는다 |
| 스크린샷 | PNG · `deviceScaleFactor: 2` · `animations: 'disabled'` · `caret: 'hide'` | Playwright는 PNG/JPEG만 낸다 |

ffmpeg가 **설치돼 있지 않다** (`winget install Gyan.FFmpeg`).

```bash
# 2×2 (장면 2)
ffmpeg -i seat1.webm -i seat2.webm -i dealer.webm -i board.webm \
  -filter_complex "[0]scale=960:540[a];[1]scale=960:540[b];\
    [2]scale=960:540[c];[3]scale=960:540[d];\
    [a][b]hstack[t];[c][d]hstack[u];[t][u]vstack,fps=12" \
  -loop 0 -q:v 55 docs/assets/s2-hand.webp
```

  진행 상황을 모른다. 여기서는 `docs/assets/`에 **V2 자산을 새로 쌓는
  것까지**만 한다. (`aboutMe`에 지금 걸린 `playsync.png`는 V1 것이다)

## 10. 순서

```
0. ffmpeg 설치
1. B0 좌석 태블릿 에러 원인
2. B1 전광판 내비 (display → (board))
```

1~3은 카메라 앞 화면의 결함이라 촬영보다 먼저다. 4~5가 실제 크기이고,
6~7은 기계적이다.
