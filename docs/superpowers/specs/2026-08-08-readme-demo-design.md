**항목**: 백로그 (T34 후속). 선행은 T33(촬영 하네스) · T34(화면 구현)다.
**상태**: 초안. 승인 전.

README는 563줄인데 **이미지가 0장**이다. 이 문서는 그 그림을 무엇으로,
어디서, 어떻게 뽑는지를 정한다. README의 글 구조는 건드리지 않는다.

## 4. 산출물

```
docs/assets/
  demo.webp              2×2 동시성 (1920×1080)
  phone-otp.webp         폰 OTP 조회 → 태블릿 입력 (390×844)
  console.png            화면 1
  seat-waiting.png       화면 2
  seat-game.png          화면 3
  dealer-felt.png        화면 4
  dealer-winner.png      화면 5
  scoreboard.png         화면 6
  phone-me.png           화면 7
```

`frontend/e2e/recordings/`(webm 원본)와 `frontend/e2e/.shots/`(중간 산출물)는
`.gitignore`다. 리포에 남는 것은 `docs/assets/`뿐이다.

### 규격

| | 값 | 근거 |
|---|---|---|
| 움짤 형식 | **애니메이션 WebP** | GitHub README의 `<img>`에서 자동재생된다. WebM은 상대경로 raw 파일로 재생되지 않는다. GIF 대비 0.15~0.3배 |
| 프레임 | 12fps | Playwright webm은 fps가 등간격이 아니다. ffmpeg에서 고정한다 |
| 타일 | 960×540 ×4 = 1920×1080 | 면마다 뷰포트가 다르다. `scale`+`pad`로 맞춘다. 늘리지 않는다 |
| 용량 | `demo.webp` ≤ 3MB | README 상단이 그보다 크면 모바일에서 안 뜬다 |
| 스크린샷 | PNG · `deviceScaleFactor: 2` · `animations: 'disabled'` · `caret: 'hide'` | Playwright는 PNG/JPEG만 낸다 |

ffmpeg가 **설치돼 있지 않다** (`winget install Gyan.FFmpeg`).

```bash
ffmpeg -i console.webm -i scoreboard.webm -i dealer.webm -i seat.webm \
  -filter_complex "\
    [0]scale=960:540:force_original_aspect_ratio=decrease,pad=960:540:-1:-1[a];\
    [1]scale=960:540:force_original_aspect_ratio=decrease,pad=960:540:-1:-1[b];\
    [2]scale=960:540:force_original_aspect_ratio=decrease,pad=960:540:-1:-1[c];\
    [3]scale=960:540:force_original_aspect_ratio=decrease,pad=960:540:-1:-1[d];\
    [a][b]hstack[t];[c][d]hstack[u];[t][u]vstack,fps=12" \
  -loop 0 -q:v 55 docs/assets/demo.webp
```

## 5. 촬영

### 시나리오 — 동시성 한 장면

한 클릭이 여러 면을 동시에 바꾸는 것을 한 화면에서 본다.

| 타일 | 면 |
|---|---|
| 좌상 | 콘솔 |
| 우상 | 전광판 |
| 좌하 | 딜러 태블릿 |
| 우하 | 좌석 태블릿 |

1. 콘솔에서 **대회 시작** → 전광판이 `대기 중`에서 블라인드 시계로 바뀐다
2. 딜러가 **프리플랍 시작** → 두 펠트에 블라인드가 깔린다
3. 딜러가 **액션을 받는다** → 좌석 태블릿의 차례·스택과 전광판의 평균 스택이 같이 움직인다
4. 딜러가 **승자를 결정** → 팟이 승자에게 간다

**면 넷을 한 테스트 안에서 처음에 다 열고 끝까지 유지한다.** 지금 스펙들은
면마다 테스트가 달라 타임라인이 안 맞는다 — 합성하려면 t=0이 같아야 한다.
`stage`는 이미 여러 번 호출할 수 있다(쓰는 스펙이 없을 뿐).

폰은 별도로 짧게: OTP 조회 → (컷) → 좌석 태블릿 키패드에 같은 숫자가 들어간다.

### 하네스에 필요한 변경

**`slowMo`.** 지금 영상은 클릭이 즉시 끝나 무슨 일이 일어났는지 안 보인다.
촬영 프로젝트에만 건다.

**커서.** Playwright는 커서를 그리지 않는다. `addInitScript`로 촬영할 때만
꽂는다 — **제품 코드에 넣지 않는다.**

**`fixtures/backstage.ts`에 좌석 헬퍼.** 지금은 `login` 하나뿐이다.
핸드를 돌리려면 최소 둘이 앉아야 하는데 `terminal.spec.ts`는 하나만 앉힌다.

경계는 기존 규칙 그대로 — 대회 시작·딜러 입장·액션·승자 결정은 **화면으로**,
player2~5 착석은 **API로**.

**Playwright projects 둘.** 데모 스펙은 대회를 시작하므로 `harness.spec.ts`의
"무대는 아직 PENDING" 단언보다 뒤여야 한다. 파일 이름 알파벳순은 우연히 맞은
것이고 다섯 번째부터 이름을 억지로 짓게 된다.

```ts
projects: [
  { name: 'regression', testMatch: /e2e\/(console|dealer|harness|terminal)\.spec\.ts/ },
  { name: 'demo', testMatch: /e2e\/demo\/.*\.spec\.ts/, dependencies: ['regression'] },
]
```

### 시드

영상 안에서 블라인드가 오르는 것을 보여주려면 **시드의 레벨 길이를 줄여야
한다.** `page.clock`으로는 안 된다 — 레벨을 미는 것은 서버
(`checkAndSyncBlindLevel`)이고 브라우저 시계를 속여도 서버 시각은 그대로다.

지금 시드는 레벨당 3분이다. 촬영용 시드가 따로 필요한지, 아니면 데모에서
블라인드 상승을 빼는지는 **미정** — §7.

## 7. 하지 않는 것 · 미정

**하지 않는다**

- README 글 구조 개편
- 콘솔 `/stores`·`/admin` 라우트 신설 — 링크를 지운다
- 태블릿 세로 레이아웃 재설계 — 죽은 공간이 있지만 팔 길이에서 읽히는지는
  화면만 보고 판정할 수 없다
- 장면 6~7(탈락 · 휴식 · 테이블 합치기) — 별도 티켓
- 다크 테마 — Carbon Gray-100은 별도 팔레트고 토큰에 없다

**미정 — 착수 전에 정해야 한다**

- 촬영용 시드(짧은 블라인드 레벨)를 따로 둘 것인가, 데모에서 블라인드 상승을
  뺄 것인가
- `aboutMe`에 어떻게 싣는가. **이 문서 범위 밖이다** — 그 리포의 구조와
  진행 상황을 모른다. 여기서는 `docs/assets/`에 **V2 자산을 새로 쌓는
  것까지**만 한다

## 8. 순서

```
0. ffmpeg 설치
1. B0 좌석 태블릿 에러 원인
2. B1 전광판 내비 (display → (board))
3. B2 UUID · B3·B4 콘솔 Carbon
4. backstage 좌석 헬퍼 · projects 둘 · slowMo · 커서
5. 데모 스펙 (동시성 · 폰)
6. 촬영 → ffmpeg → docs/assets/
7. README 편집 + 낡은 숫자
```

1~3은 카메라 앞 화면의 결함이라 촬영보다 먼저다. 4~5가 실제 크기이고,
6~7은 기계적이다.
