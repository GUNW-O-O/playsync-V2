# 램프 설계 — 동시접속을 어디까지 받고, 몰림을 어디까지 견디나

**날짜**: 2026-08-15
**전신**: [`2026-08-09-load-test-design.md`](./2026-08-09-load-test-design.md)의 "램프와 도착 프로필",
`docs/handoff.md`의 "T41에서 정해야 할 것 셋"
**상태**: 설계 완료. 구현이 T41

---

## 앞선 설계에서 무엇이 바뀌었나

원 설계의 램프는 **계단**이었다. 단계마다 규모를 세우고, 재고, 다음 단계로 간다.
착수 시점에 질문이 한 겹 더 구체화되면서 그 모양을 바꿨다.

> 동시접속을 어디까지 커버할 수 있는가, 그리고 동시접속자가 많을 때
> 피크 부하를 어디까지 견디는가.

**두 질문은 같은 실행 안의 서로 다른 구간이 답한다.** 그래서 램프를 성장형으로
바꾸고 구간에 태그를 갈랐다.

| | 원 설계 | 이 문서 |
|---|---|---|
| 램프 모양 | 단계마다 세우고 잰다 | **한 번 붙은 테이블은 끝까지 돈다.** 계속 붙인다 |
| 인원 | 자연 감소 | **무한 리바인.** 탈락자가 즉시 다시 앉는다 |
| 봇 액션 | 콜만 | 체크·콜 65 / 레이즈 20 / 폴드 15 |
| 중단 | 서버 lag 붕괴선 | 서버 lag **또는 사용자 불만선(내 액션 p95 1초)** |
| 램프 A·B | 시나리오 둘 | 파일 하나 + `LOAD_TABLES_PER_STORE` |

원 설계의 판단 중 살아남는 것: 배수가 아니라 등차로 늘린다, VU 하나가 테이블
하나를 든다, 정상 운영을 기준선으로 앞에 깐다, 붕괴선은 바닥값을 뺀 lag이다.

## 성장 램프 — 아무도 내려가지 않는다

k6 `ramping-vus`로 VU(= 테이블)를 등차로 늘리고 **`gracefulRampDown` 구간을
두지 않는다.** 새 VU가 하는 일이 곧 증설이다.

```
새 VU  →  POST /store/sessions/:id/tables   테이블을 연다 (상점 콘솔 경로)
       →  좌석 9개를 제품 경로로 채운다      로그인 bcrypt가 여기서 몰린다
       →  소켓 10개를 열고 게임에 합류        착석마다 SEAT_LIST_UPDATED
이미 도는 테이블  →  계속 핸드를 돈다
```

누적이라야 소켓 수가 실제로 쌓인다. 단계마다 세우고 다시 시작하면 재는 것이
"N테이블의 부하"가 아니라 "N테이블을 새로 세우는 비용"이 된다.

### 구간을 둘로 가른다

```
grow-N     N개로 늘리는 중      ← 피크 내성. 로그인 bcrypt + 착석 O(T²)가 몰린다
steady-N   고원 (기본 3분)      ← 동시접속 상한의 근거. 정상 운영이다
```

**둘을 같은 태그로 뭉치면 답이 갈리지 않는다.** "40테이블에서 터졌다"가 게임
부하 때문인지 그 순간 몰린 입장 때문인지 구분되지 않는다. 모니터가 이미 `step`
태그를 붙이므로(`load/lib/monitor.js`) 라벨만 갈라 주면 원시 시계열에서 분리된다.

원 설계의 **도착 프로필 셋이 이 구조 안에 흡수된다.** 별도 실행이 아니다.

| 프로필 | 어디에 있나 |
|---|---|
| 현실 등록 | `grow-N` 구간이 곧 그것이다. 착석·리바인이 이미 도는 게임 위에 겹친다 |
| 정상 운영 | `steady-N` 구간. 첫 고원이 기준선이 되고 나머지를 거기서 뺀다 |
| 재접속 폭발 | 고원 하나를 골라 소켓 전부를 닫고 다시 연다. 티켓 `GETDEL` 포함 |

고원을 3분으로 두는 근거는 핸드 주기다. 기본 생각 시간에서 핸드 하나가 약 2분
이라, 그보다 짧으면 **핸드 사이 딜링 25초만 잡고 끝나는 단계**가 생겨 그 단계의
부하가 실제보다 작게 나온다.

### 램프 A와 B는 파라미터 하나로 갈린다

| | `LOAD_TABLES_PER_STORE` | 무엇을 늘리나 | 답하는 질문 |
|---|---|---|---|
| B | 미설정 | 대회 하나 안에서 테이블 | Q2 — 대회 정원, `SEAT_LIST_UPDATED`의 O(T²) |
| A | `6` | 6테이블마다 새 대회 | Q1 — 한 인스턴스에 홀덤펍 몇 곳 |

**이 값이 "몇 상점"의 전제다.** 설계 문서는 홀덤펍을 4~8테이블로 잡았는데 구현이
6을 박고 있었다. 4로 재면 정원이 크게 나오고 8이면 작게 나오므로, 결과 문서에
값을 같이 적지 않으면 숫자가 혼자 돌아다닌다.

시나리오를 둘로 나누지 않는 이유: 봇·지표·중단 판정·태그가 전부 같고 다른 것은
"새 테이블을 어느 대회에 붙이나" 한 줄이다. 파일을 나누면 그 한 줄을 위해 나머지
전부가 복제되고, 한쪽만 고치는 날이 온다.

## 무한 리바인 — 인원이 줄지 않게

### 지금 봇은 아무도 터지지 않는다

딜러 봇이 폴드하지 않은 **전원**을 한 그룹으로 넣는다(보드 하이). 그러면 팟이
낸 만큼 되돌아오고, 좌석 봇이 콜만 하니 스택이 갈리지도 않는다. 결과로
`resolveWinners`의 리바인 분기(`dealer.service.ts:309`)가 **한 번도 실행되지
않는다** — 탈락자가 없기 때문이다.

즉 지금 하네스는 부하의 한 갈래(리바인 · 탈락 · 사이드팟)를 통째로 비워 두고
있다. 램프가 길어질수록 이 공백이 커진다.

### 바꾸는 것 둘

**딜러 봇이 승자를 무작위 한 명으로 고른다.** 승자는 계산되는 값이 아니라 딜러가
입력하는 값이다(이 리포의 전제 — 카드는 물리다). 봇이 카드를 못 봐도 이 경로는
정당하고, 실물 딜러가 하는 일과 형태가 같다. 칩이 한 명에게 쏠려 탈락자가 나온다.

**좌석 봇이 `REBUY_PROMPT`에 즉시 수락한다.** `{ accept: true }`를
`REBUY_RESPONSE`로 보낸다(`ws.gateway.ts:324`, `RebuyResponseSchema`). 좌석이
비지 않으므로 램프의 규모 축이 흔들리지 않는다.

### 얻는 것과 대가

| 얻는 것 | |
|---|---|
| 인원 유지 | 램프가 길어져도 테이블이 비지 않는다 |
| 리바인 경로 | 락 밖 응답 대기 → DB 트랜잭션 → 프라이즈풀 갱신 → 브로드캐스트 |
| 올인·사이드팟 | 짧은 스택이 실제로 생겨 최악 장부 경로가 돈다 |

대가는 핸드 주기다. `processRebuy`가 락 **밖**에서 최대 15초(`REBUY_TIMEOUT_MS`)
사람 입력을 기다리고, 그동안 `HAND_END`가 다음 핸드를 막는다
(`dealer.service.ts:275-278`). 봇이 즉시 답해도 왕복이 끼므로 테이블당 핸드 주기가
늘어난다 — **실제 대회도 그렇다.** 부하가 작아지는 방향이지만 그것이 실제 모양이다.

리바인이 성립하려면 `isRegistrationOpen`이 참이어야 한다(`:309`). 부하 시드가
`rebuyUntil: 600`(분)에 블라인드를 한 레벨만 두므로 램프 실행 시간 안에서는 자동
마감이 오지 않는다.

## 액션 믹스

지금은 콜만 한다. 합법 액션 중에서 뽑도록 바꾼다.

| | 비율 | 왜 이 액션이 필요한가 |
|---|---|---|
| 체크 / 콜 | 65% | 기본. 핸드가 끝까지 가야 플랍·턴·리버·쇼다운이 전부 돈다 |
| 레이즈 | 20% | **`resetChecked()`가 돌아 라운드가 한 바퀴 더 간다**(`table-engine.ts:333`). 액션 수가 늘고 fan-out이 그만큼 곱해진다 |
| 폴드 | 15% | 폴드가 없으면 사이드팟이 안 생기고 팟이 늘 전원 분배다 |

**레이즈 금액은 목표 총 베팅액이다.** `handleRaise`가 보는 것은
`betAmount > currentBet` 하나뿐이고 최소 레이즈 규칙이 없다
(`table-engine.ts:321`). 봇은 `currentBet + BB × {1,2,3}`으로 뽑는다. 스택을
넘으면 `executeBet`이 잘라 올인이 되고, 그 자리가 사이드팟을 만든다 — 일부러
막지 않는다.

**비율은 합법 액션 안에서 정규화한다.** `currentBet > me.bet`이면 체크가 불법이라
(`table-engine.ts:55`) 콜로 접고, 스택이 `currentBet`에 못 미치면 레이즈를 뺀다.
불법 액션은 서버가 던지지만, 그 거절이 부하에 섞이면 재는 것이 게임이 아니라
에러 경로가 된다.

원 설계가 "콜만 한다"고 정한 근거(레이즈를 섞으면 스택이 갈려 테이블이 빈다)는
리바인이 인원을 유지하면서 사라진다.

## 중단 — 사람이 "이거 왜 이래"라고 말하는 지점

근거가 둘이다. HCI 응답 한계(Miller 1968 / Nielsen 1993)와 **이 도메인의 턴
타이머**.

| 선 | 내 액션 p95 | 사람이 느끼는 것 |
|---|---|---|
| 합격 | 200ms | 즉각. 직접 조작감이 산다 |
| **불편** | **1초** | **"이거 왜 이래."** 흐름은 유지되지만 지연을 인지한다 |
| 실패 | 3초 | 누르고도 안 먹은 것처럼 보여 **다시 누른다**. 중복 액션이 서버에 또 얹힌다 |

일반 웹보다 임계를 낮게 잡는 이유가 도메인에 있다. 서버 턴 타이머가 30초라
지연이 커지면 증상이 "느리다"가 아니라 **폴드당한다**로 바뀐다. 돈이 걸린 실패다.

**중단은 먼저 닿는 것으로 한다.**

| 판정자 | 조건 |
|---|---|
| 테이블 VU | 자기 최근 30건 창의 내 액션 p95 > 1000ms, **연속 2회** |
| 모니터 VU | 바닥값 뺀 서버 lag p95 > 100ms, **연속 2회** |

연속 2회인 이유는 한 번 튄 것과 무너지는 것을 가르려는 것이다. 판정한 VU가
`k6/execution`의 `test.abort()`를 부른다 — k6는 VU 간 상태를 공유하지 않으므로
**각자 자기가 본 것으로 멈춘다.** 서버 lag은 모니터만 보고, 클라이언트 지연은
테이블 VU만 본다.

**k6 `thresholds`로는 이 판정을 할 수 없다.** 임계값이 실행 전체 누적으로
평가되므로, 성장 램프에서는 앞 단계의 좋은 표본이 뒤 단계의 나쁜 표본을 희석한다.
`thresholds`는 합격/불합격 기록용으로 남기고, 중단은 롤링 창으로 한다.

## 계정 풀 — 있는 것부터 쓴다

시드 기본값 600을 그대로 쓴다. **66테이블(594명)이 상한**이고, 거기까지 통과하면
풀을 늘려 재실행한다.

**풀보다 커지면 조용히 전부 신규 가입으로 넘어간다**(`table.js:176`의
`index >= accountPool`). 그러면 bcrypt가 사람당 두 번(`hash` + `compare`) 돌아
실제의 두 배가 되고 정원이 낮게 나온다. 결과의 `signups` / `logins` 카운터로
매번 확인한다 — 비율이 `LOAD_NEW_USER_RATIO`(0.1)에서 멀어져 있으면 풀이 모자란
것이다.

램프 A에서 대회가 여럿이어도 계정을 재사용하지 않는다. `@@unique([tournamentId,
userId])`라 기술적으로는 가능하지만, 한 사람이 두 홀덤펍에 동시에 앉아 있는 것은
도메인에 없는 모양이다.

## 착수 전에 고치는 것 하나

**`createSession`이 첫 테이블에 빈 스냅샷을 세우지 않는다.**
`session.service.ts:181`이 `setSeatBitmap`만 부른다. `createTable`은 T38 이후
둘 다 부른다(`:220`, `:235`).

T38이 세운 불변식은 "테이블이 있으면 스냅샷이 있다"이고, 그래야 "스냅샷이 없다"의
뜻이 **유실 하나로** 좁아진다. 대회 생성 경로가 그 불변식을 어기고 있다 — T40이
데모 시드에서 찾은 것과 같은 모양이고(`seed.ts`가 `prisma.table.create`를 직접
불렀다), 이번 것은 **제품 경로**다.

증상은 딜러가 먼저 붙는 실제 순서에서 나온다. `GET /playsync/:tableId`가 500이고
(`playsync.service.ts:41`), WS는 `data: null`을 조용히 보내 화면이 빈 펠트로 선다.
착석이 `createEmptyTableState`로 덮어 주므로(`entry.service.ts:267`) 손님이 먼저
앉으면 드러나지 않는다.

램프 A가 대회를 만들 때마다 이 자리를 밟으므로 착수 전에 닫는다. 트랜잭션 뒤
`setSeatBitmap` 옆에 `saveSnapShot(..., createEmptyTableState(...))` 한 줄이다.

## 램프 중에 터진 것을 어떻게 다루나

램프는 제품을 처음으로 진짜 동시성 아래 두는 자리다. 실행 중 결함이 나오면
갈래를 둘로 나눈다.

| | 어떻게 |
|---|---|
| 장부 · 락 · 트랜잭션 경계 | **우선 고치고 진행한다.** 하네스를 완주하는 것보다 장부가 먼저다 |
| 나머지 | 티켓으로 적고 램프를 계속 돌린다 |

이미 알고 있는 후보 둘.

- **테이블 생성 동시 409.** `insertTable`이 트랜잭션 안에서 `tableOrder` 최댓값을
  뽑고 최종 방어가 `@@unique([tournamentId, tableOrder])`다. 여러 VU가 같은 순간에
  열면 진 쪽이 409를 받는다. 봇이 짧은 지터로 재시도하고, **409 횟수 자체를 지표로
  남긴다** — 상점 콘솔의 버튼 하나로는 안 보이는 값이다.
- **T42(레이스 컨디션 전수조사).** 스냅샷을 고치는 열한 경로가 "락 안에서 다시
  읽는다"를 각자 손으로 지킨다. 램프가 그 창을 실제로 열면 T42를 앞으로 당긴다.

## 산출물

| | |
|---|---|
| 램프 A 곡선 | 상점 수 대 lag · 지연. 한 인스턴스에 홀덤펍 몇 곳(Q1) |
| 램프 B 곡선 | 테이블 수 대 lag · 지연. 대회 정원(Q2)과 O(T²)의 실측 |
| 두 선의 위치 | 불편선(내 액션 1초)과 붕괴선(lag 100ms) 중 어느 쪽이 먼저 오는가 |
| 확장 순서의 현재 위치 | 원 설계의 1~4 중 어디까지 왔는지 |

`load/results/`에 단계별 요약이 쌓이고, 결과 문서가 그것을 읽어 곡선으로 만든다.

## 범위 밖

- **병목 수정.** `Buffer` 인코딩 1회화, 델타 전송, `SEAT_LIST_UPDATED` 범위 좁히기.
  측정이 먼저다 — 안 그러면 무엇을 얼마나 고쳤는지 증명할 기준선이 없다.
- **재접속 폭발 프로필을 별도 실행으로.** 성장 램프 안에서 한 단계로 넣는다
  (고원 중에 소켓 전부를 닫고 다시 연다). 별도 실행으로 두면 규모 축이 하나 더
  생기고 실행 시간만 배가 된다.
- **풀을 키운 재실행.** 66테이블을 통과한 뒤에 판단한다.

## 버린 선택지

**계단 램프(원 설계).** 단계마다 세우고 재고 내린다. 재현성은 높지만 재는 것이
"N테이블의 부하"가 아니라 "N테이블을 세우는 비용"이 된다. 동시접속 상한을 묻는
질문에 누적이 없는 답이다.

**리바인 없이 자연 감소.** 봇을 그대로 두면 탈락이 없어 인원이 유지되기는 한다.
대신 리바인 · 탈락 · 사이드팟 경로가 통째로 빠지고, 램프가 길어질수록 그 공백이
커진다.

**승자를 무작위 절반으로.** 칩이 천천히 갈려 탈락이 드물다. 리바인 경로가 돌기는
하지만 빈도가 낮아 부하에서 차지하는 비중이 작다.

**액션 믹스에 올인을 따로 두기.** 레이즈 금액이 스택을 넘으면 `executeBet`이
이미 올인으로 만든다. 별도 액션으로 두면 같은 경로에 입구가 둘이 된다.

**중단을 k6 `thresholds`의 `abortOnFail`로.** 임계값이 실행 전체 누적이라 성장
램프에서 앞 단계가 뒤 단계를 희석한다. 원 설계가 이 방법을 적어 뒀는데, 계단
램프(단계마다 실행이 갈림)를 전제한 것이었다.

**램프 A·B를 파일 둘로.** 다른 것이 "새 테이블을 어느 대회에 붙이나" 한 줄뿐이라,
나누면 나머지 전부가 복제되고 한쪽만 고치는 날이 온다.
