# T100 — Redis 장애가 리바인 창에 끼면 돈이 빠지거나 장애 때문에 탈락한다

**티켓**: `tickets-recovery.md`의 T100(이 PR이 대장에 올린다). T97 최종 리뷰가 잔여로
남긴 「장애 중 리바인 창」이 출발점인데, 코드를 따라가 보니 **탈락보다 돈이 먼저다.**
**의존**: T95(`resumePending` · 「이어서 진행」) · T96(`SYNCING` n/n) · T97(`RedisService.outage`).

## 무엇이 깨졌나

리바인은 `DealerService.resolveWinners` 2단계다. 파산자 전원에게 15초짜리 팝업을 띄우고
(`PlaysyncService.processRebuy` → `waitForRebuyResponse`), 수락하면 반영한다. 이 구간은 락
밖이고, T97의 장애 가드를 하나도 지나지 않는다.

**장애 중에 「리바인」을 누르면** (코드를 따라간 경로. 실측 아님)

1. `REBUY_RESPONSE`는 게이트웨이 가드가 없다. `RebuyOverlay`는 화면 전체를 덮어 장애 배너를
   가리고, 버튼도 막히지 않는다
2. `executeRebuyTransaction`의 DB 트랜잭션이 **커밋된다** — 포인트 차감 · `totalBuyinAmount` ·
   참가 행 `currentStack += startStack`
3. 커밋 뒤 `redis.rebuyPlayer`가 던진다 → `processRebuy`가 「트랜잭션 실패」로 기록하고 **0을
   돌려준다.** 스냅샷 스택은 0 그대로다
4. `finally`의 `markRebuyPending(null)`도 Redis라 던진다 → `resolveWinners`가 예외로 끝나고
   탈락 확정(3단계)이 안 돈다. 테이블은 `HAND_END`에 남는다
5. 복구 뒤 딜러가 「저장 재시도」를 누르면 `checkpointTableToDb`가 참가 행 `currentStack`을
   **스냅샷 값 0으로 덮는다**

→ **포인트는 빠졌고, 칩은 0이고, 탈락도 안 된 좌석.**

**장애 중에 아무도 안 누르면** 서버 타이머(프로세스 메모리)가 계속 흘러 거절로 처리되고,
Redis가 돌아온 뒤 3단계가 그 사람을 탈락시킨다. 화면이 「기다리라」고 하는 동안 서버는
탈락을 결정한다.

## 결정

**장애가 낀 리바인은 아무것도 결정하지 않고, 딜러가 판을 다시 열 때 새로 묻는다.**
T97의 「짧은 부팅」과 같은 원칙이다 — 장애 동안 확정하지 않고, 판을 다시 여는 순간은
테이블을 보는 딜러가 정한다.

```
리바인 창 (15초)
  ├ Redis down → 떠 있는 프롬프트 전부 즉시 「중단」 (마감을 기다리지 않는다)
  │   · 수락이 락 안에서 장애 세대에 걸려도 「중단」 — 스냅샷도 DB도 쓰지 않는다
  ├ Redis 복구 → 테이블에 resumePending{downMs}, rebuyPending은 지운다
  │   · 좌석: 「딜러가 판을 다시 열기를 기다리는 중」 (T95 배너 그대로)
  │   · 딜러: 정지 배너 + k/n, 「이어서 진행」은 n/n 전까지 잠김 (T96 그대로)
  └ 딜러 「이어서 진행」 → 「중단」이었던 사람에게 새 15초로 다시 묻는다
      · 그 판에 또 장애가 끼면 같은 고리를 한 번 더 돈다
```

### 기각한 것

| 안 | 왜 버렸나 |
|---|---|
| 알림만 한다(모든 소켓에 장애 방송) | **이미 한다**(T97 `serverOutage`). 알림은 사람을 기다리게 할 뿐, 서버가 내리는 결정(타이머 만료 = 거절, 수락 = DB 먼저 커밋)을 막지 않는다. 이미 보낸 수락은 화면으로 못 막는다 |
| 복구 즉시 새 15초로 다시 묻는다 | 복구가 얼마나 걸릴지 모르는 동안 자리를 비운 사람이 있다. 다 돌아왔는지는 k/n을 보는 딜러가 확인한다 |
| 장애 시간만큼 마감을 민다 | T97이 턴에 대해 기각한 이유와 같다 — 장애 동안 말이 없다가 시간이 갑자기 생긴다. 게다가 자리를 비운 사람은 여전히 못 돌아온다 |
| 장애가 끼면 리바인 없이 탈락 | 장애 때문에 사람이 탈락한다 — 막으려는 결함 그 자체다 |
| DB 먼저 쓰고, 칩은 복구를 기다렸다 넣는다 | 커밋된 리바인을 메모리에 들고 기다려야 한다. 그 사이 프로세스가 죽으면 **참가자가 돈을 잃는다** |
| DB를 먼저 쓰고, Redis가 실패하면 환불한다 | 보상 트랜잭션(환불 거래 종류)이 새로 생기고 장부에 리바인 → 환불 두 줄이 남는다 |

## 1. 쓰는 순서 — 스냅샷 → DB → 전광판

**장애 중에는 첫 Redis 쓰기가 먼저 실패해 돈이 움직이기 전에 멈춘다.** 그래서 순서를 바꾼다.
다만 **전부를 앞으로 옮기지 않는다** — `rebuyPlayer`의 `hincrby`는 없는 키를 만들어서, 닫힌
대회에 먼저 쓰면 지워진 `tournament:{id}:info`가 TTL 없는 쓰레기로 부활한다(`domain.md`
「Redis 쓰기는 트랜잭션 뒤로 보낸다」).

| 순서 | 무엇 | 실패하면 |
|---|---|---|
| 1 | **스냅샷에 칩** — `mutateSnapshot` 안에서 들어올 때 잡은 장애 세대 `g`와 `isUp()`을 다시 본다 | 어긋나면 쓰지 않고 「중단」. 스냅샷이 없거나 그 사람이 없으면(대회가 닫힘 · 좌석 해제) 쓰지 않고 끝 |
| 2 | **DB 트랜잭션** — 지금의 `executeRebuyTransaction`에서 `rebuyPlayer`를 뺀 것 | 거절(포인트 경합 · 닫힌 대회 · 중단된 대회)이면 락 안에서 **칩을 되돌린다** |
| 3 | **전광판 표시** — `rebuyPlayer` (파생값) | 로그만. 돈과 칩은 이미 맞다 |
| 4 | **전파** — `game.state.updated` | 2가 커밋된 뒤. 되돌렸으면 되돌린 상태를 보낸다 |

**1과 2 사이에 칩이 스냅샷에 있다.** 테이블이 `HAND_END`라 그 칩으로 판이 돌 수 없고
(`startPreFlop`은 `WAITING`만 받는다), 체크포인트(4단계)는 리바인 전원이 끝난 뒤에 돈다.
같은 테이블의 다른 리바인이 먼저 커밋해 전파하면 아직 커밋 전인 칩이 화면에 보일 수 있다 —
2가 거절되면 되돌린 상태를 다시 보내 바로잡는다.

**실패 방향이 뒤집힌다.** 지금의 이중 장애는 「돈은 빠졌는데 칩이 없다」(참가자 손해)이고,
바꾼 뒤의 이중 장애(DB 거절 직후 되돌리려는 순간 Redis까지 끊김)는 「칩은 있는데 돈이 안
빠졌다」다. 되돌리기 실패는 `error` 로그로 남긴다(범위 밖).

**보상 경로는 평소에도 돈다.** DB 거절은 드물지 않다 — 포인트 경합, 닫힌 대회, 중단된
대회. 다만 **기존 검사는 이 경로를 안 지난다.** `closed-tournament` A와 `abort-settlement` 8은
`executeRebuyTransaction`을 직접 불러 DB 거절만 본다(스냅샷도 이미 지워진 뒤다). 보상은 새
통합 검사가 든다(4절). `rebuyPlayer`가 트랜잭션 함수 밖으로 나가므로 A-2(지운 전광판 키가
되살아나지 않는다)는 저절로 초록이다 — **그 보장은 이제 `processRebuy`의 순서가 진다.**

## 2. 장애가 낀 판 — 딜러의 재개를 기다린다

**결과의 종류.** `processRebuy`가 금액 대신 결과를 돌려준다.

| 결과 | 뜻 | 다시 묻나 |
|---|---|---|
| 반영 | 1~2가 커밋 | 아니다 |
| 거절 | 게이트웨이가 up일 때 받은 명시적 거절 | 아니다 — 장애와 무관한 본인 의사 |
| 시간초과 | 장애 없이 마감이 지남 | 아니다 |
| 해당 없음 | 포인트 부족으로 묻지 않음 · DB 거절(되돌림) · 스냅샷 없음 | 아니다 |
| **중단** | 대기 중 `down` · 들어올 때 이미 up이 아님 · 1의 세대 가드 | **예** |

**`waitForRebuyResponse`가 `down`을 듣는다.** 발화하면 즉시 「중단」으로 끝낸다. 리스너는
응답 리스너와 같이 `settle`에서 뗀다(T97 리스너 수명과 같은 이유).

**`resolveWinners` 2단계가 고리가 된다.**

```
asked = 파산자 전원
loop:
  g = outage.generation
  markRebuyPending(asked)                  ← 새 마감
  결과 = Promise.all(asked.map(processRebuy(…, g)))
  중단이 없으면 break
  await outage.whenUp()
  스냅샷: rebuyPending 삭제, resumePending = { downMs: 지금 − 중단을 본 시각 } → 전파
  await 이 테이블의 재개
  asked = 결과가 중단인 사람
finally: markRebuyPending(null)
```

- **`RedisOutage.whenUp()`** — up이면 바로, 아니면 `recovered`에 풀리는 Promise. 한 줄짜리다
- **재개 신호** — `DealerService`가 `Map<tableId, 풀기>`를 든다. `resumeTable`이 성공하면 그
  테이블의 대기를 푼다. 생성자 시그니처는 바꾸지 않는다
- **`resumeTable`은 그대로다.** 차례가 없는 `HAND_END`에서 `scheduleTurnTimeout`은 세대만
  올리고 마감을 비운다
- **n/n 전에는 못 연다.** `runDealerAction`의 `SYNCING` 가드와 딜러 화면의 잠긴 버튼이 이미 있다
- **요청이 서로 막히지 않는다.** 딜러의 `RESOLVE_WINNERS`는 재개까지 걸려 있지만, Nest `ws`
  어댑터가 소켓의 메시지를 `mergeMap`으로 병렬 처리하므로 같은 소켓의 `RESUME_TABLE`이 들어온다
- **T97 스윕과 겹치지 않는다.** `planPause`는 차례 없는 테이블에 `null`이라 `HAND_END`에
  정지 표시를 달지 않는다. 이 고리가 스스로 단다

## 3. 게이트웨이와 화면

**게이트웨이** — `handleRebuyResponse` 맨 앞에 `!isUp()`이면 `SERVER_RECOVERING_MESSAGE`로
거절한다. `handlePlayerAction`의 가드와 같은 모양이다.

**좌석 (`SeatGameClient` · `RebuyOverlay`)**

- 오버레이가 `outage`와 `resumePending`을 받는다. 둘 중 하나면 두 버튼을 막고 카운트다운을
  숨긴다. 문구는 `outage`면 계약의 `SERVER_RECOVERING_MESSAGE`, `resumePending`이면 「딜러가
  판을 다시 열면 다시 묻습니다」
  - `resumePending` 동안에도 막는 이유: 복구 뒤 재개 전에 누르면 받을 대기가 이미 끝나 있어
    누른 것이 조용히 사라진다
- **`REBUY_PROMPT`가 오면 「거절로 탈락」 화면(`exitReason === 'eliminated'`)을 걷는다.**
  장애 알림 직전에 거절을 눌렀는데 서버가 이미 down이라 막았으면, 화면은 탈락을 그린 채
  재개 뒤 새 프롬프트를 받는다. 좌석 소멸로 난 진짜 탈락 뒤에는 프롬프트가 오지 않는다

**딜러** — 바꾸지 않는다. `rebuyPending` 띠가 지워지고 T95 정지 배너 · T96 k/n이 뜬다.

## 4. 테스트

| 계층 | 자리 | 무엇 | 반대 입력 |
|---|---|---|---|
| 시나리오 | `src/scenario/rebuy-outage.int-spec.ts` (신규) | 아래 단계, 단계마다 칩 총량과 포인트 | 장애 없는 판은 한 번만 묻는다 |
| 통합 | `playsync.service.int-spec.ts` | 쓰는 순서 — `processRebuy`에서 DB가 거절하면(포인트를 수락 직후 빼 둔다) 칩이 되돌아가고 마지막 전파에 칩이 없다. 스냅샷이 없으면(닫힌 대회) DB도 전광판 키도 안 건드린다 | 수락이 반영되면 칩 · 차감 · 전광판이 한 번씩. 기존 `closed-tournament` A · A-2 · `abort-settlement` 8이 그대로 초록 |
| 통합 | `ws.gateway.int-spec.ts` | down이면 `REBUY_RESPONSE` 즉시 거절 | up이면 이벤트가 흐른다 |
| 단위 | `outage.spec.ts` | `whenUp` | up이면 즉시 |
| 프론트 | `RebuyOverlay` · `SeatGameClient` | `outage`·`resumePending`이면 버튼 비활성 · 문구 · 카운트다운 숨김, 프롬프트가 거절 탈락 화면을 걷는다 | 둘 다 없으면 지금처럼 활성, 좌석 소멸 탈락은 프롬프트 없이 남는다 |

**시나리오 단계** — 실제 ioredis 클라이언트를 `disconnect()` · `connect()`로 끊고 붙인다(T97과 같다).

1. 판이 끝나 파산자 둘(A · B). 리바인 창이 열린다
2. B가 거절한다 — up이라 받는다
3. 끊는다 → A의 프롬프트가 즉시 「중단」. **포인트 그대로 · 스냅샷 스택 0 · 탈락 없음**
4. 붙인다 → `resumePending`이 서고 `rebuyPending`이 없다. **다시 묻지 않는다**(프롬프트 0)
5. 재개(`DealerService.resumeTable`) → A에게만 새 프롬프트, 마감이 3의 것과 다르다.
   n/n 전에 재개가 거절되는 것은 게이트웨이(`runDealerAction`의 `SYNCING` 가드)라 하네스에 없다 —
   T96의 게이트웨이 검사가 이미 든다
6. A가 수락 → 칩과 차감이 **한 번씩**. B는 탈락한다
7. **락 안 가드** — 수락을 스파이로 `mutateSnapshot` 안에 붙잡은 채 끊는다 → DB가 한 번도 안 불렸다 → 재개 뒤 다시 묻는다

**실패를 먼저 본다.** `waitForRebuyResponse`의 `down` 리스너를 빼면 3이, 쓰는 순서를 되돌리면
7이, 재개 대기를 `whenUp`만으로 바꾸면 4가 빨개지는지 확인한다.

`test:outage`는 넓히지 않는다 — 파산자를 만들려면 핸드를 하나 더 몰아야 해서 시나리오가
드는 것에 비해 비싸다.

## 범위 밖

- **7초보다 짧은 장애의 오프라인 큐** — 1의 칩 쓰기가 큐에서 뒤늦게 실행되면 「칩은 있는데
  돈이 안 빠졌다」. T97 잔여의 같은 부류
- **되돌리기의 이중 장애** — DB 거절 직후 Redis까지 끊기면 칩이 남는다. 로그만 남긴다
- **리바인 대기 중 프로세스 재시작** — 고리와 재개 대기가 메모리라 사라진다. 원래 있던 결함
  (지금도 재시작하면 `HAND_END`에 멈춘다)
- **재접속한 좌석** — 끊겼다 다시 붙은 좌석은 이미 뜬 프롬프트를 다시 받지 못한다. 원래 있던 결함
- **딜러가 끝내 재개하지 않으면** 그 테이블의 정산이 멈춘다. 배너가 서 있어 딜러가 안다 — 감수
- **여러 인스턴스**(B9) — 재개 대기가 프로세스 메모리다
