# 부하테스트 설계 — 한 인스턴스가 무엇을 받는가

**날짜**: 2026-08-09
**전신**: 백로그 B9(WS 수평 확장, "하지 않는다"), T31(서버 장애 복구)
**상태**: 설계 완료. 구현은 T37 · T38 완료, T39~T41 남음. T42(레이스 컨디션 전수조사)가 그 뒤

---

## 왜 지금

1단계에서 "정확하게 돌아간다"를 세웠고, T34에서 화면이 붙었고, T36에서 촬영까지
끝났다. 남은 질문이 하나다 — **이게 몇 명을 받나.**

이 리포는 실배포를 하지 않는다. 그래서 부하테스트의 목적도 "운영 전 검증"이
아니다. **이 시스템의 확장 한계가 어디고, 그 한계를 만드는 것이 무엇인지 숫자로
말할 수 있게 되는 것**이 산출물이다. 백로그 B9이 "지금 필요하지 않다"고 접은
판단에 실측 근거를 붙이는 일이기도 하다.

## 답하려는 질문 셋

| | 질문 | 판정하는 결정 |
|---|---|---|
| Q1 | 한 인스턴스에 홀덤펍 몇 상점을 얹나 | SaaS 원가. 사업 판단 |
| Q2 | 대회 하나의 정원은 몇 테이블인가 | 프로세스 분할이 성립하는 상한 |
| Q3 | 부하 상태에서 장부가 깨지나 | 락·트랜잭션 경계의 증명 |

Q1·Q2는 수치, Q3은 정합성이다. **요구가 반대라서 계층을 가른다** — Q3은 DB와
Redis 안을 들여다봐야 하고, Q1·Q2는 밖에서 진짜 네트워크로 때려야 정확하다.

## 도메인이 정하는 부하의 모양

홀덤은 초당 이벤트가 낮다. 라이브 테이블이 시간당 25~30핸드, 핸드당 서버 액션
20건 남짓이라 **테이블 하나가 0.13 액션/초**다. 그런데 부하는 액션 수가 아니라
**fan-out의 곱셈**에서 나온다.

```
브로드캐스트 1회 = N × (UTF-8 인코딩 + 프레임 헤더 + 소켓 write)
```

`ws.gateway.ts:178`이 `JSON.stringify`를 이미 루프 밖에 두고 있어 직렬화는 1회다.
남은 소켓당 비용은 셋 — `s.send(message)`가 문자열이라 소켓마다 `Buffer.from()`
UTF-8 인코딩이 돌고, 프레임 헤더가 붙고, write가 나간다. 인코딩만 없앨 수 있고
(`Buffer`로 미리 바꾸면 1회) 나머지는 fan-out의 본질이다. `perMessageDeflate`는
켜져 있지 않다(ws 기본값) — 켰으면 소켓마다 압축이라 훨씬 나빴다.

### 곱셈이 두 겹인 자리

```
entry.service.ts:327   getTournamentTables(tournamentId)   대회의 모든 테이블 좌석 비트맵
entry.service.ts:328   SEAT_LIST_UPDATED                   대회 전체 소켓에 브로드캐스트
```

`getTournamentTables`는 `hgetall`이라 페이로드가 **테이블 수에 비례**하고, 그것을
대회 스코프 소켓 전부에 뿌리므로 **한 명이 앉을 때마다 O(테이블²)**이 나간다.
테이블당 JSON 약 110바이트로 잡으면:

| 테이블 | 착석 1건의 fan-out 총량 |
|---|---|
| 6 | ~40 KB |
| 40 | ~1.8 MB |
| 560 | ~345 MB |

**이 발견 자체가 부하테스트의 첫 산출물이다.** 고치는 것은 별건이다(아래 범위 밖).

### 피크는 대회 시작이 아니라 `rebuyUntil` 직전

참가자는 한꺼번에 오지 않는다. 늦은 등록과 리바인이 있어 인원은 등록 마감까지
계속 늘고, 마감 후에는 줄기만 한다. 그래서 최악은 **등록 부하와 게임 부하가
겹치는 유일한 구간**인 `rebuyUntil` 직전이다. 램프를 그 지점까지만 돌리면 되므로
실행 시간도 짧아진다.

## 두 계층

| | 어디 | 무엇을 잡나 |
|---|---|---|
| 정합성 (Q3) | 기존 통합 하네스 — jest, 5433/6380 컨테이너 | 동시 요청 폭탄 + 매 단계 `checkInvariants` |
| 수치 (Q1·Q2) | k6 컨테이너 → 1코어 제한 백엔드 컨테이너 | p95 지연, 이벤트 루프 lag |

정합성 계층은 배선이 공짜다(`harness.ts`와 `checkInvariants`가 이미 있다) — 그래서
CI에 올라간다. 잡을 것:

경합마다 **판정자가 다른 것**을 고른다. 같은 판정자를 두 번 보면 두 번째가
아무것도 증명하지 않는다.

| 경합 | 판정자 |
|---|---|
| 같은 좌석에 여럿이 동시 입장 | `@@unique([tableId, seatPosition])` |
| 같은 사람이 서로 다른 테이블에 동시 입장 | `@@unique([tournamentId, userId])` — 테이블마다 락이 따로라 락은 못 막는다 |
| 한 테이블에서 여럿이 동시에 액션 | `withTableLock`의 직렬화 |
| 딜러가 핸드 시작을 동시에 두 번 | 락 + 락 안의 `phase !== WAITING` 가드 |

동시 리바인·탈락은 넣지 않는다 — 블랙박스 동시 호출로 테이블 락을 증명할 수
없다는 것이 T37의 결론이므로, 같은 방식으로 하나 더 만들어도 결과가 같다.
램프 실행에서 실제 부하로 지나간다.

딜러 중복 시작은 **`checkInvariants`만으로는 잡히지 않는다.** 블라인드가 두 번
나가도 칩은 스택에서 팟으로 옮겨질 뿐이라 총량이 보존된다. 팟 값을 직접 봐야
한다 — 검사가 둘이면 둘이 어긋나는 입력이 있어야 각각이 증명된다(T29의 교훈).

시나리오 계층의 관행을 그대로 따른다 — **틀어진 첫 순간**을 잡도록 단계마다
불변식을 검사하고, 실패 메시지에 단계 이름이 남게 값을 감싼다.

## 측정 환경

```
k6 컨테이너         제한 없음          측정기가 피측정자를 굶기면 안 된다
backend 컨테이너    cpus=1, mem=512m   t4g.micro급
db / redis          제한 없음          RDS + ElastiCache 가정
```

**DB와 Redis를 예산 밖에 두는 이유**: 서버 인스턴스와 관리형 데이터 스토어를
나누는 것이 맞는 인프라 구성이고, 셋을 한 예산에 넣으면 병목이 어디인지 분리가
안 되어 "그래서 무엇을 고치나"가 나오지 않는다.

백엔드 `Dockerfile`을 새로 만든다(지금 없다 — compose가 상태 있는 것만 맡는 것이
이 리포의 방식이었다). bcrypt가 네이티브 모듈이라 컨테이너 안에서 설치해야
한다. `seed` 서비스가 이미 겪은 함정이다.

k6도 컨테이너에 넣는다. 호스트가 Windows라 소켓 수천 개에서 호스트 한계가 먼저
올 수 있고, 그러면 측정한 것이 서버가 아니라 측정기가 된다.

## VU 하나가 테이블 하나를 통째로 든다

가장 중요한 구현 결정이다.

**"남의 액션이 내 화면에 뜨기까지"를 재려면 보낸 시각과 받은 시각이 같은
프로세스에 있어야 한다.** k6는 VU 간 상태 공유가 없다(`SharedArray`는 읽기
전용). 그래서 VU를 사람 하나에 대응시키면 이 지연을 아예 잴 수 없다.

VU = 테이블 1개로 둔다. `k6/experimental/websockets`(비동기 API)로 한 VU가 소켓
10개(좌석 9 + 딜러)를 들고, 봇이 게임 규칙대로 돈다 — `renderGame`을 파싱해
자기 차례일 때만 액션을 보내고, 딜러 봇이 핸드를 시작·종료시킨다. 그러면 두
지연이 같은 시계 위에 놓인다.

```
내 액션    send 시각 → 그 소켓의 renderGame 수신     p95 < 200ms
남의 액션  send 시각 → 다른 8개 소켓의 renderGame    p95 < 500ms
```

**규칙을 지키는 봇을 고른 이유**: 부하의 모양이 진짜 대회와 같아야 나온 숫자가
그대로 정원이 된다. 마구 던지면 대부분 "차례 아님"으로 거절되는데, 거절 경로도
락을 잡으므로 CPU는 차지만 올인·사이드팟 같은 비싼 경로가 한 번도 안 돌아 최악
장부 경로를 못 본다.

## 램프와 도착 프로필

램프 둘.

| | 무엇을 늘리나 | 답 |
|---|---|---|
| A | 홀덤펍 대회(6테이블·54명)를 **하나씩** 1→2→3→4→… | Q1 — 상점 몇 개 |
| B | 대회 1개의 테이블을 **둘씩** 4→6→8→10→… | Q2 — 대회 정원, O(T²) 곡선 |

**배로 늘리지 않는다.** 처음에는 1→2→4→8이었는데, 그러면 "8에서 터졌다"까지만
알 수 있고 실제 정원이 5인지 7인지가 구간 안에 묻힌다. 답이 "몇 개까지"인
질문에 2배 간격은 절반이 오차다.

램프 B를 둘씩 늘리는 것은 O(T²) 때문이다 — 곡선이 급하게 꺾이므로 한 칸이
크면 꺾이는 지점을 통째로 뛰어넘는다. 대신 단계가 많아지므로 **경고선을
넘은 뒤에는 간격을 좁히고, 붕괴선을 넘으면 멈춘다**(아래 지표 절).

대규모 대회를 별도 램프로 두지 않는다. **B를 계속 늘리면 그것이 WSOP급**이라
별개의 축이 아니라 B의 끝점이다.

도착 프로필 셋. 최악 하나만 재면 답이 "정원"이 아니라 "스파이크 내성"이라
Q1이 닫히지 않는다.

| | 정점 | 그때 겹치는 것 |
|---|---|---|
| 현실 등록 | `rebuyUntil` 직전 | 착석·리바인 O(T²) + 이미 돌고 있는 게임 액션 |
| 재접속 폭발 | 임의 시점 | 전원 핸드셰이크 (티켓 `GETDEL` 포함) |
| 정상 운영 | — | 액션 fan-out만. 기준선 |

**재접속 폭발은 억지 부하가 아니다.** T31이 만든 복구 경로의 뒷면이다 — 서버가
살아 돌아오거나 행사장 AP가 한 번 끊겼다 붙으면 정확히 이 모양이 된다. 그리고
`SeatGameClient.tsx:118`은 자동 재접속이 없다 — `onclose`에서 에러 배너만 세운다.
그래서 실제 모양은 "사람들이 배너를 보고 동시에 새로고침"이고, 여기엔 지터가
걸려 있지 않다. `common/retry.ts`의 풀 지터는 서버 내부 재시도용이고 프로덕션
호출자가 `playsync.service.ts:238` 한 곳(체크포인트 DB 쓰기)뿐이다.

정상 운영은 싸므로 램프마다 앞에 한 번 깔아 기준선으로 삼고, 나머지 둘의 수치를
거기서 뺀다.

## 서버측 지표

`monitorEventLoopDelay` + `process.cpuUsage` + rss를 노출하는 작은 엔드포인트.

넣는 이유: 합격선(p95)만 보면 이미 무너진 뒤에야 신호가 온다. CPU가 100%를 치기
전부터 지연은 벌어지기 시작하는데, 그 구간을 못 보면 "몇 상점까지"의 경계가
뭉개진다. lag이 선행 지표다. 그리고 이벤트 루프 lag은 **프로세스 밖에서 잴 수
없다** — `perf_hooks.monitorEventLoopDelay`가 프로세스 내부 API라 `docker stats`도
k6도 그 값을 볼 방법이 없다.

**두 단계로 판정한다.** "터졌다"만 알면 정원이 나오지 않는다 — 필요한 것은
**언제부터 지연이 보이기 시작했고, 언제 급해졌고, 어디서 무너졌는가**다.

| 선 | 값 | 뜻 |
|---|---|---|
| 경고 | lag p95 20ms | 지연이 보이기 시작한다. 사람은 아직 못 느낀다 |
| 붕괴 | lag p95 100ms | 무너지는 중이다. 내 액션 합격선(200ms)의 절반 |

모니터 VU가 5초마다 읽어 시계열로 남기고, 두 선을 넘는 순간을 로그로 박는다.
원시 시계열은 `--out json=`이 타임스탬프와 단계 태그까지 그대로 떨어뜨린다 —
결과는 `load/results/`에 쌓인다.

**바닥값을 빼고 기록한다.** `monitorEventLoopDelay`가 샘플링 간격만큼을 늘
얹어 돌려주므로, 빼지 않으면 시계열 전체가 10ms 들려 있어 "언제부터 올랐나"의
기준선이 흐려진다.

`LOAD_METRICS=1`이 게이트하는 것이 둘이다. 기본값(미설정)이면 둘 다 일어나지
않고, 제품 경로에는 조건문 하나만 남는다.

```
LOAD_METRICS=1  →  histogram.enable()           수집 시작 (libuv 타이머 하나)
                →  GET /internal/metrics 등록   라우트
```

**제품 코드를 부하테스트를 위해 건드리는 유일한 지점이다.** T32가 "라우트를 단 채
남은 수동 테스트 잔재"를 걷어낸 티켓이라 같은 종류를 다시 만드는 것 아닌가를
따졌고, 환경변수 게이트로 가기로 했다 — T32가 지운 것은 **기본으로 켜져 있던**
경로였다. 대안 둘은 버렸다(아래 버린 선택지).

## 시드

`prisma/seed.ts`는 손대지 않는다 — 데모 촬영이 매번 같은 무대를 요구한다.
`prisma/seed-load.ts`를 따로 두고 헬퍼만 공유한다. 규모는 `LOAD_TOURNAMENTS` /
`LOAD_TABLES` 환경변수로 받는다.

참가자를 수천 명 만들 때 bcrypt를 사람마다 돌리면 시드가 몇 분 걸린다. 해시를
한 번 계산해 전원에게 복사한다 — 로드용 계정이라 전부 같은 비밀번호다.

| 내 액션이 내 화면에 반영 | p95 < 200 ms |
| 남의 액션이 내 화면에 반영 | p95 < 500 ms |
| 이벤트 루프 lag | p95 — 위 둘이 깨지는 지점과 함께 기록 |

홀덤은 턴이 초 단위라 남의 액션은 느슨해도 되지만, 내가 누른 버튼은 즉각이어야
한다. 두 값이 다른 이유가 그것이다.

## 확장 순서 — pub/sub은 마지막

부하테스트가 임계를 재는 것은 이 순서 중 **어디까지 왔는지**를 알기 위해서다.

```
1. 소켓당 UTF-8 인코딩 제거        Buffer.from() 1회로
2. 메시지 크기 줄이기              델타 전송 / SEAT_LIST_UPDATED 범위 좁히기
3. 프로세스 여럿 + 대회별 고정 배정  ← pub/sub 없이 코어를 다 쓴다
4. Redis pub/sub                   한 대회가 프로세스 하나에 안 들어갈 때만
```

3번이 핵심이다. Node 프로세스 하나는 코어를 하나만 쓰므로 큰 인스턴스를 사도
얻는 것이 클럭뿐이다. 코어를 쓰려면 프로세스를 늘려야 하는데, **브로드캐스트가
대회 경계를 넘지 않으므로** 대회(=상점)를 프로세스에 고정 배정하면 그것으로
끝난다. `tournamentSessions` / `tableSessions` Map이 갈라져도 무관하다 — 같은
대회 소켓은 같은 프로세스에 있다.

pub/sub이 불가피해지는 것은 **한 대회가 프로세스 하나에 안 들어갈 때**, 즉
WSOP급 하나뿐이다. 백로그 B9의 "한 행사장 한 프로세스가 단위"라는 판단이 여기서
실측 근거를 얻는다. 램프 B가 그 지점을 찾는다.

## 티켓 분할

한 세션 크기로 자른다(CLAUDE.md 리뷰 예산 규칙).

| | 범위 | 무엇으로 끝났다고 하나 |
|---|---|---|
| T37 | 정합성 부하 — jest 스펙 + `checkInvariants` | 동시 요청 폭탄에서 불변식이 선다. CI에 올라감 |
| T39 | 무대 — `Dockerfile`, `docker-compose.load.yml`, 메트릭 엔드포인트 | 백엔드가 1코어 컨테이너로 뜨고 `/internal/metrics`가 lag을 준다 |
| T40 | 봇 — `seed-load.ts`, k6 플레이어·딜러 봇 | 테이블 하나에서 봇들이 규칙대로 핸드를 돌리고 두 지연이 잡힌다 |
| T41 | 실행 — 램프 A·B × 도착 프로필 셋, 결과 문서, README | 등급별 정원과 pub/sub 임계가 숫자로 나온다 |

**셋업을 셋으로 쪼개고 실행은 하나로 둔다.** 세션 한도는 토큰이지 시간이 아니다 —
램프 실행은 대기가 길 뿐 남는 토큰은 결과 요약뿐이고, 램프 A·B가 같은 봇과 같은
지표를 쓰므로 그 사이에 잘라 넣을 경계가 없다. 반대로 셋업은 코드가 실제로
쌓이는 자리라 T39·T40이 각각 한 세션이다.

T37은 앞의 셋과 독립이다. 인프라가 이미 있고(통합 테스트 컨테이너) 컨테이너
작업이 필요 없어, 순서를 지킬 이유가 없다.

**T38 자리가 비어 있다.** 하네스가 실제로 막히는 자리를 먼저 뗐다 —
`createTable`이 빈 스냅샷을 세우지 않아, 딜러 화면이 부르는
`GET /playsync/:tableId`가 아무도 앉지 않은 테이블에서 500을 냈다
(`docs/backlog.md`의 B11절, T38). 램프 B는 테이블을 4→10→25→50으로 늘리는데
딜러 봇이 붙는 순간 전부 500이 되므로, T40의 봇을 짜기 전에 닫아야 했다.
그래서 하네스 셋이 T39~T41로 밀렸다.

**T37이 발견한 회귀 공백은 T42로 갔다.** 스냅샷을 쓰는 열한 경로가 "락 안에서
다시 읽는다"를 각자 손으로 지키고 있고, 그 줄을 지워도 아무 테스트도 빨개지지
않는다. 실피해가 없어(재읽기가 실제로 막고 있다) 하네스 뒤로 보냈다.

## 범위 밖

- **병목 수정.** `Buffer` 인코딩 1회화, 델타 전송, `SEAT_LIST_UPDATED` 범위
  좁히기. 전부 별건이다 — **측정이 먼저다.** 안 그러면 무엇을 얼마나 고쳤는지
  증명할 기준선이 없다.
- **프론트(Next) 부하.** k6는 REST와 WS를 직접 친다. Next 렌더링 비용이 섞이면
  게임 서버의 정원이 가려진다. T24가 만든 티켓 중계 경로는 부하 경로에서 빠지고,
  k6는 티켓을 백엔드에서 직접 받는다.
- **실제 AWS 배포.** 이 리포는 실배포를 하지 않는다.
- **`activePlayers` 기준(T30), 등록 마감 권위 이원화(T31 이월).** 부하로 드러날
  수 있지만 도메인 장부 회계라 별건이다.

## 버린 선택지

**한 도구로 묶기 (jest만, 또는 k6만).** jest만 쓰면 수치가 런타임·동일 프로세스
오버헤드를 포함해 README에 실을 값이 못 된다. k6만 쓰면 불변식을 끝난 뒤에만 볼
수 있어 "틀어진 첫 순간"을 놓친다 — 시나리오 계층을 따로 만든 이유와 같은 자리다.

**셋을 한 CPU 예산에.** "최저 티어 한 대에 다 올렸다"는 상황에 가장 직접
답하지만, 병목이 Node인지 Postgres인지 분리되지 않아 확장 순서 1~4 중 어디로
가야 하는지가 안 나온다.

**기록 재생(미리 만든 액션 배열을 그대로 틀기).** 스크립트가 단순하고 재현성이
높지만, 서버가 느려지면 순서가 어긋나 거절이 쌓이고 그 순간 부하의 의미가
변질된다. 부하가 커질수록 측정이 부정확해지는 방향이라 목적과 반대다.

**VU = 사람.** 자연스러운 대응이지만 "남의 액션 지연"을 잴 수 없다. k6에 VU 간
공유가 없기 때문이다.

**대규모 대회를 별도 램프로.** 램프 B의 끝점이라 축이 늘지 않고 실행만 늘어난다.

**메트릭 엔드포인트를 안 넣고 `docker stats`만 보기.** 컨테이너 CPU%는 밖에서
보이지만 이벤트 루프 lag은 못 본다. 포화가 이미 일어난 뒤에야 신호가 오므로
임계 앞뒤를 구분할 수 없다.

**별도 진입점(`main.load.ts`)에만 메트릭을 붙이기.** 제품 부트스트랩과 섞이지
않는다는 장점이 있지만 부트스트랩이 복제된다. 그러면 부하테스트가 재는 것이
제품이 실제로 뜨는 모양과 조금씩 달라지고, 그 차이가 어디서 생겼는지 아무도
추적하지 않게 된다.

**서버 페이로드에 타임스탬프를 심어 지연 측정.** 제품 코드를 부하테스트를 위해
바꾸는 것이고, 클라이언트와 서버의 시계 차이 문제가 새로 생긴다. VU가 테이블을
통째로 들면 한 시계로 해결된다.
