# 결정 로그 — 2단계 (T22~T36)

> 백엔드 고도화를 마친 뒤 **위협 모델 → 화면 → 데모 촬영**까지 간 구간이다.
> 1단계(T1~~T21)는 [`chat-log.md`](./chat-log.md), 부하테스트부터의 3단계(T37~~T55)는
> [`chat-log3.md`](./chat-log3.md)에 있다.
>
> 각 항목은 **요청 → AI 제안 → 사람 판단 → 근거 → 결과** 순서다. **AI 제안이
> 기각되거나 철회된 것도 그대로 남겼다** — 무엇을 골랐는지보다 무엇을 왜 버렸는지가
> 같은 자리를 다시 볼 때 쓸모 있기 때문이다. AI가 단독으로 판단한 부분은
> 그렇게 표시해 사람이 결정한 것과 구분했다.
>
> 세션 경계는 지웠다. 티켓 번호가 본문에 붙어 있어 어디쯤인지는 그것으로 읽힌다.

## 1. 기능명세 스코프 분할과 디자인 토큰 방향

- **사용자 요청(요지):** 기능명세부터 작성. CSS 토큰은 DESIGN.md 사용 예정. 어드민/상점별/상점상세 등 기본 SaaS 구조를 가지려 함.
- **AI 제안:** 범위가 넓어 4개 서브프로젝트(A 디자인토큰 기반, B SaaS 셸+역할라우팅, C 상점목록/상세, D 플랫폼 어드민)로 쪼갤 것을 제안. 기존 DESIGN.md는 BMW M 브랜드 토큰(사유 폰트 `BMWTypeNextLatin`, 브랜드 고유 색상명)이라 배포·재사용에 문제가 있다고 지적.
- **사람 판단:** "전체 로드맵 1장 + A 상세 spec" 선택. 이어서 "값은 쓰고 이름은 의미로 바꿈" 선택. "npx getdesign@latest add ibm로 기존 토큰 버리고 라이트/다크 둘 다 지원하는 토큰으로" 선택 후 직접 명령 실행 — IBM Carbon 계열로 교체됨. 비교를 위해 `npx getdesign@latest add kraken`도 직접 실행.
- **추가 질문·문제제기:** kraken 프리셋은 스케일이 정의되지 않은 무드보드에 가까워 AI가 값을 지어내야 하는 문제가 있다고 판단됨(비교 결과, IBM 유지).
- **사람 판단(최종):** 같은 취지 요청을 재입력한 뒤 "디자인토큰은 너는 신경쓰지말고. 그냥 프론트엔드 기능명세와 무엇이 들어가야하는지만 얘기해줘." — 디자인 토큰 논의를 이번 기능명세에서 배제.
- **결과:** 루트 `DESIGN.md`는 IBM Carbon 계열 값(550줄)으로 남았으나, 이번 기능명세 문서에는 토큰 내용을 다루지 않기로 함. AI가 제시한 CSS 2계층 변수 접근안(원시 팔레트 → 의미 토큰 → `@theme inline`)은 논의가 배제되며 명시적 채택 없이 소멸.

## 4. OTP 기반 착석 흐름 (사용자 제안)

- **사용자 요청(요지):** 모바일 범위는 회원가입/로그인/대회찾기/등록까지, 전광판은 상점 TV. 추가로 "태블릿접속을 폰에서 대회참여시 otp를 볼수있고 태블릿에서 otp로 인증해서 앉는구조는 어떰?"이라며 OTP 착석 방식을 직접 제안.
- **AI 제안:** OTP 방식 채택, 좌석-사람 결합 지점이 명확해진다고 설명. `(display)` 그룹을 별도로 분리해 전광판을 인증 없는 읽기전용 화면으로 설계.
- **사람 판단:** entryFee 차감 흐름 질문에 "폰에서 충전하고 사용하는 게 자연스러움. 좌석선점 말고 테이블선점으로 수정" 선택.
- **근거:** 흐름 자체는 사용자가 직접 제안
- **결과:** 태블릿=좌석이라는 물리적 결합 원칙 확립. `acquireSeatLock`을 테이블 정원 기준 선점으로 변경하는 방향. 모바일 등록 흐름(포인트차감·participation생성·테이블선점을 원자적으로 처리)으로 정리.

## 5. 좌석 위치 입력 방식 — 태블릿 위치 기억 대신 사람이 선택

- **사용자 요청(요지):** "태블릿이 이 태블릿의 위치가 어디인가를 기억하기보다 otp입력하면서 테이블위치·좌석위치를 선택하고 otp를 누를수있도록" 하자. "전광판은 폴링으로해야됨"(기존에도 폴링이 블라인드 레벨을 체크하는 로직이 붙어 있음).
- **AI 제안:** 착석 화면을 테이블선택→좌석선택→OTP입력 한 화면으로 설계, 선택값과 선점 테이블을 대조해 검증 강화. 딜러 단말에 좌석별 닉네임을 표시해 육안 대조를 최종 방어선으로 채택.
- **근거:** "기기 옮길 때마다 재설정이 필요하고 어차피 어디 앉았는지는 앉은 사람만 안다"는 AI 설명에 이견 없음.
- **결과:** 전광판 폴링은 기존 `checkAndSyncBlindLevel` 지연평가 구조로 확인. 폴링 주체 분산(전광판 2초/딜러 2초/콘솔 5초) 설계.

## 6. 태블릿 UI 단순화와 딜러 계정 제거

- **사용자 요청(요지):** "태블릿단말은 모두 ws로 동작하게되어있음. 넌 그런거 신경쓰지말고 사용자흐름과 기본적인 구조만 어떻게잡을지만 결정하는역할임. 기술부채는 신경쓰지마셈." 이어서 "유저가 otp로 진입시에 테이블위치가 어딘지만 찍으면 태블릿에선 빈자리에 표시되고 이것을 딜러가 조정해주는방식."

- **결과:** 태블릿은 OTP 입력만, 좌석 배치는 딜러가 조정하는 흐름으로 정리.

## 8. OTP를 대회 단위 식별자로 통일

- **사용자 요청(요지):** "모바일에서 참가신청완료한 대회상세를볼때 대회정보랑 otp도 같이확인하도록 개인 otp가 아니라 딜러 otp같은 대회용 1회 사용자식별로하려고함."
- **AI 제안:** OTP를 대회 단위 코드로 통일(발급 시점·확인 위치만 다름, 만료·재발급 없음). 테이블 밸런싱으로 좌석 이동 시 동일 OTP를 재사용하는 방식을 AI가 자체 결정해 "아니면 말해줘"라고 남김 — 이 판단 자체에 대한 사용자 반응은 대화에서 확인되지 않음(AI 자체 판단, 사람 반응 없음).
- **사람 판단:** OTP를 대회 단위로 통일하는 것 자체는 사용자 요청이므로 그대로 반영.
- **결과:** 커밋 `cf57c44`. 만료·재발급 로직 제거, 좌석은 시스템이 임의 배정한 뒤 딜러가 조정, 테이블은 유저가 선택하는 구조로 확정.

## 10. Task 3~5 진행과 최종 리뷰

- **AI 발견(Task 3 리뷰):** `next.config.ts`의 `/api/:path*` rewrite와 미들웨어 matcher가 겹쳐 미인증 `POST /api/auth/login`이 `/login`으로 307 리다이렉트되어 로그인 자체가 불가능했음(Critical). 수정 투입.
- **AI 발견(Task 4 리뷰):** 수정한 matcher의 `.*\.` 패턴이 "마지막 세그먼트 확장자"가 아니라 "경로 아무 곳의 점"으로 해석되어 `/stores/my.store`, `/admin/users/a.b` 같은 경로가 가드를 우회함. 수정 투입.
- **AI 발견(최종 전체 리뷰):** 브랜치가 main보다 18커밋 뒤처짐(백엔드·문서) — 충돌 없이 병합. 라우트 재편으로 전광판 파라미터명이 깨져 `/dashboard/undefined`로 fetch되던 문제, 삭제된 `/playsync` 경로로의 `router.push` 잔존 2건도 확인·수정.
- **사람 판단:** "Continue from where you left off." / "작업 이어서 진행" / "워크트리 확인후 이어서진행" — 구체적 방향 지시 없이 재개만 지시. 수정 내용 자체는 AI가 자체 발견·수정한 것으로 별도의 사람 판단 문구는 확인되지 않음.
- **결과:** Plan 1(앱셸) 5개 태스크 전부 완료, 커밋 8개(main 병합 포함), 프론트 테스트 0→35, contract/백엔드 단위 44/122 기준선 유지, 타입 에러 0, 빌드 성공. 통합 테스트는 백엔드 미변경으로 미실행. `auth/action.ts`의 `BACKEND_URL` 기본값 오타(`http://localhost:3001.com`)는 계획2(로그인 화면) 범위로 백로그 이관. 마지막 AI 턴에서 "PR 만들까?"를 물은 채 세션 종료(사람 반응은 대화 범위 내 미확인).

## 11. 백엔드 대기 중 프론트에서 무엇을 할까 — "화면만 그리기"

- **사용자 요청(요지):** "백엔드 작업이 v2의 기준만큼 진행됨. 프론트엔드는 백엔드를 작업하는동안 mock api를 만들었던걸로 기억함." — 프론트 현황 파악과 다음 작업 선택.
- **AI 제안:** 목업은 기억과 달리 MSW 테스트 픽스처(핸들러 1개, 브라우저 워커 없음)라 백엔드 대체가 안 된다고 보고. 선택지 셋 제시 — (1) 백엔드 B1~B4 실제 진행분 확인, (2) B5 프론트 기능 명세 착수, (3) 목업을 브라우저 워커까지 확장.
- **추가 질문·문제제기:** "일단 그럼 이 워크트리만 만들어두고 백엔드를 어느정도 추가진행을 한뒤에 프론트를 작업하는게 맞는순서인거지? 화면만 그리는거는 어떰?"
- **사람 판단:** 백엔드 선행이 맞는 순서인지 되묻고, 그 사이 "화면만 그리기"를 대안으로 직접 제시.
- **근거:** (근거 미명시) — 워크트리를 만들어 둔 상태에서 대기 시간을 놀리지 않으려는 의도로 읽힘 `(추정)`.
- **결과:** AI가 "B1~B4는 화면을 늘리거나 필드를 얹지 기존 화면을 부수지 않는다"며 화면 작업 가능 판정. 조건 셋(fetch 금지·props 타입은 `packages/contract` zod에서, 통합 어드민 제외)과 `.env` 부재·`http://localhost:3001.com` 오타 선행 처리를 제안.

## 59. B2(서버 장애 복구) 설계 — T31

- **사용자 요청(요지):** "b2 에러 복구?" 이어서 기존 기획 공유 — "기존 v1에서는 에러발생시간을 상점에서 체크하고 이후 복구시 시간계산 차이를 그냥 startedAt을 밀어서 해결하려고 했었는데, 더 나은 자동방안이 있다면 그것을 채택할것이고, buttonUser는 redis aof마지막 지점을 복구할때까지만 … 한핸드전까지는 보장을 해주는 생각으로 기획을 한것"
- **AI 제안:** `Tournament.startedAt`과 `BlindField.startedAt`이 두 뜻을 겸하므로 미는 것은 DB에 거짓을 남긴다고 지적하고 **스톱워치 모델**(`elapsedMs` + `resumedAt`)을 제안. 자동 다운타임 측정 수단으로 **DB에 쓰는 하트비트**(Redis ping 성공 조건) 제안. AOF는 `everysec`이라 유실이 1초 수준이지만 볼륨 유실 케이스에서는 0이라고 갈래를 나눔.

- **사람 판단:** (1) 스톱워치 모델 기각, **두 `startedAt`을 다른 뜻으로 갈라 선언**하는 쪽 채택. (2) `buttonUser`를 핸드 종료 트랜잭션에 좌석 인덱스로 기록, Redis 유실 시 DB로 재구성. (3) "추가적으로 재구성하는건 상점에서 관리할 일이 아님. 서버를 복구해주는것까지 saas 가 해야할 일이니까" (4) "내가 아까 하트비트는 서버가 관리하는 전체대회에대한 거라고 말했잖아. 스펙써" (5) "간단한건 태스크 합치고 최대한 불필요한 왕복줄여"
- **근거:** 운영자 수동 정지는 홀덤에 존재하지 않는 상황(있는 건 예정된 휴식뿐)이라 스톱워치의 이점 하나가 사라짐. 복구는 플랫폼 책임이지 상점이 판단할 일이 아니므로 **B2에 엔드포인트도 화면도 생기지 않음**. 하트비트는 "한 행사장 한 프로세스"가 배치 단위라 서버 단위 한 행이면 충분.
- **결과:** 스펙 `2026-07-30-server-recovery-design.md`(`918b007`), 계획 `2026-07-30-server-recovery.md`(`3ff3da3`, 4 태스크·태스크 리뷰 3개). 결정 다섯: 두 `startedAt` 분리 / 하트비트 서버 단위·DB·ping 조건 / `buttonUser` 두 지점 쓰기 / 재구성은 부팅 시 자동·판정은 키 유무·실패는 대회 단위 격리 / `entry` fallback 가드(격리가 이것에 의존).

## 85. 다중 세션 녹화 가능성과 자원 — 그리고 사람이 지정한 장면 목록

- **사용자 요청(요지):** 크롬 창을 한 PC에서 여러 세션으로 띄워 녹화하듯 Playwright에서도 되는지, 헤드리스가 PC 자원을 많이 먹던데 무리인지. 그리고 보여줄 것으로 **폰 화면 + 태블릿 OTP로 대회 진입 + 콘솔에서 실제 확인, 7명이 아니어도 한 테이블에서 게임이 진행되는 여러 태블릿 세션, 딜러가 무언가 행동 가능하다, 탈락자 리바인 및 탈락**을 지목.

- **결과:** 장면 넷 표로 정리. 전광판은 1920×1080 대신 1280×720으로 결정(2x2 타일이 어차피 960×540이고 넷 다 16:9여야 레터박스가 없음 — AI 판단).

## 86. 핸드 시나리오 설계 — 사이드팟과 탈락

- **사용자 요청(요지):** "칩 최저가 올인, 나머지가 플레이하면서 사이드팟을 만들고, 최저가 족보 1위여서 우승을 하고, 테이블의 딥스택이 핸드를 이기고 중간이 탈락하는 그런 **다이나믹한 흐름**을 구성하는 것." 이어서 **"테이블이 합쳐지는 것도 움짤에 추가하면 좋음."**

## 88. T36 — 카메라 앞 결함 다섯, 그리고 하네스·데모 스펙

- **사용자 요청(요지):** "5까지 진행해" (명세 §10의 4~5, 즉 하네스와 데모 스펙까지). 이후 **"1은 사람이 결제를 하고 대회에 참여하는 모습까지만, 2부터는 게임이 흘러가는 거니 상관없을 듯"**.

- **결과:** B1(전광판을 `(board)` 그룹으로 분리, 링크 0개), B2(UUID → `1번 테이블 · 9번 자리`), B3·B4(알약·둥근 모서리 제거, 펠트 900px 안에) 처리. 콘솔의 죽은 링크 둘(`/stores`·`/admin`)은 라우트를 만드는 대신 삭제하고 재발 방지 테스트를 박음. 촬영 하네스는 Playwright 프로젝트 둘(`regression`/`demo`), `slowMo: 220`, **제품 코드를 안 건드리는 가짜 커서 주입**(`addInitScript`), `backstage`에 `seat`·`tableState`·`chipsOnTable`. 커밋 `c30c962`(B0~B4)는 푸시, 하네스·데모 스펙은 워킹 트리에만 남음.

## 89. 1차 시사 — 지적 여섯

- **사용자 요청(요지):** 데모 영상을 보고 여섯을 지적. ① 플레이어 아이디가 성의 없어 구분이 안 됨 ② s1 폰 화면이 너무 빨라 내용 확인 불가 ③ 태블릿에서 OTP를 입력해 진입하는 화면이 없는데 상점 콘솔만 보여주면 무슨 소용인가 ④ s2 태블릿 하단 베팅 콘솔이 본인 턴일 때만 슬라이더·타이머가 생겼다 없어져 레이아웃이 고정이 아님 ⑤ s3도 무슨 조작을 했는지 확인이 안 됨 ⑥ s5 테이블 머지는 흐름을 모르겠음.
- **AI 제안:** 여섯 모두 실제 결함으로 판정. 시드 이름을 사람 이름으로 바꾸고 스펙은 이름 대신 순서(`playerAt`)로 고르게 함, 단계마다 멈춤, 장면 1에 태블릿 키패드 추가, `SeatActionPanel`을 자리는 늘 잡고 내용만 바꾸도록 수정(`ActionTimer` 포함), `press()`가 커서를 먼저 옮기고 클릭 파문을 남기게 함, s5를 네 단계로 분해.
- **사람 판단:** 지적 제기까지가 사람의 것. 각 해법 선택에 대한 사람 승인 발화는 없다. (AI 자체 판단, 사람 반응 없음)
- **근거:** 영상으로 읽히지 않는다는 관찰. ④는 "팔 길이에서 보는 고정 기기"라는 도메인 근거를 AI가 덧붙였다(AI 발화).
- **결과:** 여섯 반영. 장면 1이 8초 → 57초. 화질도 함께 손봄(`-q:v 85`, libwebp `-preset text`, lanczos). 프론트 테스트 90 → 94.

## 90. 2차 시사 — 테넌트·역할 이름·딜러 위치·s5 흐름 지정

- **사용자 요청(요지):** 화질은 개선됨. ① s1에 상점 이름을 찾는 화면이 없어 테넌트 분리 여부에 의문이 생길 수 있음 ② OTP 확인에서 태블릿 조작까지 텀이 긺 ③ 상점 콘솔의 테이블 펠트를 작게 해도 됨 ④ s2 조작 호흡은 적당함 ⑤ OTP는 더 빨라도 되고, 차라리 s1에서 이 데모 시드 토너먼트의 딜러 OTP를 노출하는 흐름이 있으면 s2 이해에 좋음 ⑥ 딜러 펠트·플레이어 펠트에 딜러 위치 표기가 사라짐 ⑦ 닉네임은 사람 이름보다 **보여주고자 하는 역할**로 하는 편이 직관적 ⑧ s5는 2×2로 A 태블릿·B 태블릿·상점 콘솔·A 유저 폰을 놓고, 2번 테이블을 모두 해제해 A가 나가고 B는 가만히 있는데 A가 1번 테이블에 합석하는 것을 B 태블릿에서 보여주는 흐름.
- **AI 제안:** ⑧ 흐름을 그대로 구현. ⑥을 코드에서 확인해 `player.button`을 백엔드가 채우지 않음(엔진은 `state.buttonUser`만 옮김)과 딜러 표찰 자리를 비워만 둔 것을 찾아 RED 먼저 수정. ⑦은 `숏스택 · 미드스택 · 딥스택 · 합석A~C`로. 콘솔 좌석 도식 760 → 520.
- **추가 질문·문제제기:** ⑤에서 "시드 값을 쓰지 말고 화면에서 읽은 번호로 들어가라"는 취지의 흐름을 사람이 직접 설계해 지시했다.
- **사람 판단:** s5 2×2 구성과 딜러 OTP 노출 흐름은 **사람이 직접 지정**했다. 나머지는 지적 제기.
- **근거:** "테넌트 분리가 되어 있는가에 대한 의문이 있을 수 있을 것 같고", "보여주고자 하는 사람의 역할로 이름을 보여주는 게 직관적일 것 같고".
- **결과:** 여덟 전부 반영. s5를 2×2로 찍으려다 제품 결함이 추가로 드러남 — **좌석 해제·착석이 그 테이블에 `game.state.updated`를 안 보냄**(B 화면에 A가 안 나타나서 발각). `SEAT_LIST_UPDATED`는 대기 화면용 신호였다. 통합 335, 프론트 97.

## 91. OTP 입력 시간 측정 요청

- **사용자 요청(요지):** "전체적으로 otp를 누르는 것이 너무 김. 현재 otp 입력들의 텀이 몇 초인지만 알려줘." — 고치지 말고 수치만.
- **AI 제안:** 한 자리당 약 0.61초(slowMo hover 220 + before 60 + slowMo click 220 + after 110). 참가 8자리 4.9초, 딜러 6자리 3.7초. 지배 요인은 `slowMo: 220`이 hover·click 두 번 걸리는 것이며, 키패드에서만 우회하는 선택지 셋을 제시.
- **사람 판단:** 고치기 전에 **수치부터 요구**했다.
- **근거:** 어디를 깎을지 사람이 판단하려고 원인 분해를 먼저 요구.
- **결과:** 수치 보고만 하고 수정하지 않음. 다음 턴에서 사람이 "절반으로"라는 목표치를 정함.

## 92. 3차 시사 — OTP 절반, 두 태블릿 동시 활성, 딜러 진입 순서

- **사용자 요청(요지):** ① OTP 입력을 절반으로 줄여라 ② s2에서 본인 턴 외에는 조작 UI가 비활성이어야 하는데 둘이 동시에 활성으로 보인다, 영상 싱크가 안 맞는 건지 ③ 딜러가 OTP로 먼저 입장해 있고 전광판이 뜬(대회 시작) 이후에 핸드 시작 버튼이 활성화되는 순서가 더 적합하지 않은가.
- **AI 제안:** ②를 먼저 프레임으로 판정 — 제품 버그인지 영상 어긋남인지. 결과 제품은 정상, 영상 정렬 문제로 확인하고 기준 시각을 `닫힘 − 파일 길이`로 변경. ①은 키패드에서만 hover를 빼 0.61 → 0.30초. ③ 순서 변경 중 **대회 시작도 같은 구멍**(버튼을 추첨해 스냅샷에 저장하는데 그 테이블에 안 알림)을 찾아 RED 먼저 수정.
- **사람 판단:** ②를 "영상 싱크가 안 맞는지"로 **가설을 열어 둔 채** 제기했고, ③은 도메인 순서 제안. ①은 절반이라는 목표치 지정.
- **근거:** ③ — "딜러는 otp를 먼저 눌러서 입장을 해 있고 전광판이 뜸(대회 시작함) 이후에 핸드 시작에 활성화 버튼이 들어오는 게 더 적합한 순서".
- **결과:** 셋 다 반영. 같은 구멍이 좌석 해제·착석·대회 시작 **세 곳**이었음이 드러남. `핸드 시작` 버튼 잠금은 딜러 화면이 대회 상태를 실시간으로 알아야 해서 남겨 둠(스냅샷에 그 정보가 없음). 통합 336.

## 93. 4차 시사 — 도메인 문구와 s4 재구성

- **사용자 요청(요지):** ① s1에서 "플레"를 입력하기도 전에 상점이 화면에 떠 있는 이유 ② s2에서 백엔드가 거절한 것을 태블릿 화면에서도 확인할 모달을 띄우면 완벽 ③ 딜러 모달의 `이긴 순서대로 누르세요`는 `족보 순서대로`가 도메인에 더 적합 ④ `팟이 n층입니다`도 `사이드팟이 n개 존재합니다`라는 설명으로 ⑤ s4는 내 참가 OTP가 아니라 내가 참가한 대회 목록에서 리바인 거부 → 탈락 시 등수가 매겨지는 화면이 더 직관적 ⑥ s5에서 딜러 OTP가 s1부터 같은 컨텍스트라면, 백엔드는 bcrypt라 요청할 때만 알려주더라도 프론트에서는 들고 있는 게 맞다.
- **AI 제안:** ①의 원인이 시드에 상점이 하나뿐이라 검색 전후가 같은 것임을 확인하고 상점 셋을 추가. ②는 배너 → 모달, 그리고 백엔드 문구 `블라인드 정보가 없습니다` → `대회가 아직 시작되지 않았습니다.`로 변경(사람 요청에 없던 추가). ⑥은 `sessionStorage`로 구현.
- **사람 판단:** ③④는 **도메인 용어 교정을 사람이 직접 지정**했다. ⑤⑥도 사람이 원하는 동작을 명시했다.
- **근거:** ③ — "족보 순서대로 누르세요가 도메인에 더 적합한 설명인 거 같음". ⑥ — 같은 컨텍스트인데 프론트가 OTP를 버리는 것이 이상하다는 지적.
- **결과:** 여섯 반영. ⑥의 근거로 "새로 고칠 때마다 `••••••`로 돌아가면 딜러가 받아 적은 번호가 무효가 된다"는 설명이 붙음(AI 발화). 프론트 100.

## 94. 정합성 문제 — 진행 전 승인 요구

- **사용자 요청(요지):** ① s2가 여전히 화면마다 같은 시각이 아닌 것 같음 ② 시작 전 모달에 불필요한 문구가 너무 많음, 대회 시작 전인 것만 알려주면 됨 ③ 모달 → 전광판 딜레이가 너무 길고, 대회 시작 누르기 직전에 이미 1행 2열 화면이 바뀌며 전광판에서 이미 몇 초 진행돼 있음 ④ s3·s4를 합쳐 2×2로 만들고 탈락 등수 확인은 png로 ⑤ s5의 2행(콘솔·폰)에 경계가 없어 무슨 화면인지 직관적이지 않음, 7:3이나 6:4로 폰은 레터박스. **"바로 진행하지 말고 어떻게 할 건지 나한테 허락을 받아."**
- **AI 제안:** 실행하지 않고 계획만 제출. 슬레이트(딱딱이) 방식 — 촬영 맨 앞에서 모든 면을 동시에 번쩍이고 `signalstats`로 그 프레임을 찾아 시각을 못 박음. 전광판 폴링 3초 → 1초. s3+s4 2×2 병합, 모든 타일에 2px 구분선.
- **추가 질문·문제제기:** 사람이 **작업 전 승인 절차를 명시적으로 요구**했다. 이 세션에서 처음이다.
- **사람 판단:** 진행 금지 + 계획 제출 요구.
- **근거:** 앞선 네 차례 시사에서 영상 정렬 수정이 반복적으로 어긋난 이력.
- **결과:** AI가 다섯 항목 계획을 제출하고 s5 2행 비율은 두 안을 내 사람에게 고르게 함.

## 95. 계획 승인과 전광판 폴링 회귀 진단

- **사용자 요청(요지):** "좋다." ① 슬레이트 같은 "여기부터 시작"이라는 무언가가 있어야 화면 정합성 표현에 맞고, 시간으로 계산하는 것보다 훨씬 확실해 보임 ② 모달 문구는 내가 원하는 톤 ③ **애초에 전광판 폴링이 1초마다였는데 컴포넌트를 다 버리고 다시 만들면서 체크를 못 한 듯**, 1초마다 서버 시간을 가져와 렌더링하는 건 양측 모두 큰 부하 아님 ④ 리바인 대기는 1초 정도, 리바인 X ⑤ 격자는 모든 곳에 적용해야 다른 화면인 걸 알 수 있음.
- **AI 제안:** 계획대로 실행. 슬레이트는 처음에 여는 즉시 0.15초만 쳤다가 늦게 연 좌석 태블릿이 통째로 놓쳐, 1초 뒤에 더 길게(0.4초 자홍색) 치도록 수정.
- **사람 판단:** 계획 승인. ③에서 **폴링 3초가 신규 결정이 아니라 재작성 과정의 회귀임을 사람이 직접 진단**했고, 부하 우려도 사람이 직접 기각했다. ⑤에서 AI가 제시한 "s2·s3에도 적용" 범위를 **모든 곳으로 확대**했다.
- **근거:** ③ — "애초에 전광판 폴링이 1초마다였는데… 체크를 못한듯". ⑤ — "모든 곳에 적용해야 다른 화면인 걸 알 수 있을 것 같음".
- **결과:** 다섯 반영. 프레임으로 정합 확인 — 대회 시작 +3초에 전광판 `LEVEL 1 · 2:59`, 세 펠트 모두 버튼(D)이 같은 자리, 팟 0. 움짤 5개 → 4개(s1·s2·s3·s5).

## 시행착오 요약

- 테스트 파일을 워크트리가 아닌 메인 리포에 생성: AI가 스스로 발견해 워크트리로 이동 (사람 개입 없음)

- 영상 면 간 시각 정합: 절대 시각 → 파일 길이 배율 → 오프셋 복귀 → `닫힘 − 파일 길이` → 슬레이트 검출까지 5차례 방식 변경. 촬영을 다섯 번 이상 다시 돌림 (중간 진단은 전부 AI 턴)

- 자산 타일 레이아웃: 반올림 1px 부족, 원본보다 확대 시 pad 깨짐. 2회 재시도 후 성공
