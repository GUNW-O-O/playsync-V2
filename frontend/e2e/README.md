# 촬영 하네스 · 화면의 회귀 계층

두 가지를 한다. README에 넣을 데모 영상을 만들고, **화면이 백엔드에서 온 값을
실제로 그리는지 잡는다.**

처음(T33)에는 영상만 만드는 자리였다. 화면이 아직 없었기 때문이다. T34에서
성격이 하나 늘었다 — 프론트 단위 테스트의 목은 **백엔드를 병렬로 만들던 시절의
도구**였고, 백엔드가 다 선 지금은 목이 틀려도 그 사실을 알려주는 것이 없다.
실제로 두 번 사고가 났다: 대회 전환 레이스가 대회 하나짜리 배열에 가려졌고,
`{ tournament, seatStatus }` 봉투를 안 벗기는 코드가 봉투 없는 목 때문에 그
경로에 닿지도 못했다.

그래서 경계는 이렇다. **단위 테스트는 빠른 TDD 루프**로 남기고, **봉투 모양 ·
키 이름 · 상태 전이는 여기서 진짜 백엔드가 판정한다.** 화면의 색·간격·배치는
여전히 단언하지 않는다 — 그걸 박으면 화면을 고칠 때마다 빨개진다.

```bash
cd backend && docker compose up -d   # 무대를 깐다 (DB를 지우고 다시 만든다)
npm run test:e2e                     # 화면 회귀. 개발 서버는 떠 있으면 재사용한다
npm run demo                         # 데모 촬영. 시드 → 프론트 빌드 → 장면 다섯
npm run assets                       # 촬영본을 자르고 합쳐 img/ 로
```

**프로젝트가 둘이다**(`playwright.config.ts`). `regression`은 `e2e/*.spec.ts`,
`demo`는 `e2e/demo/*.spec.ts`다. `dependencies`를 걸지 않았다 — 회귀는 상태를
남기고(사람이 앉는다) 촬영은 자기 무대가 필요하다. 대신 `npm run demo`가 시드를
먼저 깐다.

촬영에만 `slowMo`와 커서 주입이 걸린다. 회귀에서는 느린 것이 손해고, 없는 DOM
노드를 하나 더 얹으면 그만큼 다른 것을 보게 된다.

**스펙이 상태를 남긴다.** `terminal.spec.ts`가 사람을 자리에 앉히므로, 시드를
다시 깔지 않고 두 번 돌리면 그 자리가 이미 차 있어 빨개진다. 반복해서 돌릴
때는 시드부터 다시 깐다.

```bash
npm run seed -w backend && npm run test:e2e
```

파일 이름의 알파벳 순서가 곧 실행 순서다(워커 하나). 그래서 읽기만 하는
`console.spec.ts`가 앞에 오고, 사람을 앉히는 `terminal.spec.ts`가 뒤에 온다 —
`harness.spec.ts`가 그 사이에서 "무대는 아직 `PENDING`"을 단언한다. 콘솔
스펙이 대회를 시작하거나 딜러 OTP를 재발급하면 그 단언과 `dealer.spec.ts`가
같이 무너진다. 쓰기를 콘솔 스펙에 넣지 않은 이유다.

영상은 `e2e/recordings/<테스트 제목>/<면>.webm`에 떨어진다. 전부 `.gitignore`다 —
리포에 남길 것은 편집이 끝난 파일뿐이다.

## 무대는 시드가 깐다

`backend/prisma/seed.ts`가 상점 · 대회 · 테이블 둘 · 참가자 여덟을 만들고
**거기서 멈춘다.** 좌석도 앉히지 않고 대회도 시작하지 않는다. 그 둘이 데모가
보여줄 장면 자체이기 때문이다.

시드는 같은 내용을 리포 루트 `.demo-seed.json`에도 쓴다. 촬영 스크립트가 대회를
**이름이 아니라 id로** 가리키기 위해서다 — 이름으로 찾으려면 목록 화면이 먼저
있어야 하고, 그러면 아직 만들지 않은 화면 하나가 모든 장면의 선행 조건이 된다.

```ts
const { tournament, dealerOtp } = manifest;      // 픽스처가 읽어 준다
const table = tableByOrder(manifest, 1);
const otp = playerAt(manifest, 0).otp;          // 이름이 아니라 순서로
```

없으면 시끄럽게 죽는다. 무대 없이 진행하면 첫 실패가 404나 로그인 실패로
나타나서, 원인이 "시드를 안 돌렸다"라는 사실이 두세 겹 아래 묻힌다.

## 면이 넷이다

| 면 | 뷰포트 | 무엇 |
|---|---|---|
| `console` | 1440×900 | 상점 콘솔 |
| `scoreboard` | 1280×720 | 전광판 |
| `tablet` | 1280×720 | 좌석 태블릿 · 딜러 콘솔 (16:9) |
| `phone` | 390×844 | 참가자 폰 |

크기가 곧 설계다. 전광판은 10m 밖에서, 태블릿은 팔 길이에서, 폰은 손 안에서
읽힌다. 하나의 크기로 찍으면 그 차이가 영상에서 사라진다.

전광판을 1920×1080으로 찍지 않는다. 2×2 타일이 960×540이라 어차피 줄어들고,
면이 다 16:9라야 레터박스가 없다.

```ts
const phone = await stage('phone', 'demo-참가');
const board = await stage('scoreboard', '전광판');
```

`stage`가 면마다 **따로 된 브라우저 컨텍스트**를 연다. 쿠키가 섞이지 않아야
폰의 `demo`와 콘솔의 `owner`가 같은 실행 안에 공존한다. 두 번째 인자가 그대로
영상 파일 이름이 된다.

## 카메라 밖의 손

`fixtures/backstage.ts`에 있는 것은 **화면 없이 일어난다고 선언한 동작**이다.
로그인(토큰 발급), 착석(`POST /tournaments/:id/enter`), 테이블 상태 조회, 칩
총량 계산 넷이다.

칩 총량은 **스택의 합 + 팟**이고, 계산은 `backend/src/scenario/harness.ts`의
같은 이름 함수와 맞춘다. 촬영이 보는 불변식과 시나리오 테스트가 보는 불변식이
갈리면 어느 쪽이 사실인지 아무도 모르게 된다. (실제로 `bet`을 한 번 더 더해
총량이 4,300 부풀어 촬영이 멈춘 적이 있다.)

경계는 이렇게 긋는다. 상점이 대회를 시작하는 것, 사람이 OTP를 넣고 앉는 것,
딜러가 액션을 받는 것은 장면 자체라 브라우저로 한다. 반면 "나머지 참가자를 미리
앉혀 둔다" 같은 준비는 배경이고, 태블릿 여섯 대를 띄워 여섯 번 찍는 것은
영상에 아무것도 더하지 않으면서 실행 시간만 늘린다.

## 지금 있는 것 / 없는 것

`harness.spec.ts`는 **하네스 자신**을 검사한다. 앱의 화면을 단언하지 않는다 —
매니페스트와 DB가 같은 대회를 가리키는지, 영상이 이름 붙은 파일로 남는지,
매니페스트에 없는 것을 고르면 거기서 멈추는지 셋이다.

화면을 보는 것은 나머지 셋이고, 화면마다 **목이 못 잡는 것 하나**를 고른다.

| 스펙 | 잡는 것 |
|---|---|
| `console.spec.ts` | 대회 상세의 `{ tournament, seatStatus }` 봉투, `tables[].tableOrder`, 시작 전 대시보드가 **빈 본문 200**이라는 사실, `/me`의 `playerOtp`, 블라인드의 `sb * 2` 파생 |
| `dealer.spec.ts` | 딜러 OTP → bcrypt 대조 → `dealerToken` 쿠키 → 딜러 화면까지가 한 줄로 이어지는지 |
| `terminal.spec.ts` | 참가 OTP 입장이 Redis 좌석 비트를 올리고, 그 비트가 대기 화면의 점선으로 돌아오는지 |

빈 본문 200은 목으로는 확인할 수 없다 — 목은 항상 무언가를 돌려주기 때문이다.

## 데모는 장면 다섯이 **테스트 하나**다

`demo/tournament.spec.ts` 하나가 결제부터 테이블 합치기까지 이어서 돈다.
나눌 수가 없어서다 — **좌석이 컨텍스트에 매여 있다.** 자리에 앉으면 좌석
토큰이 그 태블릿의 쿠키로 심기고, 테스트가 끝나 컨텍스트가 닫히면 새 컨텍스트는
그 자리를 다시 잡을 수 없다(이미 사람이 앉아 있어 대기 화면의 그 자리가 점선으로
잠긴다). 실제 운영에서 태블릿이 자리에 고정된 것과 같은 제약이다.

| 장면 | 무엇 | 짝이 되는 시나리오 |
|---|---|---|
| 1 | 폰에서 결제하고 참가 OTP를 받는다 | T27 · T28 |
| 2 | 앉는다 · 대회가 열린다 · 한 판이 돌아 스택이 갈린다 | `full-flow` |
| 3 | 올인 → 사이드팟 두 층 → **딜러가 1등만 찍으면 거부** | `allin-sidepot` |
| 4 | 리바인 거절 → 탈락 → 폰에서 순위 | `elimination-rebuy` |
| 5 | 좌석 해제 → 옮겨 앉기 → 빈 테이블 닫기 | `table-move` |

**휴식을 기다리지 않는다.** `releaseSeats`가 요구하는 것은 `GamePhase.WAITING`
뿐이고(T29), 핸드가 정산되면 테이블이 자연히 그 상태로 돌아온다. 다음 핸드를
시작하지 않으면 레벨당 3분을 기다릴 이유가 없다.

**자르는 것은 ffmpeg다.** 스펙의 `mark()`가 장면 경계를 `timeline.json`에
시각으로 남기고, `scripts/make-demo-assets.mjs`가 그걸 읽어 자른다. 면마다
시계가 다르다는 것(녹화는 컨텍스트를 연 순간 시작한다)도 거기 같이 남으므로,
`tpad`로 앞을 검게 채워 전부 촬영 시작을 0초로 맞춘 뒤 자른다.

**스택을 손으로 벌리지 않는다.** 시드는 전원 5,000 균등인데 스택이 같으면
사이드팟이 갈리지 않아 장면 3의 경로가 아예 실행되지 않는다. 승자를 딜러가
입력하므로 누가 이길지는 촬영이 통제할 수 있고, 그래서 워밍업 핸드를 한 판 돌려
자연히 벌린다. 화면에 보이는 모든 숫자가 화면에서 벌어진 일의 결과다.

**단계마다 칩 총량을 본다.** 어긋나면 거기서 촬영을 멈춘다 — 시나리오 계층과
같은 이유다.

**누르는 것은 보이게 누른다.** `press()`가 커서를 먼저 목표 위로 보내고 한
박자 쉰 뒤 누른다. `click()`은 커서를 순간이동시킨 뒤 곧바로 눌러 **무엇을
눌렀는지가 프레임에 남지 않는다.** `slowMo`를 올리는 것으로는 안 된다 —
그건 키패드 여덟 번에도 같은 시간을 쓴다.

### 누른 것이 사라질 수 있다

`sendDealerAction`도 `sendPlayerAction`도 소켓이 안 열려 있으면 `console.error`
하나만 찍고 끝난다. 예외도 없고 화면도 그대로다. 딜러 화면은 SSR 스냅샷으로
펠트를 먼저 그리므로 **버튼이 보인다고 소켓이 붙은 게 아니다.**

이 구멍으로 촬영이 세 번 당했다 — 한 번은 팟 0에 차례 -1로 조용히 통과했고,
한 번은 20초를 기다리다 죽었다. 그래서 `pressUntilEffective`와 액션 재시도는
**"눌렀다"가 아니라 "상태가 바뀌었다"를 성공으로 삼는다.** 새 조작을 추가하면
같은 규칙을 쓴다.

### 시계를 맞추는 것이 제일 어려웠다

**Playwright의 녹화는 컴포지터가 프레임을 낼 때만 받아 적는다.** 남의 차례를
기다리며 몇십 초 가만히 있는 좌석 태블릿은 그 구간에 프레임이 거의 없어
영상이 실제보다 11% 늘어나 있었고, 빈 탭으로 열어 두었다가 늦게 `goto`한
콘솔은 0초가 그 `goto` 시점이었다. 면을 나란히 붙이는 촬영에서 이건 **같은
순간에 서로 다른 장면**으로 나타난다.

파일이 적어 둔 길이(`Duration`)로 배율을 만들어 보정하는 방법은 더 어긋났다 —
밀림이 구간마다 다르다. 그래서 원인을 없앴다: `cursor.ts`가 **보이지 않는 점
하나를 100ms마다 다시 칠한다.** 그 뒤로 면 일곱의 파일 길이가 실제 구간과
0.4% 안에서 맞는다.

같은 이유로 **면을 처음부터 켜 둔다.** 상점 콘솔은 대회 내내 열려 있고 좌석·
딜러 태블릿은 대기 화면을 띄운 채 사람을 기다린다 — 운영이 실제로 그렇고,
그래야 타일에 검은 사각형이 안 생긴다.

### 촬영은 프로덕션 빌드로 돈다

개발 서버는 화면마다 좌하단에 Next 개발 표시기를 앉히고, 라우트를 처음 열 때
컴파일하느라 12초씩 흰 화면을 남긴다. 둘 다 영상에 그대로 들어간다.
`scripts/demo.mjs`가 빌드하고 `DEMO_PROD=1`로 프로덕션 서버에 붙인다. 스펙만
고치며 여러 번 돌릴 때는 `node scripts/demo.mjs --no-build`.

## webm 말고 다른 것이 필요하면

Playwright가 내놓는 것은 webm 하나뿐이다. `npm run assets`가 ffmpeg로 자르고
합쳐 애니메이션 WebP와 PNG로 바꾼다.

ffmpeg는 **`ffmpeg-static` 개발 의존성**이다. Playwright도 ffmpeg를 번들로 갖고
있지만(`ms-playwright/ffmpeg-*`) `--disable-everything` 빌드라 webm 디코드까지만
되고 **애니메이션 webp 인코딩도 hstack/vstack도 없다.** 시스템에 설치하지
않는다 — 리포와 함께 지워지고 CI에서도 같은 바이너리다.
