# 부하 봇

k6가 도는 자리다. 무대(컨테이너·메트릭)는 T39가 세웠고
(`backend/docker-compose.test.yml`), 여기는 그 위에서 **사람 노릇을 하는 코드**다.

```
lib/api.js         REST 체인. 회원가입부터 WS 티켓까지 제품 경로 그대로
lib/table.js       VU 하나가 테이블 하나를 든다. 소켓 열 개
lib/monitor.js     서버 지표를 주기적으로 읽어 시계열로. 경고·붕괴 판정
lib/summary.js     결과를 results/에 파일로
scenarios/smoke.js 테이블 하나로 "봇이 규칙대로 도는가"만 본다
scenarios/ramp.js  성장 램프. 테이블을 계속 붙이며 정원과 피크 내성을 본다
results/           실행 결과 (git에 안 들어간다)
.load-seed.json    시드가 떨어뜨리는 무대 좌표 (git에 안 들어간다)
```

## 실행

```bash
npm run load:up        # 백엔드를 1코어 컨테이너로 (첫 실행은 빌드 몇 분)
npm run seed:load      # 무대를 세운다 — 전부 지우고 다시 만든다
npm run load:smoke     # 스모크
npm run load:ramp-b    # 성장 램프 — 대회 하나 안에서 테이블을 늘린다
npm run load:ramp-a    # 성장 램프 — 6테이블마다 다음 대회로
npm run load:down      # 정리
```

**`load:down`은 `-v`라 마이그레이션까지 지운다.** 다시 세울 때는 시드 앞에
`cd backend && npx prisma migrate deploy`가 필요하다(부하 스택에는 통합
테스트의 `global-setup` 같은 자동 마이그레이션이 없다).

시드를 호스트에서 돌릴 때는 테스트 인프라를 가리켜야 한다.

```bash
DATABASE_URL="postgresql://test:test@127.0.0.1:5433/playsync_test" \
REDIS_HOST=127.0.0.1 REDIS_PORT=6380 REDIS_PASSWORD=test \
npm run seed:load
```

**통합 테스트와 저장소를 나눠 쓴다.** 부하 실행 중에 `npm run test:int`를 돌리면
서로 데이터를 지운다. 동시에 돌리지 않는다.

## VU 하나 = 테이블 하나

이 하네스의 핵심 결정이다. 재려는 것 중 하나가 **"남이 누른 액션이 내 화면에
뜨기까지"**인데, k6는 VU 사이에 상태를 공유하지 않는다(`SharedArray`는 읽기
전용). VU를 사람 하나에 대응시키면 보낸 쪽과 받은 쪽이 다른 VU라 시계를 맞출
수 없어 그 지연을 **아예 잴 수 없다.**

한 VU가 좌석 아홉 + 딜러 하나, 소켓 열 개를 들면 두 지연이 같은 시계 위에
놓인다. 램프에서 테이블 100개는 VU 100개, 소켓 1,000개다.

## 제품 경로를 그대로 탄다

토큰을 미리 발급해 두고 건너뛰지 않는다.

```
POST /auth/join                bcrypt.hash
POST /auth/login               bcrypt.compare
POST /tournaments/payment      참가 행 · 참가 OTP · 거래 내역 · 프라이즈풀
GET  /user/me/participations   OTP 조회 (대회 직전에 전원이 한 번씩 친다)
POST /tournaments/:id/enter    좌석 확정 → 좌석 토큰
POST /ws/ticket                1회용 티켓 (소켓마다 하나, 재사용 불가)
WS   /playsync?ticket=..&tableId=..   Origin 헤더 필수
POST /dealer/auth              bcrypt.compare — 테이블마다 한 번
```

프론트(Next)는 타지 않는다 — 측정 대상을 게임 서버로 좁힌다.

### bcrypt 둘은 일어나는 시점이 다르다

처음에는 좌석마다 가입과 로그인을 둘 다 태웠다. 그러면 bcrypt가 사람당 두 번
돌아 **실제의 두 배**가 되고, 정원이 낮게 나온다.

| | 실제로 언제 | 측정 안에 있어야 하나 |
|---|---|---|
| `hash` (가입) | 몇 주 전, 흩어져서 | 아니다 — 소수 비율만 |
| `compare` (로그인) | 대회 직전, 몰려서 | **그렇다** — 문 앞의 부하 |

실제 홀덤펍에서 대회 직전에 몰리는 것은 로그인이다. 손님 대부분은 계정이 이미
있고, 그날 새로 만드는 사람은 첫 방문자 소수뿐이다.

그래서 **계정은 시드가 풀로 만들어 두고**(해시를 한 번 계산해 복사하므로 비용이
거의 없다) 봇은 로그인만 탄다. 신규 가입은 `LOAD_NEW_USER_RATIO`(기본 10%)
만큼만 실행 중에 한다. 풀이 모자라면 자동으로 신규로 넘어가고, 그 사실은
`signups` 카운터에 남는다.

풀 계정은 `p0000` 형식이고 크기는 `LOAD_ACCOUNT_POOL`(기본 600)이다. 테이블마다
`poolBase`를 밀어 줘야 한다 — 겹치면 `@@unique([tournamentId, userId])`가 두
번째를 409로 막는다.

## 생각 시간이 부하의 모양을 정한다

봇은 생각하지 않으므로 그대로 두면 테이블 하나가 **초당 두 핸드**를 돈다.
실제 라이브는 시간당 25~30핸드다. 350배 빠른 부하로 잰 정원은 정원이 아니다.

처음에는 고정 7초를 썼다가 버렸다. **이벤트 루프를 밀어붙이는 것은 평균이
아니라 몰림**이고, 고정값은 부하를 매끄럽게 펴서 순간 부하를 실제보다 작게
만든다. 실제 테이블의 액션은 두 종류로 갈린다.

| | 무엇 | 기본값 |
|---|---|---|
| 거의 즉시 | 체크·폴드·콜. 낼 것이 정해져 있다. 연달아 몰린다 | 2초 |
| 오래 | 레이즈 사이즈, 큰 팟에서의 콜 판단 | 18초, 비율 15% |
| 자리 비움 | 아예 안 누른다. 서버 타임아웃에 맡긴다 | 비율 3% |
| 지각 | 마감 직후에 누른다 | 30.3초, 비율 2% |
| 핸드 사이 | 딜러가 카드를 회수·셔플·딜링한다 | 25초 |

앞의 둘은 절반~1.5배로 흩고 30초를 넘기지 않는다.

**자리 비움과 지각은 없으면 안 되는 경로다.** 봇이 언제나 30초 안에 누르면
`TIME_OUT` 잡이 한 번도 돌지 않는다 — 그 경로는 BullMQ 큐 → 락 → 스냅샷 쓰기 →
브로드캐스트를 전부 쓰는 진짜 부하이고, 실제 대회에는 자리를 비운 사람이 늘
있다. 지각은 **마감 시각 판정**(`playsync.service.ts:86` — "판정 기준은 요청
도착 순서가 아니라 마감 시각이다")을 밟는 유일한 경로다.

**핸드 사이에 팟을 미는 시간은 없다.** 칩이 디지털이라 정산과 지급을 서버가
`resolveWinners`에서 끝낸다. 딜러에게 남는 물리 작업은 카드뿐이다 — 회수 3~5초,
손 셔플·컷 10~15초, 딜링 9인 2장 8~12초. 합쳐 21~32초라 25초로 둔다.

기본값이면 핸드 하나가 약 2분이라 시간당 27핸드쯤 된다. 환경변수로 덮는다:
`LOAD_THINK_FAST_MS` · `LOAD_THINK_SLOW_MS` · `LOAD_THINK_SLOW_RATIO` ·
`LOAD_DEAL_MS`.

**스모크는 셋 다 0이다.** 보는 것이 정원이 아니라 "봇이 규칙대로 도는가"라,
라이브 속도로 돌리면 30초에 핸드 하나도 못 끝낸다.

## 액션 믹스 — 콜만 하면 아무도 안 터진다

봇은 처음에 콜만 했고 딜러는 폴드 안 한 **전원**을 승자로 넣었다(보드 하이).
그러면 팟이 낸 만큼 되돌아와 **탈락자가 한 명도 안 나오고**, `resolveWinners`의
리바인 분기(`dealer.service.ts:309`)가 실행 내내 한 번도 돌지 않는다. 부하의
한 갈래(리바인 · 탈락 · 사이드팟)가 통째로 비어 있었다.

| | 기본값 | 왜 필요한가 |
|---|---|---|
| 체크·콜 | 나머지 65% | 핸드가 끝까지 가야 플랍·턴·리버·쇼다운이 전부 돈다 |
| 레이즈 | `LOAD_RAISE_RATIO` 0.2 | `resetChecked()`가 돌아 라운드가 한 바퀴 더 간다. 액션 수와 fan-out이 곱해진다 |
| 폴드 | `LOAD_FOLD_RATIO` 0.15 | 없으면 사이드팟이 안 생기고 팟이 늘 전원 분배다 |
| 딜러 승자 | 무작위 한 명 | 칩이 쏠려 탈락자가 나온다 |
| 리바인 | 즉시 수락 | 좌석이 비지 않아 규모 축이 인원 감소로 흔들리지 않는다 |

**합법인 것 중에서만 고른다.** 불법 액션은 엔진이 거절하는데, 그 거절이 부하에
섞이면 재는 것이 게임이 아니라 에러 경로가 된다. 레이즈의 `amount`는 목표
**총** 베팅액이고 최소 레이즈 규칙이 없다 — 스택을 넘으면 `executeBet`이 잘라
올인이 되고, 그 자리가 사이드팟을 만든다.

리바인 수락의 대가는 `processRebuy`가 락 **밖에서** 최대 15초 기다리는 동안
`HAND_END`가 다음 핸드를 막는 것이다. 핸드 주기가 늘어나지만 실제 대회도 그렇다.

## 성장 램프

붙은 테이블은 내려가지 않는다. 계단 램프(단계마다 세우고 재고 내린다)를 버린
이유는, 그러면 재는 것이 "N테이블의 부하"가 아니라 **"N테이블을 세우는 비용"**이
되기 때문이다.

질문이 둘이고 **같은 실행의 다른 구간이 답한다.**

| 구간 | 태그 | 답하는 질문 |
|---|---|---|
| 증설 | `grow-N` | 몰림을 어디까지 견디나 (피크 내성) |
| 고원 | `steady-N` | 동시접속을 어디까지 받나 (정원) |

`N`은 그 순간 실제로 도는 테이블 수다. **예정표가 아니라 `exec.instance.vusActive`
에서 읽는다** — 증설이 느려지면(로그인이 밀리면) 예정표와 실제가 어긋나고, 램프가
무너지는 구간이 바로 그 구간이라 태그가 거짓말을 하면 안 된다. 모니터 VU 하나를
빼서 숫자가 곧 테이블 수가 되게 한다.

램프 A와 B는 파일 하나이고 `LOAD_TABLES_PER_STORE`로 갈린다.

| | 값 | 무엇을 본다 |
|---|---|---|
| 램프 B | 미설정(0) | 대회 하나 안에서 테이블을 늘린다. `SEAT_LIST_UPDATED`의 O(T²) 곡선 |
| 램프 A | 6 | 6테이블마다 다음 대회로. "홀덤펍이 하나 더 생겼다" |

**대회는 시드가 미리 세운다**(`LOAD_STORES`, 기본 12). 램프가 실행 중에 만들 수
없다 — k6는 VU 사이에 상태를 공유하지 않으므로 7번째 VU가 앞선 VU가 만든 대회의
id를 알 방법이 없다. 측정 밖에 두는 것이 옳기도 하다: 대회 생성은 실제로 몇
시간~며칠 전에 한 번 하는 일이고, 직전에 몰리는 것은 로그인과 착석이다.

**대회 시작은 착석 뒤다.** `startSession`이 최소 인원을 세므로(`MIN_PLAYERS_TO_START`)
아무도 앉기 전에는 409다. 대회마다 첫 VU가 자기 좌석을 채운 뒤 한 번만 부른다 —
두 번 부르면 `initializeGame`이 다시 돌아 이미 도는 테이블을 갈아엎는다.

### 언제 멈추나

| 선 | 값 | 사람이 느끼는 것 |
|---|---|---|
| 합격 | 내 액션 p95 200ms | 즉각 |
| **불편** | **내 액션 p95 1초** | **"이거 왜 이래"** |
| 실패 | 3초 | 안 먹은 줄 알고 다시 누른다. 중복 액션이 또 얹힌다 |
| 붕괴 | 서버 lag p95 100ms | 서버가 무너지는 중 |

일반 웹보다 낮게 잡는 이유가 도메인에 있다. 턴 타이머가 30초라 지연이 커지면
증상이 "느리다"가 아니라 **폴드당한다**로 바뀐다 — 돈이 걸린 실패다.

먼저 닿는 것으로 멈춘다. 테이블 VU가 자기 롤링 창 30건의 p95로, 모니터가 서버
lag으로, 각각 **연속 2회**에 `exec.test.abort()`. **k6 `thresholds`로는 못 한다** —
실행 전체 누적이라 성장 램프에서는 앞 단계의 좋은 표본이 뒤 단계의 나쁜 표본을
희석한다.

### 환경변수

| 이름 | 기본 | 무엇 |
|---|---|---|
| `LOAD_START_TABLES` | 4 | 첫 단계의 테이블 수 |
| `LOAD_STEP_TABLES` | 2 | 단계마다 몇 개씩 |
| `LOAD_MAX_TABLES` | 66 | 상한. 계정 풀 600이 594명(66테이블)을 덮는다 |
| `LOAD_GROW_S` | 30 | 한 단계를 늘리는 데 주는 시간. 짧을수록 험한 몰림 |
| `LOAD_STEADY_S` | 180 | 고원. 핸드 하나가 약 2분이라 그보다 길어야 한다 |
| `LOAD_TABLES_PER_STORE` | 0 | 0이면 램프 B, 6이면 램프 A |
| `LOAD_MY_ACTION_ABORT_MS` | 1000 | 불편선 |
| `LOAD_BREACH_STREAK` | 2 | 몇 번 연속으로 넘어야 멈추나 |
| `LOAD_RECONNECT_AT_TABLES` | 0 | 이 테이블 수의 고원 중간에 재접속 폭발. npm 스크립트는 30 |
| `LOAD_STORES` | 12 | 시드가 세우는 상점·대회 수 |

### 재접속 폭발

별도 실행이 아니라 **고원 중에 한 번 일어나는 사건**이다. 별도로 두면 규모 축이
하나 더 생기고 실행 시간만 배가 된다.

전 VU가 같은 절대 시각에 소켓 열 개를 통째로 끊고 다시 붙는다. **지터를 걸지
않는다** — 실제 모양이 "배너를 본 사람들이 동시에 새로고침"이고
(`SeatGameClient.tsx:118`에 자동 재접속이 없다) 백오프가 낄 자리 자체가 없다.

**티켓은 1회용이라 소켓마다 새로 받아야 한다.** 그래서 이 사건은 WS만이 아니라
`POST /ws/ticket`을 전원이 동시에 치는 REST 부하이기도 하다.

`reconnect_ms`는 **다시 붙은 소켓 전부가 첫 `renderGame`을 받기까지**다. 소켓을
여는 데 걸린 시간이 아니라 화면이 다시 살아나기까지가 사람이 겪는 시간이다.

### 단계별로 읽는다

```bash
node scripts/load-report.mjs load/results/ramp-b-raw.json
```

원시 시계열을 `step` 태그로 갈라 단계마다 한 줄씩 낸다. 요약 하나로는 "터졌다"
까지만 알 수 있고, 필요한 것은 **어느 테이블 수에서 꺾였는가**다.

## 지표

| 이름 | 무엇 | 합격선 |
|---|---|---|
| `my_action_ms` | 내가 누른 버튼이 내 화면에 반영되기까지 | p95 < 200ms |
| `others_action_ms` | 남이 누른 액션이 내 화면에 반영되기까지 | p95 < 500ms |
| `hands_played` | 완주한 핸드 수 | > 0 |
| `socket_errors` | 서버가 거절한 소켓 | == 0 |
| `rebuys_accepted` | 리바인 수락 수. 탈락 경로가 실제로 돌았다는 증거 | > 0 |
| `raises` · `folds` | 액션 믹스가 의도대로 나왔는지 | > 0 |
| `table_create_conflicts` | 테이블 생성이 409로 거절된 횟수 | 기록용 |
| `table_setup_ms` | 테이블 하나를 열고 좌석 아홉을 채우기까지. 증설 비용 | 기록용 |
| `reconnects` · `reconnect_ms` | 재접속 폭발 횟수와 복구 시간 | 기록용 |

`hands_played`와 `socket_errors`가 있는 이유는 같다 — **소켓만 붙어 있고 아무
일도 안 일어나는 실행**의 지연 수치는 아무것도 의미하지 않는다. 촬영에서 배운
것과 같은 자리다(눌렀다가 아니라 상태가 바뀌었다를 성공으로 삼는다).

## 언제부터 무너졌는지를 남긴다

실행이 끝난 뒤의 요약 하나로는 **"터졌다"까지만** 알 수 있다. 정작 필요한 것은
언제부터 지연이 보이기 시작했고 언제 급해졌는가다 — 그게 있어야 "몇 개까지"의
답이 나온다.

모니터 VU가 5초마다 `/internal/metrics`를 읽어 시계열로 남기고 두 선으로
판정한다.

| 선 | 값 | 뜻 |
|---|---|---|
| 경고 | lag p95 20ms | 지연이 보이기 시작한다. 사람은 아직 못 느낀다 |
| 붕괴 | lag p95 100ms | 무너지는 중이다. 내 액션 합격선(200ms)의 절반 |

**바닥값을 빼고 기록한다.** `monitorEventLoopDelay`가 샘플링 간격(10ms)만큼을
늘 얹어 돌려주므로, 빼지 않으면 시계열 전체가 그만큼 들려 있어 기준선이
흐려진다. 읽는 행위 자체가 창을 닫고 다시 여는 것이라 각 샘플은 **직전 샘플
이후 구간**을 덮는다 — 누적 평균이 아니다.

결과는 `results/`에 두 가지로 쌓인다.

```
<name>-<timestamp>.json   요약 (지표·임계 판정·서버 지표)
<name>-latest.json        마지막 실행 (타임스탬프를 찾아 들어가지 않아도 된다)
<name>-raw.json           --out json=이 남기는 원시 시계열 (모든 샘플, 태그 포함)
```

단계 태그(`step`)가 붙으므로 원시 파일에서 "테이블 12개 구간의 lag"처럼 갈라
볼 수 있다.

## 실측이 잡은 것 셋

봇을 짜면서 나온 것들이고, 전부 처음에는 조용히 잘못된 수치를 냈다.

- **지연 측정 창은 큐여야 한다.** 창을 하나만 두고 "열려 있으면 새 액션을
  막는" 방식이었는데 테이블이 멈췄다. 브로드캐스트 하나를 소켓 열 개가 각자
  처리하는데, 세 번째 소켓이 "내 차례다"를 볼 때는 아직 일곱이 안 받아 창이
  열려 있었다.
- **중복 예약을 막아야 한다.** 자기 차례인 동안 브로드캐스트가 올 때마다
  `step`이 다시 불려 액션을 또 예약했다. 중복 액션은 서버가 무시하지만
  브로드캐스트는 그대로 나가고, 그러면 창과 수신이 하나씩 어긋나 **생각 시간이
  그대로 지연으로 잡혔다** — 실측에서 정확히 `THINK_MS`만큼 나왔다.
- **WS 경로는 `/playsync`다.** 루트로 붙으면 핸드셰이크 이전에 거절돼 서버
  로그에도 남지 않는다. 소켓 열 개가 조용히 다 죽었다.
- **재접속이 예약된 액션을 죽인다.** 생각 시간이 최대 30초라 그 사이에 폭발이
  끼면, 예약된 `setTimeout`이 닫힌 소켓에 `send`를 불러 `InvalidStateError`로
  VU가 통째로 죽는다. 버린 소켓에는 표시를 달아 예약 발사·수신·종료 판정을 전부
  건너뛴다 — 표시가 없으면 우리가 끊은 것이 `socket_errors`로 잡히기도 한다.
- **`BlindStructure.name`이 전역 유니크다**(상점 범위가 아니다). 상점을 여럿
  세우면서 드러났다.
- **죽은 소켓 하나가 지연 지표를 통째로 부풀린다.** 창 큐를 "소켓 열 개가 다
  본 창"에서 걷어내는데, 하나가 죽으면 그 창이 영영 안 채워져 큐 앞에
  눌러앉고 뒤에 오는 메시지가 점점 더 오래된 창에 붙는다. 램프 B 첫 실행이
  그렇게 죽었다 — **서버 lag 0.4ms · CPU 1.8%인데 한 VU가 p95 1989ms를 보고
  실행을 중단시켰다.** 살아 있는 소켓으로 세고, 10초 넘게 응답이 없는 창은
  표본에서 버린다(`stale_windows`에 남긴다).
- **WS 티켓은 30초 만에 만료된다.** 열 개를 미리 받아 두고 순차로 붙으면
  부하가 커질 때 마지막 소켓이 만료된 티켓으로 1008을 받는다. 티켓은 **소켓을
  여는 자리에서** 받는다. 위 항목의 방아쇠가 이것이었다.
